はじめに

夕方、台所に立って「カレーを作ろう」と考えます。冷蔵庫には肉と野菜があります。鍋も包丁もあります。それでも、目の前の材料が勝手に一皿のカレーになるわけではありません。何人分を作るのか、何をどれだけ使うのか、どの順序で作業するのかを決める必要があります。

プログラミングも、ここから始まります。Pythonの文法を知っているだけでは、カレーを作る仕事は定義できません。「材料を処理する」と書けても、その処理が洗浄なのか、切断なのか、加熱なのかを知らなければ、コンピュータに実行してほしい内容が決まらないからです。

本書は、Pythonの文法を覚えることから始まりません。カレーの作り方を考えることから始まります。肉と野菜を渡すと、カット済みの具材を受け取る。具材を加熱すると、盛り付けに進める状態になる。こうした仕事に名前を付け、必要な情報を受け取り、結果を返す仕組みが、プログラムの「関数」です。

ところが、現実の仕事は成果物だけでは語れません。鍋は汚れ、在庫は減り、コンロが故障すれば途中で止まります。何が変わったのか。誰に知らせるのか。失敗したあと、もう一度実行してよいのか。この問いをたどると、引数、戻り値、副作用、状態、例外、テストという概念が、暗記すべき用語ではなく、仕事を説明するために必要な言葉として現れてきます。

本書で作るのは、調理ロボットではありません。コンピュータの中に材料の量や工程の状態を記録し、その記録を一定の約束に従って更新する、教育用のシミュレーターです。画面に「加熱完了」と出ても、現実の鍋に火が通った証拠にはなりません。この区別を大切にしながら、見えにくいソフトウェアの仕組みを、見慣れた仕事に結び付けます。

読み終えたとき、関数の書式より先に「この仕事の完成とは何だろう」「前工程から何を受け取るのだろう」と考えられるようになっていれば、本書の目的は達成されています。いつもの帳票づくりにも、在庫確認にも、検査結果の集計にも、同じ問いを向けてみてください。プログラムを書く前の理解こそが、自動化の土台になります。

この本の読み方

第Ⅰ部は、パソコンがなくても読めます。紙に工程や材料を書き出してください。第Ⅱ部からは、短いプログラムを一つずつ実行します。長いコードを打ち込む前に「何が表示されるか」「どの値が返るか」を予想すると、理解の穴を見つけやすくなります。第Ⅳ部で設計と検証を学び、第Ⅴ部で一つのシステムにまとめます。

各章のコードは、特記がなければ、その枠全体を新しいファイルにコピーして実行できます。実行結果は枠の下に示します。「シミュレーターを読み込む」とある例だけは、付録Eのファイルを同じフォルダーに置いてください。図はクリックで拡大できます。演習の解答は開閉でき、印刷時にはすべて表示されます。

本書では短い導入例に日本語の関数名を使い、後半で英語の名前に移行します。日本語は仕事との対応が明瞭である一方、共同開発では英語の名前が広く使われます。大切なのは、難しい英語を使うことではなく、同じ概念に同じ名前を付けることです。

対象バージョンと検証範囲

2026年10月12日に確認した現行安定版はPython 3.15.0です［S1］。本書はその公式資料を参照し、3.12以降に共通する基本構文を中心に記述しています。実行検証のバージョンと件数は末尾の「制作・検証記録」に記載します。資料上の適合確認と、実際に動かした環境は区別しています。

本書で使う料理モデル

基本カレーの1人分は、肉100 g、玉ねぎ75 g、じゃがいも75 g、にんじん40 g、ルー25 g、水250 mL、炊飯済みご飯180 gと仮定します。分量は計算練習用であり、実際の製品の調理説明ではありません。材料の量は原則として非負の整数で表し、必要量は正の整数とします。水と具材の単位を混ぜて足すことはしません。

実際の調理では、使用する食材や製品の説明、適切な衛生管理と加熱確認が必要です。本書の「6ステップで加熱完了」は仮想工程の規則にすぎません。時間、中心温度、食品の安全性を計算するものではありません。ご飯は炊飯済みを入力とし、炊飯工程はモデルの外に置きます。洗浄や器具の片付けも考察には含めますが、完成版の工程シミュレーターでは詳細を計算しません。

本書を通じて持ち続ける問い：何を完成と呼ぶか。何を受け取るか。何を返すか。何が変わるか。失敗したらどうするか。どう確かめるか。

第Ⅰ部　プログラムを書く前に、カレーを理解する

第1章　カレーの作り方を知らずに、カレーを作るプログラムは書けない

1.1　プログラミングができても料理ができるとは限らない

「夕飯を自動で作るプログラムを書いてください」と頼まれたとします。プログラマーは、使える機械や言語を調べるかもしれません。しかし、その前に聞くべきことがあります。誰が食べるのか。何時までに必要なのか。どのような一皿を望んでいるのか。これらが決まらなければ、どれほど正確に動く機械でも、期待と違う結果を作れます。

コンピュータが得意なのは、定められた処理を繰り返すことです。依頼の裏にある事情を自動的に満たしてくれるわけではありません。たとえば4人分の材料で2皿だけを盛り付けても、「鍋の中身を二つの皿に分ける」という命令には従っています。けれども4人が夕食を食べるという目的は達成していません。

プログラムの動作が正しいことと、仕事の結果が正しいことは別です。この間をつなぐために、仕事を知っている人と、実装する人との対話が必要になります。同じ人が両方を担当するときも、自分の中で二つの立場を切り替えて考えます。

1.2　レシピとは何か

レシピは作業の順番を並べた文章であると同時に、材料や道具、判断基準を共有するための取り決めです。「玉ねぎを炒める」という一行も、玉ねぎが用意されていること、加熱器具が使えること、作業者が適切な扱いを知っていることを前提にしています。

人間向けのレシピは多くを省略できます。読者が常識で補えるからです。しかし自動化では、その省略が問題になります。「適量」「十分に」「いつものように」は、誰かが判断できるうちは便利でも、機械の処理としては未定義です。すべてを数字にする必要はありませんが、誰が何を基準に判断するかは決めなければなりません。

本書では、仕事の約束を記したものを「仕様」と呼びます。レシピ全体がそのままプログラムの仕様になるとは限りません。現実の作業のうち何を扱うか、扱わない部分を誰が担うかまで決めて初めて、システムの範囲が定まります。

1.3　カレーの完成とはどのような状態か

完成の定義を「完成と表示されること」にすると、最初からそう表示するだけで合格になってしまいます。表示は証拠になり得ますが、完成条件そのものではありません。本書の工程モデルでは、材料が確保され、下ごしらえが終わり、必要な仮想加熱ステップを終え、人数分の盛り付け段階まで到達したことを完成条件にします。

観点 現実の夕食 本書の工程モデル
分量 食べる人に十分か 人数に応じて必要量を計算したか
状態 食材に適切な処理がなされたか 定めた工程を順に通過したか
提供 食べられる形で提供されたか 盛り付け完了の状態か
安全 現実の食材・器具・衛生状態の確認 判定しない。現実の安全は保証しない

この表の右欄を満たしても、左欄すべての保証にはなりません。モデルとは、現実の一部を、ある目的に合わせて表したものです。地図に道が描かれていても実際の道そのものではないのと同じです。

1.4　作業と目的を混同しない

「20回かき混ぜた」は作業の記録です。「ルーが均一に混ざった」は結果の状態です。前者を実行すれば常に後者になるとは限りません。鍋の大きさや量が変われば、同じ回数では足りないこともあります。作業回数を測るのは便利ですが、目的との関係を検討しなければなりません。

業務でも「報告書を送った」と「必要な判断材料が相手に届いた」は違います。本書のシミュレーターは単純な規則を採用しますが、それは現実を十分に表現したからではなく、学習したい構造を取り出すためです。規則を選ぶ理由を説明できることが、設計の第一歩になります。

1.5　業務知識とプログラミング知識は別物である

業務知識は、何を作るべきか、何が失敗かを判断する知識です。プログラミング知識は、その判断や作業をコンピュータ上で表す知識です。料理をよく知る人がPythonを学ぶときには、すでに持っている知識が設計の材料になります。一方、料理を知らない人がPythonだけで不足を埋めようとすると、動くけれど役に立たないものを作りやすくなります。

まず仕事を言葉で説明し、分からない部分を質問として残しましょう。「肉をどれだけ使うか未確認」と書けることは前進です。未確認の条件を、勝手に決めた数値で隠すより、後から確かめる場所が明確になります。

場面を具体化する

2人分の夕食を考えます。「基本カレー、炊飯済みご飯あり、材料は在庫から使用、足りなければ開始しない」と決めると、何を数え、何を確かめるかが見えてきます。まだPythonは不要です。完成条件を文章で読み合わせるだけでも、半分しかできていない仕事を「完了」と扱う誤りを防げます。

よくある間違いは、例外をすべて後回しにすることと、知っているつもりの言葉を確認しないことです。「人数」は食べる人数なのか、標準的な一皿の数なのか。今回は後者と結び付け、一人一皿のモデルに固定します。

演習1　完成条件を言葉にする

  1. 「カレーを作る」を、完了したかどうか確かめられる三つ以上の条件に分けてください。
  2. 「10分煮込む」と「具材が目的の状態になる」は、どちらが作業で、どちらが結果ですか。
  3. 本書のモデルだけでは判断できない現実の条件を二つ挙げてください。
解答と考え方

  3. 食品の実際の加熱状態、アレルギーへの適合、器具の清潔さなどです。画面上の状態から推測して合格にしてはいけません。

第2章　カレーづくりを分解する

2.1　大きな仕事を小さな仕事に分ける

初めての人に「カレーを作って」と頼むと、何から始めればよいか分からないかもしれません。しかし「材料を確認する」「具材を準備する」「加熱する」「盛り付ける」に分けると、質問すべき場所がはっきりします。大きな仕事を小さな仕事に分けることを、ここでは「分解」と呼びます。

分解には二つの効用があります。一つは、個々の作業を理解しやすくすることです。もう一つは、担当や変更の境目を作れることです。盛り付けだけ変更したいときに、下ごしらえまで考え直さずに済むようにします。ただし、分ければ自動的に独立するわけではありません。受け渡す材料の状態が関係するため、次章の入出力の約束も必要です。

2.2　下ごしらえ・加熱・盛り付け

「カレーを作る」の直下に、下ごしらえ、加熱、盛り付けを置きます。これらはおおむね同じ程度の大きさの仕事です。そこに「じゃがいもを一回切る」を並べると、大きさの違う項目が混ざり、全体が読みづらくなります。同じ段には、同じくらいの詳しさの仕事を並べるのが出発点です。

材料の購入を入れるべきかは目的次第です。今回は、材料は在庫として与えられ、在庫の確認と確保を調理の前に置きます。買い物リストは第12章の練習に登場しますが、最終シミュレーターが実際に購入するわけではありません。範囲を決めると、必要な機能と、説明のためだけの例を区別できます。

2.3　下ごしらえをさらに分解する

下ごしらえには、肉を切る、野菜を扱う、必要な量を分ける、といった作業が含まれます。さらに「野菜を扱う」を、確認する、洗う、皮など不要部分を除く、切る、と分けられます。現実の衛生管理では食材や器具の扱いも重要ですが、工程モデルでは「下ごしらえ完了」という一段階にまとめます。

ここで大切なのは、詳しく考えたことと、すべてをコードにすることは同じではないという点です。内部にどのような作業があるか理解したうえで、学習目的上は一つの処理にまとめる判断もできます。「知らないので省略した」のか、「理解したうえで範囲外とした」のかでは、説明の信頼性が違います。

2.4　作業の階層構造を樹形図で表す

樹形図の上は大きな仕事、下はそれを構成する小さな仕事です。線は「この仕事が、この仕事を担当させる」という関係を表します。図の上から下へ食材が流れる、という意味ではありません。肉を切る処理の結果が野菜を切る処理の入力になるとは限らないからです。

木の枝分かれは、作業が同時に動くことも意味しません。この図だけでは、順序や同時実行の有無は決まりません。実行順序を説明したいときは、別の工程図や、順序を明記した手順が必要です。図の線に一つの意味を与えることが、図解の正確さを支えます。

2.5　分解はどこで止めればよいのか

包丁を握る指の動きまで分解したら、説明は膨大になります。反対に、すべてを「調理する」の一言で済ませれば、何も検討できません。止める目安は、その仕事について入力、出力、失敗条件、確認方法を説明できることです。

たとえば工程管理だけが目的なら「下ごしらえ」は一つの単位で十分かもしれません。切断ロボットを制御するなら、それでは粗すぎます。分解の細かさは、扱う問題と、仕事を任せる相手の能力によって変わります。プログラムの関数も、いつも同じ行数にすればよいわけではありません。

もう一つの目安は、名前で約束を伝えられることです。「処理1」では役割が見えません。「必要量を計算する」なら、入力が人数やレシピで、出力が必要量だと推測できます。名前を付けにくい仕事は、複数の目的が混ざっている可能性があります。

2.6　作業の抜け漏れと重複を発見する

分解表を作ったら、最初から最後まで一回分の仕事を通してみます。盛り付けるときにご飯がないなら、炊飯済みご飯を入力に入れるか、炊飯を工程に追加する必要があります。「誰かが用意するだろう」は、責任が未定の状態です。

重複にも注意します。材料確認と下ごしらえの両方で在庫を減らすと、一回の調理で二回分を使った記録になります。「在庫を減らすのは材料確保の時点だけ」と決めれば、どの工程が数量を扱うかが明確になります。作業を分けることは、責任を割り当てることでもあります。

第4章　カレーづくりの失敗を考える

4.1　材料不足

2人分を作るつもりなのに、肉が150 gしかありません。必要量は200 gなので50 g不足しています。「肉がない」よりも「肉が50 g不足している」と伝える方が、次の判断に役立ちます。失敗の通知は、単に止めるためでなく、何を修正すればよいか示すためにもあります。

不足時の方針には、買い足す、人数を減らす、別のレシピにする、中止するなどがあります。プログラムが勝手にどれかを選ぶべきとは限りません。本書の完成版は、材料が不足したら調理を始めず、必要な不足量を知らせます。代替食材を自動提案したり、無断で人数を減らしたりはしません。

4.2　加熱不足

現実には、加熱器具を動かしたことと、食材が必要な状態になったことは同じではありません。時間だけ、見た目だけなど、一つの情報では十分でない場合もあります。何を測り、誰が確認するかが業務の問題になります。

工程モデルでは、この複雑さを切り離して「仮想加熱を6ステップ終える」と定めます。5ステップの段階で盛り付けようとしたら、順序違反として止めます。これは現実の安全基準を簡略化した値ではなく、条件判断と繰り返しを学ぶために作った規則です。この説明を省くと、数字に根拠があるかのような誤解を招きます。

4.3　調理器具の故障

コンロの故障は、材料不足とは違う場所で発生します。材料はすでに取り分け、下ごしらえも済んでいるかもしれません。そのとき「失敗したからすべて元どおり」と扱えるでしょうか。切った材料を未処理の在庫に戻すことは、現実には慎重な判断を要します。

本書では、材料確保後の故障は未完成として終了し、確保分は元の在庫へ戻さない方針にします。プログラム上の数値を戻すことは簡単でも、現実に戻せるかは別問題だからです。どの時点まで巻き戻せるかは、業務に依存します。

4.4　正常時と異常時

「正常系」は、想定した条件が満たされ、予定した結果まで進む経路です。「異常系」は、入力の誤り、不足、機器故障などに対応する経路です。異常系も、設計されていればシステムの正常な振る舞いの一部です。足りないと正しく判断して止まることは、不具合ではありません。

ここでは「不正な入力」と「正しい入力を与えた結果の不成立」も分けます。人数に文字列「たくさん」を渡すのは入力形式の問題です。整数2を渡し、肉が足りないと判明するのは業務上の不成立です。後半では、前者を入力エラー、後者を未完成の結果として整理します。

4.5　曖昧なレシピが失敗を招く

「不足したら適当に調整する」と書かれていると、実装者は判断を迫られます。肉を減らすのか、全材料を同じ比率で減らすのか、味付けを変えるのか。どれも一見もっともらしくても、依頼者の期待とは違うかもしれません。

曖昧さを見つけたら、正常な例を一つ、境界の例を一つ、異常な例を一つ並べて議論します。肉200 g必要で在庫が201 g、200 g、199 gならどうするか。三つ並べるだけで、「必要量と等しければ開始可能」という条件が明確になります。

第6章　材料に名前を付ける――変数とデータ型

6.1　変数とは何か

材料の量が毎回違うのに、表示のたびに数字を直接書き直すのは面倒です。そこで、値に名前を付けます。meat_g = 200は、整数200をmeat_gという名前で扱えるようにする記述です。このような名前を「変数」と呼び、名前に値を対応付ける操作を「代入」と呼びます。

変数を箱と考えると導入には便利ですが、Pythonでは「名前からオブジェクトを参照する」と考える方が正確です。オブジェクトは、コンピュータ内でデータを表すものです。名前自体に食材や数値が物理的に詰まるわけではありません。第13章で、二つの名前が同じリストを指す場合を扱います［S3］。

Python 3
servings = 2
meat_per_person_g = 100
meat_g = servings * meat_per_person_g
print(meat_g)
print("必要な肉:", meat_g, "g")

実行結果

200
必要な肉: 200 g

1行目は人数、2行目は1人分の肉の量を記録します。3行目の*は掛け算です。右側を計算してから、その結果を左の名前に代入します。最後のprint()は、カンマで区切って複数の値を渡しており、通常は値の間に空白が入ります。

6.2　数値・文字列・真偽値

データの種類を「型」と呼びます。整数のint、小数を表すfloat、文字列のstr、真偽値のboolをまず覚えます。真偽値はTrueとFalseの二つで、条件を満たすかどうかの情報に使います。先頭が大文字である点に注意してください。

ingredient_name = "玉ねぎ"
prepared = False
print(type(potatoes_count).__name__)
print(type(water_l).__name__)
print(type(ingredient_name).__name__)
print(type(prepared).__name__)

実行結果

int
float
str
bool

type(値)は型を調べます。後ろの.__name__は、その型の名前を取り出しています。ここでは型名を確認するためだけに使います。詳しい属性の仕組みは付録Fに譲り、今は同じように見える値でも種類が違うことを確認してください。

200は整数ですが、"200"は文字列です。文字列の連結と数値の加算は別の処理です。"2" + "3"は"23"になります。画面からの入力は第18章で文字列として受け取り、必要に応じてint()で整数に変換します。

6.3　重量と個数

型が同じ整数でも、200 gと200個は違います。Pythonのintだけでは単位を区別できません。本書ではmeat_g、water_ml、potatoes_countのように名前に単位を含めます。単位を名前に書くのは、自動的な検査ではなく、人が読み間違えにくくする工夫です。

小数の計算は便利ですが、floatでは多くの十進小数を厳密に表せません。0.1のような値にも丸めが生じます。本書の最終モデルは、量を整数g・mLで表し、人数も整数にすることで、教材の計算を単純にしています。現実に小数の量が必要なら、丸め方や最小単位を仕様で決めます［S16］。

6.4　変数への再代入

print(meat_g)
print(reserved_g)

実行結果

=は数学の「左右が等しい」という主張ではなく代入です。値が等しいかを調べるには、第10章で使う==を用います。「右側を先に評価し、その結果に左の名前を結び付ける」と読むと、meat_g = meat_g - 50の意味が明確になります。

6.5　分かりやすい命名

xよりもmeat_g、nよりもservingsの方が、業務上の意味が伝わります。英語では単語を小文字にし、単語間をアンダースコアで区切るsnake_caseという慣習がよく使われます。returnなどPythonで役割が決まっている語は変数名にできません。

日本語の名前も使用できます。肉_g = 200は文法上有効です。ただし利用する人の言語、入力のしやすさ、他のコードとの統一を考えます。自分だけの短い教材では日本語が役立ち、複数人の開発では英語に統一することが多い、という使い分けです［S2］。

6.6　現実の材料とデータの違い

在庫の数値を50減らしても、冷蔵庫から肉が消えるわけではありません。プログラムは現実の記録を変えているだけです。現物と記録を一致させる手順がなければ、どちらを見ても正しい在庫が分からなくなります。

これは比喩の限界であると同時に、業務システムの重要な問題です。現物を動かす時点と、記録を更新する時点を決めましょう。本書では実物を扱わないので、記録内部の整合性に集中します。現実に導入するなら、計量や入力の責任を追加で考える必要があります。

よくある間違いは、数字が同じなら同じ意味だと思うこと、変数名を変えれば値も変わると思うこと、再代入とオブジェクトの変更を同じにすることです。後者は第13章で改めて実験します。

第7章　下ごしらえという関数を作る

7.1　名前の付いた仕事

毎回「肉を切ると表示する」「野菜を切ると表示する」を書く代わりに、二つをまとめて「下ごしらえ」と呼びたい。そこで関数を定義します。関数は、名前を通じて呼び出せる処理のまとまりです。Pythonではdefという語を使います。

まだ材料データは渡さず、結果も受け取りません。まず、仕事に名前を付け、必要な場所で実行するという構造を確かめます。第8章で入力を、第9章で戻り値を追加します。現時点の関数は、手順を表示する小さな案内係です。

7.2　def

Python 3
def 下ごしらえ():
    print("肉を切る")
    print("野菜を切る")

print("調理開始")
下ごしらえ()
print("次の工程へ")

実行結果

調理開始
肉を切る
野菜を切る
次の工程へ

1行目は関数の定義です。defのあとに名前、丸括弧、コロン:が続きます。続く二つのprint()は行頭を空けて書きます。この字下げを「インデント」と呼びます。Pythonではインデントが処理のまとまりを表します。慣習として半角空白4個を使い、タブと混ぜないようにします。

関数本体とは、インデントされた処理の部分です。関数を定義した時点では、この二つの表示は実行されません。定義を実行すると関数が作られ、名前で呼べるようになります。実際の本体が動くのは、後ろの下ごしらえ()に到達したときです。

7.3　関数の呼び出し

名前のあとに丸括弧を付けると、関数を「呼び出す」ことになります。下ごしらえと名前だけ書くことと、下ごしらえ()は違います。前者は関数そのものを参照し、後者は実行を依頼します。

最初に「調理開始」が表示され、呼び出しで関数本体へ進み、二つの行を処理したあと、呼び出した位置の続きへ戻ります。この戻る動きを「復帰」と呼びます。何も特別な命令を書かなくても、通常は本体の末尾から戻ります。値を返す仕組みは第9章で扱います。

7.4　関数から関数を呼ぶ

Python 3
def 肉を切る():
    print("肉を切る")

def 野菜を切る():
    print("野菜を切る")

def 下ごしらえ():
    肉を切る()
    野菜を切る()

def カレーを作る():
    print("開始")
    下ごしらえ()
    print("加熱の準備へ")

カレーを作る()

実行結果

開始
肉を切る
野菜を切る
加熱の準備へ

四つのdefはそれぞれ仕事を定義しています。最後の1行が実行の入口です。カレーを作る()が下ごしらえ()を呼び、その中で肉を切る()が動きます。肉を切る関数が終わると、いきなり一番外へ戻るのではなく、直近の呼び出し元である下ごしらえの続きへ戻ります。そこから野菜を切ります。

呼び出し元は「どこから再開するか」を保持しています。入れ子の呼び出しでは、後から呼び出された仕事が先に戻ります。この仕組みを積み重ねた呼び出し情報は、一般に「コールスタック」と呼ばれます。まずは、栞を挟んで別の説明を読み、読み終えたら栞へ戻るイメージを持つとよいでしょう。

7.5　関数の階層構造

この例は木の形に描けます。しかし、すべてのプログラムの呼び出し関係が木になるわけではありません。下ごしらえと盛り付けの両方が「数量を確認する」を呼べば、その関数には複数の呼び出し元があります。自分を呼ぶ再帰があれば、関係図には循環も現れます。

関数の種類を一つの点として描いた関係図を「呼び出しグラフ」と呼びます。一回の実行で起きた個々の呼び出しを別々の点に展開した図は、通常の同期的な呼び出しでは木として表せます。同じ関数が二度呼ばれても、実行上は別の呼び出しです。この二つの図を区別すると、後で再帰を学ぶときにも混乱が減ります。

7.6　抽象化の第一歩

カレーを作る()を読むとき、毎回包丁の細かな動きまで考えたくはありません。「下ごしらえを済ませる」という目的を把握できれば、全体の流れを読めます。細部をまとめ、必要な特徴に注目して扱うことを「抽象化」と呼びます。

ただし、名前が実態と一致していなければ抽象化は役立ちません。今回の下ごしらえ()は表示だけです。本物の処理をしたと誤解される場面では、下ごしらえを案内する()のような名前の方が適切です。本書では段階的な学習のための仮モデルであることを明記して使っています。

よくある間違いは、定義しただけで実行されたと思うこと、インデントを外してしまうこと、呼び出す前に必要な定義が実行されていないことです。関数本体内の別関数名は、その行を実行するときに解決されます。そのため、使う関数の定義を上にまとめ、最後に入口の呼び出しを書くと、初学者には追いやすくなります。

第8章　肉と野菜を渡す――引数

8.1　関数への材料投入

前章の下ごしらえは、毎回同じ手順を表示しました。ところが今日の材料は豚肉と玉ねぎ、明日は鶏肉とにんじんかもしれません。材料を変えるたびに関数本体を書き直すより、使う材料を呼び出し側から渡したいところです。そのための値が「引数」です。

関数を加工装置に見立てると、引数は装置へ渡す材料や設定値に当たります。ただしPythonが受け取るのは本物の肉ではなく、文字列や数値などのオブジェクトです。「材料のデータを渡す」と読むことを忘れないでください。

8.2　下ごしらえ(肉, 野菜)

Python 3
def 下ごしらえ(肉, 野菜):
    print("肉:", 肉)
    print("野菜:", 野菜)

下ごしらえ("豚肉", "玉ねぎ")
下ごしらえ("鶏肉", "にんじん")

実行結果

肉: 豚肉
野菜: 玉ねぎ
肉: 鶏肉
野菜: にんじん

定義側の肉と野菜は、呼び出し時に渡される値を受け取る名前です。厳密には「仮引数」または「パラメーター」と呼びます。呼び出し側の"豚肉"と"玉ねぎ"は、実際に渡す値で、「実引数」と呼びます。日常的には両方を引数と呼ぶこともありますが、本書では必要な場面で区別します。

一度目の呼び出しでは、関数内の肉が"豚肉"を参照します。二度目の呼び出しでは、別の呼び出しに対するローカルな名前として"鶏肉"を参照します。「ローカル」は、その関数呼び出しの内側で使うという意味です。後の呼び出しが、前の呼び出しの名前を使い回しているわけではありません。

8.3　引数の数と順序

位置で渡す場合、最初の値は最初の仮引数に、次の値は次の仮引数に対応します。下ごしらえ("玉ねぎ", "豚肉")は文法上実行できても、仕事の意味が逆になります。Pythonは肉という名前を見て、本当に肉かどうかを判断するわけではありません。

Python 3
def 必要な肉_g(人数, 一人分_g):
    print(人数 * 一人分_g)

必要な肉_g(2, 100)
必要な肉_g(人数=3, 一人分_g=100)

実行結果

200
300

1回目は位置による対応、2回目は名前による対応です。引数の意味が紛らわしい場合には、呼び出しにも名前を書くと読みやすくなります。この関数はまだ結果を表示するだけですが、第9章で結果を返す形に直します。

8.4　デフォルト引数

Python 3
def 切り方を案内する(材料, 大きさ_mm=20):
    print(材料, 大きさ_mm, "mmに切る想定")

切り方を案内する("玉ねぎ")
切り方を案内する("にんじん", 10)

実行結果

玉ねぎ 20 mmに切る想定
にんじん 10 mmに切る想定

大きさ_mm=20は、呼び出し時に値が省略された場合の既定値です。これを「デフォルト引数」と呼びます。一度目では20、二度目では指定した10が使われます。この数値はデータの受け渡し例であり、実際の食材の適切な切り方を一律に指定するものではありません。

省略可能な引数は、通常の位置引数では必須の引数の後ろに置きます。また、デフォルト値は関数を定義するときに評価されます。呼び出すたびに新しく評価されるわけではありません。整数の20では目立った問題になりませんが、リストを既定値にして中身を変更すると、呼び出し間で共有が起こります。第13章で実験します［S2］。

8.5　キーワード引数

名前を付けて渡す方法を「キーワード引数」と呼びます。切り方を案内する(大きさ_mm=10, 材料="にんじん")のように、名前が明確なら順序を変えて書けます。通常の呼び出しでは、位置引数を先に、キーワード引数を後に置きます。同じ仮引数に二重に値を与えることはできません。

関数の引数を増やすときにも、この仕組みが役立ちます。ただし、デフォルトを設ければ確認が不要になるわけではありません。人によって期待する既定値が違う仕事では、省略を許さず毎回明示した方がよい場合もあります。「よく使うから省略可」と「間違えても影響が小さいから省略可」は別の判断です。

8.6　引数の不足と誤り

必要な引数が足りない、存在しないキーワードを指定する、同じ引数を二重に渡す、といった呼び出しはTypeErrorになります。引数の個数が正しくても、内容が業務条件を満たすとは限りません。人数に-2を渡したら、掛け算自体はできるため、別の検査が必要です。

Pythonの引数の受け渡しでは、仮引数の名前が渡されたオブジェクトを参照します。自動的に深いコピーが作られるわけでも、呼び出し元の変数名自体が関数へ渡されるわけでもありません。関数内で仮引数を別の値に再代入しても、呼び出し元の名前は付け替わりません。一方、渡されたリストなどの中身を変えると、共有する呼び出し元からも変更が見えます［S2・S3］。

Python 3

    材料 = "カット済み玉ねぎ"
    print("関数内:", 材料)

名前を付け直す(元の材料)

実行結果

呼び出し元: 玉ねぎ

関数内の材料を付け替えただけなので、元の材料は"玉ねぎ"のままです。現実の玉ねぎを切る比喩をそのまま当てはめると、「渡した玉ねぎが切られて戻ってくるはず」と誤解しがちです。このコードには、その結果を返す処理がありません。次章で戻り値を使って明示的に受け取ります。

第9章　カット済み具材を受け取る――戻り値

9.1　return

また、正常に値を返す前に例外が起きたり、終わらない処理になったりすることもあります。「関数」という名前だけで、入力から必ず一つの成果物が安全に返ると考えてはいけません。入力条件と失敗時の振る舞いを合わせて読む必要があります。

第10章　火が通るまで加熱する――条件分岐

10.1　条件による判断

下ごしらえの次には加熱、と順番を覚えても、コンロが壊れていれば進めません。仕事には、状態を見て次の動きを変える場面があります。条件に応じて処理を分けることを「条件分岐」と呼びます。

この章では、実際の温度を判定せず、仮想加熱の進み具合を数値で扱います。必要なステップに達していれば次へ進み、足りなければ続けると判断します。ただし、ifそのものが繰り返しを起こすわけではありません。一回の判断を、次章の繰り返しで何度も行うことで「完了するまで続ける」になります。

ifの後ろに条件を書き、コロンで区切ります。条件が真なら、直後のインデントされた部分を実行します。偽ならelse側へ進みます。>=は「以上」です。今回4は6以上ではないので、後者が表示されます。

「続ける必要があります」と表示しても、加熱ステップ数は変わりません。状態を変える処理をまだ書いていないからです。第5章で学んだ、表示と実際の処理の区別がここでも重要になります。

第11章　ジャガイモを全部切る――繰り返し

11.1　同じ作業の反復

じゃがいもが1個なら、一回処理すれば済みます。10個なら、同じ作業を10回行います。回数の分だけ同じコードをコピーすると、個数が変わるたびに修正が必要です。そこで「対象を順番に取り出して同じ処理をする」と表現します。

繰り返しには、並んだ対象を扱う形と、ある条件の間続ける形があります。Pythonでは、主にforとwhileで表します。対象の集合が決まっている仕事にはfor、次の判断まで回数が決まらない仕事にはwhileが自然なことが多いですが、常に一対一で決まるわけではありません［S2］。

11.2　for

Python 3
for number in range(1, 4):
    print("じゃがいも", number, "を切る")
print("全個処理しました")

実行結果

じゃがいも 1 を切る
じゃがいも 2 を切る
じゃがいも 3 を切る
全個処理しました

range(1, 4)は1、2、3を順に扱えるものを作ります。終わりの4は含みません。forはその各値をnumberへ順番に代入し、インデントされた本体を実行します。対象が尽きると外側の処理へ進みます。最後の表示が繰り返しの外にあるのは、字下げがないからです。

range(3)なら0、1、2です。コンピュータでは0から数える場面が多いため、この規則に慣れておくと、第12章のリストの位置指定も理解しやすくなります。rangeは巨大な数のリストを最初に全部作る仕組みではありません。

11.3　while

Python 3

heat_target = 3

    heat_done = heat_done + 1
    print("仮想加熱", heat_done)

print("規定ステップに到達")

実行結果

仮想加熱 1
仮想加熱 2
仮想加熱 3
規定ステップに到達

whileは、本体を実行する前に条件を調べます。真なら一周分を実行し、また条件へ戻ります。最初から偽なら、本体は一度も実行されません。ここでは0から始め、一周ごとに1増やすので、3回で条件が偽になります。

仮想加熱の単位は分でも秒でもありません。待ち時間も入れていません。数を増やして状態の進行をモデル化しています。現実の料理で同じ回数だけ何かをすればよい、という意味にはなりません。

11.4　breakとcontinue

Python 3
for number in range(1, 5):
    if number == 2:
        continue
    if number == 4:
        break
    print("処理対象", number)
print("繰り返しの外")

実行結果

処理対象 1
処理対象 3
繰り返しの外

continueは今回の残りの処理を飛ばして次の反復へ進みます。breakは最も内側の繰り返しを終了します。例では2を飛ばし、4に来たところで終了するので、1と3が表示されます。「異常な食材は除外」「器具が故障したら中断」といった構造の説明に使えますが、現実の不適切な食材をどう扱うかは別途判断が必要です。

breakとreturnも違います。breakはループを抜けた後の同じ関数の処理へ進みます。returnはその関数全体から戻ります。入れ子のループでbreakしても、外側のループまで一度に終了するわけではありません。

11.5　無限ループ

条件がいつまでも真のままだと、ループが終わりません。例11-02からheat_doneを増やす行を消すと、0のままなので終了条件へ近付きません。これが「無限ループ」の典型です。

whileを書くときは、条件を変えるものが何かを説明してください。計数値なら更新箇所、外部機器の応答なら待つ時間の上限や中断条件が必要になります。毎回更新するつもりでも、その前にcontinueしてしまうと更新されない経路が生まれます。

無限ループは常に悪いわけではなく、入力を待ち続けるサービスなどで意図的に使う場合もあります。ただし、停止条件、待機方法、資源の使い方を設計する必要があります。本書のループは、有限回で終了する条件を明示します。

11.6　繰り返しと関数の組み合わせ

Python 3

実行結果

カット済みじゃがいも2
カット済みじゃがいも3

str()は値を文字列へ変換します。整数の番号を文字列へ変えてから連結しています。関数が一個分の仕事を担当し、ループが対象を次々に渡しています。関数を使うことと、繰り返しを使うことは競合しません。仕事の種類と、その実行回数を別々に表しています。

よくある間違いは、最後の結果だけを変数に残し、全部保存したつもりになることです。この例のresultは毎回付け替えられるので、ループ後には最後の文字列だけが残ります。すべての結果を保存するには、次章のリストが使えます。

append()は末尾へ追加するメソッドです。メソッドとは、そのオブジェクトに結び付いた操作で、対象.操作名()という形で呼びます。ここではリスト自身が変化します。戻り値で新しいリストを受け取る操作ではありません。shopping = shopping.append(...)と書くと、Noneを代入してしまいます［S5］。

12.2　辞書

在庫は「何番目の品物か」より、「玉ねぎがいくつあるか」を尋ねたい情報です。名前などの「キー」と、それに対応する「値」を組にして扱う「辞書」が向いています。波括弧{}の中にキー: 値を並べます。

Python 3
stock = {"肉_g": 300, "玉ねぎ_g": 200}
print(stock["肉_g"])
print(stock.get("ルー_g", 0))
print("肉_g" in stock)

実行結果

300
0
True

stock["肉_g"]はキーから値を取り出します。キーが存在しない場合はKeyErrorです。get("ルー_g", 0)は、存在しなければ0を返します。inは、そのキーがあるかを調べます。辞書に対するinは、原則として値ではなくキーを探します。

同じキーは一つの辞書の中で一つの値に対応します。同じ材料を仕入先や期限ごとに分けたいなら、「肉_g」だけでは識別が足りません。本書では材料名ごとに合計量を持つ単純な在庫とし、仕入れ単位や消費期限は管理しません。

12.3　追加と削除

Python 3

stock["ルー_g"] = 100

print(stock)

存在しないキーへの代入は追加、存在するキーへの代入は値の置き換えです。delは指定した項目を削除します。材料を0にすることと、キーを削除することは違います。前者は「この材料を管理しているが数量0」、後者は「このキーの登録がない」という状態です。本書の不足計算では、未登録も0とみなすと明示的に決めます。

リストのremove(値)は、最初に見つかった一致要素を取り除きます。存在しないとValueErrorです。リストと辞書はどちらも変更可能ですが、探し方や操作の意味が違います。データの並び順が必要か、キーによる対応が必要かで選びます。

12.6　在庫管理プログラム

def subtract_stock(stock, needed):
    for name, amount in needed.items():
        if stock.get(name, 0) < amount:
            return None
    remaining = stock.copy()
    for name, amount in needed.items():
        remaining[name] = remaining[name] - amount
    return remaining

stock = {"肉_g": 300, "ルー_g": 100}
remaining = subtract_stock(stock, {"肉_g": 200, "ルー_g": 50})
print(remaining)
print(stock)

実行結果

{'肉_g': 300, 'ルー_g': 100}

最初のループでは不足だけを調べます。すべて足りていることを確認してから、新しい辞書へ差し引きを行います。copy()は浅いコピーを作ります。今回の値は整数なので、このコピーのキーへ新しい整数を代入しても元の辞書は変わりません。入れ子のリストなどがある場合は、同じ結論にはならないため第13章で確認します。

現実の在庫管理では、二人が同時に同じ在庫を確保する問題があります。このプログラムは単一の処理から順番に利用する前提で、同時実行は扱いません。「確認してから差し引く」だけで、多人数が使う在庫システムの安全性まで保証できるわけではありません。

第Ⅳ部　カレーづくりからソフトウェア設計を学ぶ

第13章　カレーを作ったら鍋が汚れた――副作用

13.1　戻り値とは別に変化するもの

カレーを一皿受け取ったあと、台所を見ると鍋が汚れ、ガスが使われ、材料が減っています。成果物だけでは、仕事全体で起きたことを説明できません。プログラムでも、関数が値を返す以外に、外から観察できる状態を変えることがあります。これを「副作用」と呼びます。

「副」という字から、不要なもの、悪いものを想像するかもしれません。しかし、画面表示、ファイル保存、メール送信、在庫の更新は、仕事の主目的そのものになる場合があります。副作用という語は、重要度ではなく、戻り値と外部状態を区別するための用語です［S7］。

13.2　鍋・ガス・材料在庫

図の右へ出るのは成果物、下へ伸びるのは周囲に残る変化です。どちらも大切ですが、行き先が違います。プログラムの関数が、結果の数値を返すと同時に画面へ表示するなら、戻り値と表示という副作用を持ちます。呼び出し元の辞書を書き換えるなら、その変更も副作用です。

現実の料理は物質の状態変化を伴うため、元の材料をまったく変えずに料理を作ることはできません。一方、コンピュータ上では、新しい在庫表や工程表を返し、元の表を残す設計ができます。「純粋な料理」を実現するのではなく、「料理の記録を扱う計算」を分離しているのです。

13.3　外部状態の変更

Python 3
def use_meat(stock, amount_g):
    stock["肉_g"] = stock["肉_g"] - amount_g
    return "材料を確保しました"

fridge = {"肉_g": 300}
message = use_meat(fridge, 100)
print(message)
print(fridge)

実行結果

材料を確保しました
{'肉_g': 200}

関数は文字列を返すだけでなく、渡された辞書の中身を変えています。stockとfridgeが同じ辞書を参照しているので、変更は呼び出し元からも見えます。仮引数というローカルな名前を使っていても、その先のオブジェクトまでローカルとは限りません。

Python 3
def replace_name(stock):
    stock = {"肉_g": 0}
    return stock

fridge = {"肉_g": 300}

print(fridge)
print(other)

実行結果

{'肉_g': 0}

こちらはローカルな名前stockを新しい辞書に対応付け直しています。元の辞書は変更されません。「辞書の中身を変える」と「辞書を指す名前を付け替える」は違う操作です。この違いを、第8章の引数の受け渡しと合わせて理解してください。

13.4　ローカル変数とグローバル変数

関数内の名前は通常、その関数呼び出しのローカル変数です。ファイルの一番外側で定義した名前は、そのモジュールのグローバル変数です。「モジュール」は、ここでは一つのPythonファイルと考えて構いません。グローバルは、あらゆるファイルで自動共有されるという意味ではありません［S4］。

Python 3
meat_g = 300

def local_change():
    meat_g = 100
    print("内側:", meat_g)

def global_change():
    global meat_g
    meat_g = meat_g - 50

local_change()
print("外側:", meat_g)
global_change()
print("変更後:", meat_g)

実行結果

内側: 100
外側: 300
変更後: 250

最初の関数は、同じ綴りのローカル変数を作ります。二つ目の関数はglobal宣言により、外側の名前へ再代入します。これで動作の違いを確かめられますが、完成版では在庫をグローバル変数として更新する設計を採用しません。入力と戻り値で見えるようにします。

関数内で代入する名前は、原則としてその関数のローカルと判断されます。globalなしでmeat_g = meat_g - 50と書くと、右側もローカルなmeat_gを読みようとし、まだ値がないためUnboundLocalErrorになります。外側の値を読みつつ同名のローカルを作る、と都合よく解釈されるわけではありません。

名前を探す順序は、基本的にローカル、外側の関数、モジュール、組み込みです。詳細な名前解決は発展事項ですが、関数が何を入力として使っているかを考えるとき、引数以外の名前を読んでいないか確認する習慣が役立ちます。

13.5　副作用による不具合

Python 3
def add_ingredient(name, basket=[]):
    basket.append(name)
    return basket

print(add_ingredient("玉ねぎ"))

実行結果

['肉']
['肉', '玉ねぎ']

二度目の結果にも肉が入っています。デフォルトの空リストは定義時に一つだけ作られ、呼び出しのたびに使われるからです。関数内のappend()がその共有リストを変更しています。毎回新しい買い物かごを作る意図なら、次の形にします。

Python 3

        basket = []
    basket.append(name)
    return basket

print(add_ingredient("肉"))
print(add_ingredient("玉ねぎ"))

実行結果

['肉']
['玉ねぎ']

省略時には独立したリストになります。ただし、呼び出し側から既存のリストを渡した場合には、そのリストを変更します。Noneを使っただけで、すべての副作用がなくなるわけではありません。仕様が「入力を変更しない」なら、渡された場合もコピーするなどの対応が必要です。

浅いコピーにも注意しましょう。

Python 3

{'材料': ['肉', '玉ねぎ', 'にんじん']}

True

外側の辞書は別ですが、内側のリストは共有されています。copy()は内部のすべてを再帰的に複製する操作ではありません。標準ライブラリのcopy.deepcopy()で深いコピーを作れる場合もありますが、大きなデータを何でも複製すればよいわけではありません。どの部分を共有してよく、どの部分を独立させるかを考えます［S15］。

13.6　副作用の分離

    return new_stock

stock = {"肉_g": 300}

実行結果

後: {'肉_g': 200}

計算する関数は元の在庫を変えず、新しい値を返します。外側の処理が最後にその結果を採用します。「どうなるか計算する」と「その状態を正式なものにする」を分けています。完成版もこの方針で、残り在庫を戻り値に含めます。

ただし、ファイルやデータベースへ保存しなければ、プログラム終了時に在庫は失われます。教育用の完成版はメモリー内に保持するだけです。永続的な保存は拡張課題であり、実装済みの機能ではありません。実用化の際は保存失敗や同時更新も扱う必要があります。

13.7　純粋関数

この本では、同じ入力なら同じ結果になり、呼び出し元から観察できる副作用を起こさない関数を、純粋関数として扱います。必要量計算はその代表です。現在時刻、乱数、変化するグローバル在庫などを暗黙に読むと、同じ引数でも結果が変わる可能性があるため、この意味で純粋とは呼べません。

関数内で新しく作ったリストにappend()するだけなら、そのリストが外部と共有されていない限り、呼び出し元の状態は変わりません。ローカルな再代入や内部での一時的な変更があるから、必ず非純粋になるという判定はしません。本書では外から観察できる動作を中心に考えます。

手続き型プログラミングは、仕事を手順として実行し、状態を変化させて進める書き方です。関数型プログラミングは、値から値への変換と関数の組み合わせを重視する書き方です。defを使っただけで関数型になるわけではありません。Pythonでは、計算部分を純粋な形にし、外側で入力や表示を行うように、両方の考え方を組み合わせられます［S7］。

第14章　包丁を交換してもレシピは変わらない――抽象化

14.1　目的と実現方法

下ごしらえの目的は、次の工程が受け取れる具材を用意することです。道具として包丁を使うか、別の加工器具を使うかは実現方法です。目的と方法を分けると、仕事全体を書き直さずに、ある工程だけを改良できる可能性が生まれます。

ただし、包丁とフードプロセッサーは、常に同じ結果を作るわけではありません。大きさ、形、食感が違えば、加熱や完成品にも影響します。交換可能だと言うためには、次工程が必要とする条件を、どちらも満たす必要があります。比喩の便利さに引きずられず、受け渡しの約束を確認しましょう。

14.2　包丁とフードプロセッサー

ここでは物理的な加工を再現せず、どちらの道具も同じ「カット済み」というラベルを返すモデルにします。どの道具が適切かという料理上の判断は、モデルの外に置きます。

Python 3
def cut_with_knife(name):
    return "カット済み:" + name

def cut_with_processor(name):
    return "カット済み:" + name

def prepare_names(names, cutter):
    results = []
    for name in names:
        results.append(cutter(name))
    return results

names = ["玉ねぎ", "にんじん"]
print(prepare_names(names, cut_with_knife))
print(prepare_names(names, cut_with_processor))

実行結果

['カット済み:玉ねぎ', 'カット済み:にんじん']
['カット済み:玉ねぎ', 'カット済み:にんじん']

二つの関数は、この教材では同じ出力を返します。prepare_namesの第2引数へ関数そのものを渡し、内部でcutter(name)として呼び出しています。Pythonでは関数も値として扱えます。渡すときにcut_with_knife()と括弧を付けると、その場で実行して結果を渡すことになり、意図と違います。

14.3　入出力の約束

約束 この例の内容
入力 材料名の文字列一つ
出力 カット済み:を付けた文字列一つ
入力への変更 しない
表示 しない
使用側の期待 戻り値をリストへ追加できる

このような外から利用するための約束を「インターフェース」と呼びます。画面のボタンを意味する場合もありますが、ここでは関数の使い方の約束です。引数の数だけ合っていても十分ではありません。片方が文字列、もう片方がNoneを返すなら、同じようには使えません。

14.4　実装の隠蔽

「実装」は、約束を実現する具体的なコードです。「隠蔽」は、利用者がその細部へ依存しなくて済むようにすることです。秘密にすることとは限りません。ソースコードが読めても、通常の利用では内部の一時変数の名前を知らなくてよい、という関係を作ります。

たとえば、必要量を計算する関数の内部をループから別の計算法に変えても、同じ入力に対して同じ必要量が返るなら、呼び出し元は変えずに済みます。しかし「人数の上限を20から10にする」は外から見える契約の変更なので、単なる内部改良ではありません。

14.5　関数の独立性

関数がどれだけ独立しているかは、引数と戻り値以外に何へ依存しているかで変わります。外側の在庫変数、特定の表示先、固定されたレシピ名などを暗黙に読むほど、別の場面で使いにくくなります。

すべてを引数にすると、今度は引数が多すぎて使いにくくなることもあります。関係の強い値を一つの辞書へまとめる、業務上のまとまりで関数を分けるなど、利用のしやすさと明示性の両方を考えます。独立性は、引数が少ないことや、関数が短いことだけで測れません。

14.6　変更に強い設計

第15章　コンロが壊れたらどうするか――例外処理

15.1　想定外の事態

必要な材料があり、下ごしらえも終わりました。しかし加熱を始めようとするとコンロが動きません。このまま盛り付けへ進めば、仕事の約束を破ります。現在の処理では続けられないことを、呼び出し元へ伝える仕組みが必要です。

Pythonの「例外」は、通常の処理の流れを中断し、問題を知らせる仕組みです。「想定外」という言葉で紹介されることがありますが、予測している異常を例外として表すこともできます。たとえば人数が範囲外、操作の順序が違う、といった明確な条件にも使います。例外が起きたこと自体と、プログラムに欠陥があることは同じではありません［S6］。

15.2　tryとexcept

Python 3
def heat_once(stove_ok):
    if not stove_ok:
        raise RuntimeError("コンロが動きません")
    return "仮想加熱を1ステップ実行"

try:
    result = heat_once(False)
    print(result)
except RuntimeError as exc:
    print("中断:", exc)
print("状況を確認してください")

実行結果

中断: コンロが動きません
状況を確認してください

raiseは例外を発生させる文です。RuntimeError("...")は種類と説明を持つ例外を作っています。raiseへ到達した場合、通常のreturnには進みません。呼び出し先で処理されなかった例外は、呼び出し元へ伝わります。

tryの中は、例外が発生し得る処理です。対応する種類の例外が起きると、exceptの処理へ移ります。as excで例外の情報に名前を付け、表示しています。今回はprint(result)は実行されません。例外が起きた行より後のtry内を、自動的に続けるわけではないからです。

例外処理が終われば、try・exceptの外側へ進みます。ただし、自動的に再試行されるわけでも、故障が直るわけでもありません。「中断と表示した」ことを「復旧した」と取り違えないようにします。

15.3　エラーの握りつぶし

except:ですべてを捕まえ、何もしない処理を書くと、失敗が見えなくなります。これを「握りつぶす」と表現します。何も表示されないまま完成扱いになると、仕事としては特に危険です。

捕まえるのは、その場所で対応できる例外に絞ります。入力を数値へ変換するならValueError、業務の状態が合わないなら本書ではRuntimeError、と種類を見て扱います。意図しないNameErrorやKeyErrorまでまとめて「材料不足」に変えると、本当の実装不具合を隠してしまいます。

except Exceptionも広い範囲を捕まえます。利用者へ最終的な障害を知らせる最外層などで使う理由はありますが、すべての関数へ機械的に書くものではありません。標準的には、予想し、対応を決めた種類を明示します［S6］。

15.4　中断条件

第16章　レシピが正しければカレーは完成するのか――テスト

16.1　動作と正しさの違い

プログラムを実行して、画面に「完成」と出ました。これで安心できるでしょうか。人数を3にしても必要量が2人分のまま、材料不足でも盛り付けに進む、という可能性は残ります。動作したことは、ある経路でエラーが出なかったことを示すだけです。

「テスト」は、具体的な入力や状態を用意し、実際の結果が期待した結果と一致するか確かめることです。期待値はコードを見て決めるのではなく、仕様から決めます。誤ったコードの計算式をそのままテスト側へコピーすると、両方が同じように間違えて合格する場合があります。

16.2　入出力の検証

Python 3
def necessary_meat_g(servings):
    return servings * 100

assert necessary_meat_g(1) == 100
assert necessary_meat_g(3) == 300
print("必要量の確認に合格")

実行結果

必要量の確認に合格

assert 条件は、条件が真なら何もせず、偽ならAssertionErrorを発生させます。期待する性質をコードで書けるので、何度でも同じ確認を実行できます。assertが一度も失敗しなかった場合に最後の表示へ進みます。

assertは、利用者の不正入力を必ず拒否するための機能としては使いません。Pythonを-Oという最適化オプションで実行すると、assertの文が除去されるからです。業務上必須の検査には、第15章のifとraiseを使います。テストの期待値の検証と、本番の入力検査は役割が違います［S12］。

16.3　正常系と異常系

正常系のテストでは、十分な材料から完成へ進むことを確認します。異常系では、材料不足が検出される、故障時に未完成になる、不正な順番が拒否される、といったことを確認します。異常を与えて例外が出た場合も、それが期待どおりならテストは成功です。

出力の値だけでなく、変化しなかったものも確かめます。「入力の辞書を変更しない」という約束があれば、呼び出し前後で比較します。副作用は戻り値だけを見ても分からないからです。さらに、失敗したときだけ入力を書き換える不具合がないかも確認します。

すべての入力を試すのが難しい場合でも、代表的な分類と境界を選ぶことで、重要な誤りを見つけやすくなります。ただし、有限個のテストに合格しても、あらゆる入力に対する完全な正しさが証明されたわけではありません。検証した範囲を説明します。

pytestはテストを見つけて実行し、失敗の情報を読みやすく表示する外部パッケージです。Pythonの標準ライブラリには含まれません。付録Aの仮想環境にインストールしたうえで使用します。次のコードをtest_amount.pyとして保存できます［S8・S9］。

16.6　仕様そのものの誤り

もし「1人分の肉は1000 g」と誤って決めていたら、その仕様に忠実な計算はテストに合格します。テストは、期待値が業務として妥当かまで自動的に保証しません。だから第1章で、仕事の理解から始めました。

確認には二つの視点が要ります。一つは、仕様どおり実装されているか。もう一つは、その仕様が目的に合っているかです。本書の仮想加熱6ステップが正確に数えられても、実際の安全な加熱を表すことにはなりません。モデルの適用範囲を確認することも、広い意味での検証です。

テストが失敗したら、まず仕様、入力、期待値、実際の出力を並べます。すぐに期待値を実際の値へ合わせてはいけません。どちらが間違っているかを判断してから修正し、その後も同じ問題を検出できるようにテストを残します。

レシピ辞書は、nameに名前、per_personに1人分の材料辞書、heat_stepsに仮想加熱目標を持ちます。per_personは辞書の中の辞書です。make_recipe()は呼ぶたびに新しい構造を作るため、片方のレシピを変更しても、後で作った別のレシピには影響しません。

レシピの検査は、名前が空でないか、材料辞書が空でないか、量が正の整数か、といったデータ上の条件を調べます。カレーとして妥当な配合かは判断しません。水を材料から削除した辞書も、形の条件だけなら通る可能性があります。形式の検査と、料理の意味の検査は別です。

17.4　呼び出し関係

run_simulation()は全体の順序を取りまとめます。new_job()で計画を作り、shortages()で不足を調べます。揃っていればreserve()、prepare()、複数回のheat()、最後にplate()へ進みます。各処理は別の処理の内部変数を直接探しに行かず、渡された状態を使います。

stage 意味 次に許される操作
planned 計画を作った 不足確認・材料確保
reserved 材料確保済み 下ごしらえ

heating 仮想加熱の途中 加熱を1ステップ進める

図は基本レシピの6ステップを表しています。加熱目標を1に設定した場合には、最初の加熱でpreparedから直接cookedへ進みます。

このように、取り得る状態と状態間の移動を定めたものを「状態遷移」と呼びます。加熱前の状態でplate()を呼ぶと、状態が飛ばないようにRuntimeErrorを発生させます。単に関数を並べるだけより、誤った利用を検出しやすくなります。

17.5　副作用と例外

内部の関数は、元の入力を変えずに新しい辞書を返します。move()という補助関数が辞書をコピーし、必要量辞書もコピーし、履歴を新しいリストにします。第13章の浅いコピーだけでは、履歴リストを共有して過去の状態まで変えてしまうためです。

heat_doneやstageは整数や文字列なので、付け替えで扱えます。どこを新しく作る必要があるかは、データの構造から判断します。任意の深い入れ子を自動的に複製する仕組みではなく、今回の決められた構造に対応したコードです。

不正な入力は例外として呼び出し元へ知らせます。一方、材料不足やコンロ故障は、okがFalseの結果辞書として返します。これらは利用者が確認したい通常の業務結果でもあるからです。下位のheat()が出す機器故障の例外を、上位のrun_simulation()が捕まえて結果へ変換します。どの層で例外にし、どの層で結果にするかを決めています。

17.6　全体構成

結果辞書には、成功可否ok、最後の工程状態job、残り在庫remaining、失敗理由errorが入ります。成功時のerrorはNoneです。故障時のjobは、最後に成功した工程の状態を保ちます。「失敗」という一語へ上書きして、どこまで終わったかを消す設計にはしていません。

この状態辞書は、本書の関数で作ったものを順に渡すことが前提です。利用者がstageを勝手にdoneへ書き換えたり、必須のキーを削除したりした場合まで防御する仕組みではありません。完全な入力防御や情報の隠蔽が必要になったら、付録Fのクラスなども選択肢になります。

よくある間違いは、純粋な計算を採用したから在庫管理も自動的に完成したと思うことです。新在庫を返すだけなら、呼び出し元が採用しない限り元の在庫が残ります。採用する場所を一つにし、次回へ何を渡すかを確認します。

def positive_int(value, label):
    """boolを除く正のintを要求する。
    型違いはTypeError、範囲外はValueError。
    """
    if type(value) is not int:
        raise TypeError(f"{label}は整数で指定してください")
    if value <= 0:
        raise ValueError(f"{label}は1以上にしてください")


def make_recipe(kind="standard"):

def validate_recipe(recipe):
    if not isinstance(recipe, dict):
        raise TypeError("レシピは辞書で指定してください")
    name = recipe.get("name")
    if not isinstance(name, str) or not name.strip():
        raise ValueError("レシピ名が必要です")
    amounts = recipe.get("per_person")
    if not isinstance(amounts, dict) or not amounts:
        raise ValueError("1人分の材料辞書が必要です")
    for name, amount in amounts.items():
        if not isinstance(name, str) or not name.strip():
            raise ValueError("材料名は空でない文字列にしてください")
        positive_int(amount, name)
    positive_int(recipe.get("heat_steps"), "加熱ステップ数")


def requirements(recipe, servings):
    """必要量の辞書を返す。servingsは1〜20人。入力を変更しない。"""
    validate_recipe(recipe)
    positive_int(servings, "人数")
    if servings > 20:
        raise ValueError("人数は20以下にしてください")
    needed = {}
    for name, amount in recipe["per_person"].items():
        needed[name] = amount * servings
    return needed


def validate_stock(stock):
    if not isinstance(stock, dict):
        raise TypeError("在庫は辞書で指定してください")
    for name, amount in stock.items():
        if not isinstance(name, str) or not name.strip():
            raise ValueError("在庫の材料名が不正です")
        if type(amount) is not int:
            raise TypeError(f"{name}の在庫は整数にしてください")
        if amount < 0:
            raise ValueError(f"{name}の在庫は0以上にしてください")


def shortages(stock, needed):
    """不足量だけを返す。未登録の材料は在庫0とみなす。"""
    validate_stock(stock)
    missing = {}
    for name, amount in needed.items():
        positive_int(amount, name)
        gap = amount - stock.get(name, 0)
        if gap > 0:
            missing[name] = gap
    return missing


def reserve(stock, needed):
    """全材料が揃うときだけ差し引いた新在庫を返す。
    不足時はValueError。
    """
    missing = shortages(stock, needed)
    if missing:
        raise ValueError(f"材料不足: {missing}")
    remaining = stock.copy()
    for name, amount in needed.items():
        remaining[name] -= amount
    return remaining


def new_job(recipe, servings):
    """計画状態を作る。
    レシピから必要な値だけを取り込み、共有を避ける。
    """
    needed = requirements(recipe, servings)
    return {
        "recipe_name": recipe["name"], "servings": servings,
        "needed": needed, "heat_target": recipe["heat_steps"],
        "heat_done": 0, "stage": "planned", "history": ["計画済み"],
    }


def move(job, stage, event):
    """内部補助。新しい辞書と履歴リストを作る。"""
    updated = job.copy()
    updated["needed"] = job["needed"].copy()
    updated["history"] = job["history"] + [event]
    updated["stage"] = stage
    return updated


def prepare(job):
    """確保済み状態を下ごしらえ済みにする。順序違反はRuntimeError。"""
    if job["stage"] != "reserved":
        raise RuntimeError("材料確保後に下ごしらえしてください")
    return move(job, "prepared", "下ごしらえ完了")


def heat(job, stove_ok=True):
    """仮想加熱を1ステップ進める。故障時・順序違反時はRuntimeError。"""
    if type(stove_ok) is not bool:
        raise TypeError("コンロ状態はboolで指定してください")
    if job["stage"] not in ("prepared", "heating"):
        raise RuntimeError("下ごしらえ後、加熱完了前に実行してください")
    if not stove_ok:
        raise RuntimeError("コンロ故障: 加熱を中断しました")
    count = job["heat_done"] + 1
    stage = "cooked" if count == job["heat_target"] else "heating"
    updated = move(job, stage, f"加熱 {count}/{job['heat_target']}")
    updated["heat_done"] = count
    return updated


def plate(job):
    """加熱完了状態のみを盛り付ける。"""
    if job["stage"] != "cooked":
        raise RuntimeError("加熱が完了していません")
    return move(job, "done", "盛り付け完了")


def is_complete(job):
    """本モジュールの関数で作った状態について、完成条件を確認する。"""
    return (
        job["stage"] == "done"
        and job["heat_done"] == job["heat_target"]
        and "材料確保" in job["history"]
        and "下ごしらえ完了" in job["history"]
        and job["history"][-1] == "盛り付け完了"
    )


def run_simulation(recipe, servings, stock, stove_ok=True):
    """工程を実行して結果辞書を返す。
    画面表示も入力データの変更もしない。

    不正な入力はTypeError/ValueError。
    材料不足・機器故障はok=Falseの結果。
    確保後の失敗では、確保分を返却しない在庫方針を採用する。
    """
    job = new_job(recipe, servings)
    validate_stock(stock)
    if type(stove_ok) is not bool:
        raise TypeError("コンロ状態はboolで指定してください")
    remaining = stock.copy()
    error = None
    missing = shortages(stock, job["needed"])
    if missing:
        error = f"材料不足: {missing}"
    else:
        remaining = reserve(stock, job["needed"])
        job = move(job, "reserved", "材料確保")
        try:
            job = prepare(job)
            while job["stage"] != "cooked":
                job = heat(job, stove_ok)
            job = plate(job)
        except RuntimeError as exc:
            error = str(exc)
    return {
        "ok": error is None and is_complete(job),
        "job": job, "remaining": remaining, "error": error,
    }


def main():
    """対話入力と表示を担当する、副作用のある外側の処理。"""
    print("カレー工程シミュレーター（仮想工程・実際の安全判定なし）")
    try:
        servings = int(input("人数（1〜20）: "))
        kind = input("レシピ standard / seafood [standard]: ")
        kind = kind.strip() or "standard"
        recipe = make_recipe(kind)
        needed = requirements(recipe, servings)
        stock = {}
        for name, amount in needed.items():
            raw = input(f"{name}の在庫 [必要量{amount}]: ").strip()
            stock[name] = amount if raw == "" else int(raw)
        answer = input("コンロは正常ですか y/n [y]: ")
        answer = answer.strip().lower() or "y"
        if answer not in ("y", "n"):
            raise ValueError("コンロ状態はyまたはnで入力してください")
        result = run_simulation(
            recipe, servings, stock, stove_ok=(answer == "y")
        )
    except (TypeError, ValueError) as exc:
        print(f"入力エラー: {exc}")
        return
    except (EOFError, KeyboardInterrupt):
        print("\n入力を中断しました")
        return
    for event in result["job"]["history"]:
        print(event)
    print("完成" if result["ok"] else f"未完成: {result['error']}")
    print("残り在庫:", result["remaining"])


if __name__ == "__main__":
    main()

    付録F　再帰関数・クラス・オブジェクト指向への発展

    F.1　仕事の中に、同じ形の仕事がある

    第2章の業務分解では、大きな仕事の下に小さな仕事がありました。さらにその下にも仕事があります。このような入れ子の構造を同じ規則でたどるとき、「再帰」が役立ちます。再帰とは、処理の中で自分自身を、より小さい問題に対して呼び出すことです。

    階層を持つ工程表を、葉まで数える例を考えます。葉とは、さらに分解しない作業です。入力の形は「分解されていない作業名の文字列、または作業を並べたリスト」と決めます。空のリストは作業0件です。リストの中へリストを入れられるので、階層を表せます。

    Python 3
    def count_tasks(task):
    if isinstance(task, str):
        return 1
    total = 0
    for child in task:
        total += count_tasks(child)
    return total

recipe_tasks = [
    ["肉を切る", "野菜を切る"],
    ["炒める", "煮込む", "ルーを加える"],
    "盛り付ける",
]
print(count_tasks(recipe_tasks))
print(count_tasks([]))

    実行結果

    6
0

    文字列に達したら1を返して終わります。これが「停止条件」です。リストなら子の作業へ進み、その数を合計します。各呼び出しのtotalは別々のローカル変数です。呼び出しから戻った値を親の合計に加えます。

    この例のレシピは、有限で循環のない入れ子という前提です。自分自身を含むリストを作ったり、停止条件へ近付かない呼び出しをしたりすると、終わらなくなります。Pythonには再帰の深さの上限があり、深すぎるとRecursionErrorが起きます。上限を上げる前に、問題が適切に小さくなっているかを確かめます［S14］。

    再帰は、あらゆる繰り返しを置き換える万能な書き方ではありません。じゃがいもを順に切るだけならforが簡単です。深い階層を扱うときにも、明示的な作業リストを用いて反復する方法があります。データの形と、読みやすさや制約に合わせて選びます。

    F.2　呼び出しグラフと実行時の木

    count_tasksは自分自身を呼ぶので、関数の種類を点にした呼び出しグラフには自分へ戻る辺があります。一回の実行を展開すると、全体のリスト、下ごしらえのリスト、肉の文字列、といった個々の呼び出しが木の節になります。同じ名前の関数でも、各節の入力とローカル変数は異なります。

    木の図を見て実行順を考える場合、通常の同期呼び出しでは子の処理を終えて親へ戻り、次の子へ進みます。ただし、グラフそのものは順序のすべてを記述しません。条件分岐で呼ばない枝も、ループで何度も呼ぶ処理もあります。コードと入力によって実際の履歴が決まります。

    F.3　クラスは状態と操作をまとめる

    在庫の辞書と、その操作関数を別々に扱う代わりに、一つの型へまとめる方法があります。その定義に使うのが「クラス」です。クラスから作った具体的なオブジェクトを「インスタンス」と呼びます。第6章以来使ってきた整数やリストもオブジェクトですが、ここでは自分の業務に合わせた型を定義します。

    Python 3
    class Pantry:
    def __init__(self, stock):
        self.stock = stock.copy()

    def remaining(self, name):
        return self.stock.get(name, 0)

    def use(self, name, amount):
        if type(amount) is not int or amount <= 0:
            raise ValueError("使用量は正の整数にしてください")
        if self.remaining(name) < amount:
            raise ValueError("在庫不足です")
        self.stock[name] -= amount

pantry = Pantry({"肉_g": 300})
pantry.use("肉_g", 100)
print(pantry.remaining("肉_g"))

    実行結果

    200

    class Pantry:が型の定義です。__init__は、新しいインスタンスを初期化するときに使う特別なメソッドです。selfは、そのメソッドが操作するインスタンスを受け取る仮引数の慣用名です。self.stockは、そのインスタンスに保持する属性です。

    pantry.use(...)は、その在庫オブジェクトに使用を依頼する形です。この設計ではオブジェクトの状態を変更します。第13章の純粋な関数とは違い、副作用を含む操作です。それが悪いわけではありませんが、再実行の影響を考える必要があります。

    例を短くするため、初期在庫の全形式検査は省略しています。正式な在庫システムにするなら、完成版の検査を取り込むなど、契約を補います。また、Pythonではpantry.stockへ外からアクセスできるため、クラスにしただけで外部の不正変更を完全に禁止できるわけではありません。

    F.4　オブジェクト指向は現実の物を並べるだけではない

    オブジェクト指向は、状態と操作、責任、オブジェクト間のやり取りを設計する考え方です。「肉クラス」「鍋クラス」「玉ねぎクラス」と名詞を並べればよいわけではありません。必要な役割が何かを考え、その境界を決めます。

    例えば在庫を更新する操作を一つのオブジェクトへ集めれば、更新方針をそろえやすくなります。一方、必要量の計算は単純な関数のままでも十分かもしれません。関数型、手続き型、オブジェクト指向を、互いに排他的な陣営として覚える必要はありません。Pythonでは、問題に合う形を組み合わせます。
