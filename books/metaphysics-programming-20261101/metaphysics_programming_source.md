## はじめに　プログラマは小さな宇宙の創造者である

ある朝、在庫管理システムから最後の一台が消えた。倉庫に行くと、その一台は昨日と同じ場所にある。段ボールにも傷はない。消えたのは製品ではなく、画面の数字だ。ところが営業担当者にとって、その製品はもう売れない。現物は存在する。販売可能な在庫は存在しない。どちらの担当者も嘘をついていない。

存在についての議論は、こうして始められる。暗い部屋で宇宙の深淵を見つめる必要はない。午前中の問い合わせだけで十分だ。

プログラムを書くとき、私たちは世界の何を一個として数えるかを決める。人、注文、温度、部品、故障。さらに、その一個が変化しても同じ一個であり続ける条件を決める。修理後も同じ製品なのか。取り消された注文は消すのか、それとも取り消されたものとして残すのか。測っていない温度はゼロなのか。それぞれの答えが、データ構造や分岐条件になる。

形而上学は、存在、同一性、可能性、時間、原因といった基本的な事柄を問う。その境界は歴史を通じて一定ではなく、心や数学をめぐる問題とも重なる。本書はその全体を時系列に並べる歴史書ではない。小さなプログラムを入口にして、ふだんは透明になっている前提を見えるようにする試みだ。[R01](#ref-r01)

プログラマは哲学者の難問をすでに解決している、と言いたくなるかもしれない。だが、そう書けば本は売りやすくなり、議論は壊れやすくなる。プログラムの中で「同じ顧客」を顧客番号の一致として定義することはできる。しかし、その定義が人間の同一性の最終解答になるわけではない。二人に同じ番号を発行しても、人間が融合することはない。

それでも実装には哲学的な強みがある。曖昧なまま使っていた考えを、動く規則にすると、思わぬ帰結が現れる。「未入力はゼロでよい」という一言は、月平均を計算した瞬間に、存在しない低温の日を生み出す。「名前が同じなら同じ人」という直感は、同姓同名の来訪とともに破綻する。実装は答えを確定する機械である以上に、答えの代償を明らかにする機械なのだ。

本書ではPythonを使う。コードを読んだことがなくても構わない。`print`は結果を表示する命令、角括弧で囲んだものは並んだデータ、`True`と`False`は判定の結果だ。インデントは処理のまとまりを表す。詳細な文法を覚えるより、何を区別し、何を同じと見なしたのかに注目してほしい。

三つの地図を持って進もう。第一は言語の地図で、Pythonの規則に従えば何が起きるか。第二は設計の地図で、その規則を何のために選ぶか。第三は哲学の地図で、その選択を現実全体についての主張へ広げてよいか。三枚の地図が似た形をしていても、重ねた瞬間に同じ土地になるわけではない。

本書の副題は、答えではなく挑発である。存在するとは、実装することなのか。まずは宇宙全体ではなく、たった一つの名前から始めよう。

## 第1章　変数は存在するのか

### 一行の創世記

`x = 1`。これほど平穏な一行も珍しい。コンピュータは煙を上げないし、新しい自然数の誕生を祝う通知も出ない。それでも、実行前と実行後には違いがある。実行後には、名前`x`を使って値1を扱える。

ここで「箱xに1を入れた」と考えると便利だ。しかし、その箱の絵は、すぐに手直しが必要になる。Pythonでは名前がオブジェクトを参照する。代入は名前とオブジェクトの結び付きを作る操作であり、右辺の対象を必ず複製する操作ではない。[R02](#ref-r02)

入力は次の通りだ。各コードは、特に断らない限り独立に実行できる。

```python
a = [1, 2]
b = a
b.append(3)
print(a)
print(a is b)
```

実行結果：

```text
[1, 2, 3]
True
```

`append`はリストの末尾に要素を加える。`b`に対して操作したのに、`a`を表示しても3が現れる。遠隔操作の魔法ではない。二つの名前が一つのリストを参照しているからだ。`is`は、同じオブジェクトかどうかを調べている。

この例の後で`b = [9]`と書けば、`b`は別のリストを参照する。元のリストの中身が9に置き換わるのではない。名前の付け替えと対象の変更を区別するだけで、初心者が遭遇する相当数の「勝手に変わった」が説明できる。勝手だったのはコンピュータではなく、頭の中の箱の絵のほうである。

### 名前を消しても消えないもの

倉庫に棚があり、棚に部品があり、部品を指す帳簿がある。帳簿の一行を消すことと部品を廃棄することは違う。Pythonでも、名前を消す`del`を即座に対象の破壊と読んではいけない。

```python
original = ["ねじ"]
alias = original
del original
print(alias)
```

実行結果：

```text
['ねじ']
```

消えたのは`original`という結び付きである。`alias`から対象を利用できる。さらに、名前を直接付けずに、別のリストの要素としてオブジェクトを保持することもできる。名前があることと、対象が利用可能であることは一致しない。

ただし帳簿の比喩にも限界がある。現物の部品は、すべての帳簿から消えても床に転がっていられる。Pythonのオブジェクトは、プログラムから到達できなくなると回収の対象になりうる。この違いには第7章で戻ろう。比喩は入口にはなるが、住民票にはならない。

### 電圧、整数オブジェクト、数の一

「本当にあるのは、結局ビットだけではないか」。もっともな疑問だ。物理的なコンピュータには、記憶素子や電気的状態がある。しかし、その状態を何として数えるかは、説明の水準によって変わる。

紙に書かれた「1」はインクの跡である。その跡が一円を意味するか、一台を意味するか、単なる練習文字なのかは、インクの質量だけでは分からない。同様に、ビット列の物理的説明と、それがPythonの整数を表すという説明は、互いに競争するとは限らない。異なる問いに答えている。

ここでは少なくとも、物理的な記憶状態、言語の規則における整数オブジェクト、数学で扱う数の一を区別したい。プログラムを実行して整数オブジェクトを利用できるようにしても、人類が知らなかった自然数の一を新しく製造したわけではない。逆に、数が抽象的だからといって、コンピュータの消費電力まで抽象化できるわけでもない。

数学的対象は人間の活動と独立に存在すると考える立場なら、計算はその対象についての関係を扱う行為になる。記号の操作や人間の実践を重視する立場なら、まず何を許される操作とするかに注目するだろう。本書はこの段階でどちらかに決着を付けない。同じPythonコードを、異なる存在論を持つ人々が使用できること自体が重要なのだ。計算結果の合意は、存在論の合意より狭い。[R03](#ref-r03)

### 代入は、等式に似た別の約束である

数学の授業で、`x = x + 1`と書けば疑わしい目で見られる。両辺からxを引くと0＝1になるからだ。ところがプログラムでは、これはごく普通の一行である。同じ記号が登場しているのに、なぜ事件にならないのか。Pythonの代入では、右側を評価して得た対象へ、左側の名前を結び付ける。左右を永遠に等しいと宣言しているのではない。

ここで、時間という語をまだ厳密に使わなくても、少なくとも「評価する前の対応」と「評価した後の対応」を分ける必要がある。最初にxが1を指していたなら、右側のxはその1を使う。計算結果は2であり、その後でxが2を指す。1という整数オブジェクトの中身を彫り直して2にするわけではない。整数はイミュータブルである。どの記憶領域を再利用するかといった実装の細部は、この言語上の説明とは別の層だ。

この違いは、数学が静的でプログラミングが動的だという決まり文句だけでは捉えきれない。数学でも変化は記述できる。たとえば最初の状態をx₀、次の状態をx₁と分け、x₁＝x₀＋1と書けば矛盾はない。プログラムは、記号の添字を毎回書く代わりに、名前と対象の対応を実行の中で更新していると考えられる。記述方法の違いを、扱える世界の限界だと思い込む必要はない。

紙の上でも試してみよう。「x」という札を一枚作り、1と2のカードを机に置く。札を1のそばから2のそばへ移す。次に、札は動かさず、カードそのものに上書きする。二つの操作は、遠目にはどちらも「xが2になった」と見える。しかし、同じカードを見ていた別の人には違う出来事になる。名前の付け替えと対象の変更を区別する価値は、他の観察者が加わった瞬間に明らかになる。

プログラミングで難しいのは、記号が何を意味するかだけではない。どの時点の、どの対応を見ているのかも必要になる。「変数の値を見た」という短い報告に、実は小さな観測条件が折り畳まれているのだ。

### アドレスは、住所であって家ではない

オブジェクトの説明で、メモリアドレスを持ち出すのは便利だ。家と住所の比喩を使えば、二つの名前が同じ対象を指すことも説明しやすい。しかし便利な比喩には、たいてい立入禁止区域がある。

Pythonの`id`は、あるオブジェクトの生存期間中に一定で、同時に存在する別のオブジェクトとは異なる整数を与える。CPythonではその値がメモリアドレスに対応するという実装上の事情があるが、すべてのPython実装に同じ内部構造を要求する規則ではない。また、生存期間が重ならない対象で同じIDが使われることはありうる。引っ越した後の住所に別の家族が住めるように、番号の再登場を対象の復活と読んではいけない。[R04](#ref-r04)

仮に、あるプログラムを終了して、翌日もう一度実行したとしよう。昨日の顧客データと今日の顧客データが同じ顧客を表していても、そのPythonオブジェクトが昨日から生き続けているとは限らない。ファイルを読み、別のオブジェクトとして組み立て直した可能性がある。顧客の同一性を、実行中だけ有効な識別子に任せると、この境界で困る。

逆に、一つのオブジェクトを使い回し、今日の注文、明日の注文を順にそこへ読み込む設計も考えられる。すると実行中の対象は同じでも、表している注文は変わる。ここでは「同じオブジェクトだから同じ注文」という推論が壊れる。対象と表現対象を区別する必要は、哲学のためのぜいたくではない。実際のシステムの寿命を考えるときに必要な区別である。

このように、住所の比喩は参照を理解する助けになるが、住所を見れば住民の人生が分かるわけではない。プログラムの中にも、メモリの住所だけでは決まらない同一性や意味がある。それらをすべて「実体」という一語に詰め込むと、説明は短くなり、問題は長引く。

### 辞書に載っていない星

存在することと、名前を持つことの差を、もう少し遠くから眺めよう。まだ発見されていない星に人間の名前はない。しかし、名前がないから星もない、とは通常考えない。一方、物語の登場人物には名前、誕生日、好物まであるが、それだけで現実に人がいることにはならない。名前は存在を保証せず、存在は名前を要求しない。

プログラム内では事情が少し違うように見える。名前も参照もなければ、その対象をどう扱うのか。ここで、存在していることと、現在の処理から到達できることを分ければよい。たとえばリストの要素は、各々に独立した変数名を付けなくても取り出せる。対象へ届く道は、単独の名前だけではない。インデックス、辞書のキー、他の対象の属性を経由する道もある。

では、どこからも到達できない対象は存在するのか。この問いには、処理系の内部にまだ置かれているかという答えと、プログラムがこれから観測できるかという答えがありうる。後の章でガベージコレクションを扱うとき、この違いが具体的な仕事になる。ここでは、「存在する」の代わりに何を確かめたいのかを尋ねる習慣だけ持ち帰ればよい。

数学の数については、さらに別の対立がある。数が人間の記号から独立した抽象的対象としてあると考える立場もあれば、そのような存在を認めずに数学の働きを説明しようとする立場もある。メモリに整数を置けたことは、この論争を解決しない。実装された整数が何を表しているかについて、すでに異なる解釈が可能だからだ。[R03](#ref-r03)

ただし「解決しない」は「無関係である」ではない。数という抽象的対象、整数オブジェクトという言語上の対象、その実現に使われる物理状態を分けてみるだけでも、議論は整理される。宇宙の存在を一度に問うより、いま話している存在の層を確かめるほうが、最初の一歩としてはずっと役に立つ。

### 存在を調べる質問にも種類がある

名前が定義されているか。メモリ上に対象が保持されているか。データベースに対応する記録があるか。現実の製品が倉庫にあるか。これらを全部「存在確認」と呼ぶと、会話は滑らかになり、障害調査は難しくなる。

たとえば製品番号を名前として持つ辞書を作っても、それだけで製品が製造されるわけではない。一方、まだ製造されていない製品の設計をデータとして扱うことはできる。「この製品がある」という表現が、設計案、受注対象、完成品のどれを指すかを決める必要がある。

発見は地味だが強力だ。存在を問う前に、どの水準での存在を尋ねているかを特定できる。これは問題から逃げるためではない。異なる質問に同じ答えを返してしまう事故を避けるためである。

箱の絵から矢印の絵へ移るだけで、世界は少し変わった。だが、一個の対象を指せることと、それが何であるかを知ることは別だ。名前`a`が指すものは、なぜリストであって犬ではないのだろう。

**章末の問い**　二つの部署が同じ製品を別々の番号で管理しているとき、対象が二つあるのか、名前が二つあるのか。何を調べれば区別できるだろうか。

## 第2章　クラスとインスタンス――プラトンとアリストテレスの再会

### 犬の設計図は吠えるか

犬を二匹作ってみよう。現実には大仕事だが、ここでは餌も散歩も不要だ。その代わり、この犬から現実の犬について分かることは、あまり多くない。

```python
class Dog:
    def __init__(self, name):
        self.name = name

    def bark(self):
        return self.name + "が吠える"

pochi = Dog("ポチ")
hana = Dog("ハナ")
print(pochi.bark())
print(isinstance(hana, Dog))
```

実行結果：

```text
ポチが吠える
True
```

`Dog`はクラス、`pochi`と`hana`が参照するものはそのインスタンスだ。`__init__`は、通常のこの作り方では新しいインスタンスを初期化し、名前を持たせる。厳密にはオブジェクトの生成そのものと初期化は区別される。「コンストラクタ」という便利な一語で、すべての段階を押しつぶさないほうがよい。[R04](#ref-r04)

クラスを設計図、インスタンスを製品と呼べば理解しやすい。しかし画面に出たのは音ではなく文字列だ。犬を作ったと言いつつ、実際には犬についての非常に小さなモデルを作った。この留保を忘れると、哲学へ踏み出す前に、すでに世界を一匹取り違えている。

### 「犬であること」はどこにあるのか

二匹がどちらも犬なのは、何かを共有しているからなのか。共有される「犬であること」は、二匹とは別に存在するのか。それとも、似た個体をまとめて犬と呼んでいるだけなのか。ここに普遍者問題への入口がある。

プラトンのイデア論は、クラスとインスタンスの関係に似て見える。多くの個別的なものと、それらが依存する普遍的なものが区別されるからだ。ただし、中期対話篇を中心とするイデアの議論では、個物からの独立性や不変性が重要であり、単なる分類ラベルではない。対話篇間の展開や解釈上の論争もある。「プラトンがクラスを発明した」と書いてしまえば、その困難を消したことになる。[R05](#ref-r05)

Pythonの`Dog`は、プログラムの実行によって作られるクラスオブジェクトである。属性を変更することもできる。今日`Dog`を定義しなかったからといって、近所の犬が犬でなくなるわけではない。クラスは実行環境の中の人工物であり、プラトンのイデアをそのまま再現した存在ではない。

アリストテレスに進むと、個体、質料、形相、本質の関係が問題になる。何かがそのものである理由を、個物から離れた見本だけに求めるわけにはいかない。だが形相をソフトウェア、質料をハードウェアと機械的に翻訳するのも危険だ。彼の実体論は著作や論点によって複雑で、普遍的な種と個物の形相を単純に同一視できない。[R06](#ref-r06)

本書にとっての収穫は、哲学者をプログラミング言語の陣営に振り分けることではない。分類、生成、説明という三つの役割を、一つの「設計図」という比喩が兼ねてしまうことに気付く点にある。

### クラスを自分で定義しない世界

次のコードでも、名前と鳴き声を持つデータは作れる。

```python
dog = {"name": "ポチ", "sound": "ワン"}
print(dog["name"], dog["sound"])
print(type(dog).__name__)
```

実行結果：

```text
ポチ ワン
dict
```

ユーザーが`Dog`クラスを書かなくても、犬のモデルは作れる。ただしPythonから型が消えたわけではない。このオブジェクトは組み込みの`dict`型に属する。「クラスがなくてもオブジェクトは作れる」という文は、「独自のクラス定義を書かなくても」と限定すれば正確になる。

辞書で十分な場面もあれば、属性や操作のまとまりをクラスで明示したい場面もある。この選択は普遍者の実在についての投票ではない。実在論者も辞書を使い、唯名論者もクラスを定義できる。

唯名論には複数の形があるが、普遍者や抽象的対象を存在者として認めない立場を含む。その課題は、そうした対象に頼らずに類似や一般的な記述を説明することだ。「何でも好きに命名すればよい」という無責任な思想ではない。[R07](#ref-r07)

たとえば部品を「ねじ」という種類でまとめることには、反復利用や共通検査を可能にする利点がある。しかし表面処理の違いで摩擦が変わるなら、種類の名前が同じでも締結時の挙動は変わる。普遍的なまとめ方を採用したからこそ、どの差異を残すべきかという責任が生じる。

### 似ているから同じ種類なのか

机の上に、赤いリンゴと赤い工具箱を置く。どちらも赤い。では、両者に共通する「赤さ」は、一つの何かなのだろうか。それとも、異なる二つの物を私たちが同じ言葉で呼んでいるだけなのだろうか。犬の分類よりも単純に見えるこの例でさえ、共通性をどのように説明するかという問題が残る。

共通の性質を実在的に扱う説明は、なぜ離れた二つの対象へ同じ述語を適用できるのかに答えようとする。一方、普遍者を認めない説明にも、対象どうしの類似、個別の性質、言語の使い方などに訴えるさまざまな方向がある。唯名論を「全部ただの名前だから何でもよい」という態度に縮めると、なぜある分類がうまく働くのかを説明しようとする努力が見えなくなる。[R07](#ref-r07)

プログラマは、まず色を表す属性を作ればよいと思うだろう。たとえば両方のデータに`color="red"`と入れる。しかしその操作は、共通性を発見したのか、共通のラベルを与えたのか。データの中だけを見れば判定できない。対象を測って同じ範囲へ分類したのか、担当者が見た目で入力したのか、販売上の色名へ丸めたのかによって意味が違う。

赤い物のクラスを一つ作る方法もあるが、赤く塗った犬は「赤い物」と「犬」のどちらなのか。継承関係を増やしても、この問いが自動で消えるわけではない。色は変えられるが、種類は変えられないと決める設計もあれば、用途によって分類を変更する設計もある。どの性質に特別な地位を与えるかは、クラス図を描く前に考えているはずのことだ。

読者も身の回りの物を五個選び、二通りに分類してみてほしい。「材質」と「使う場所」では、同じ対象がまったく違うまとまりになる。片方が必ず誤りというわけではない。ここから、世界の分類には複数の目的が入り込むことが分かる。ただし、目的が違えば何でも同じくらい良いという結論までは出ない。燃焼試験をするのに、机の上に置くかどうかで試験体を分けても、説明力は乏しいだろう。

### 設計図をなくした製品

ある工場で、古い機械の図面が失われたとする。しかし機械はまだ動き、同じ形の部品を測って作ることもできる。このとき、図面がないから種類も存在しないとは言いにくい。反対に、図面だけ完成し、一台も製作していない製品もある。種類を示す記述と、その具体例があることは別である。

この比喩はクラスとインスタンスを考える助けになる。だが、プラトンのイデアを、人間が作った製造図面とそのまま重ねることはできない。図面は紙やファイルに記された人工物で、誤記もあれば改訂もある。プラトンが問題にする形相は、単に大量生産のための仕様書という意味ではない。また、何に対してどのような形相があるとされるかも、各対話篇の議論を無視して一律には扱えない。[R05](#ref-r05)

アリストテレスについても、個物の中に設計図ファイルが保存されていると考えた、と説明してはいけない。質料と形相の区別は、物が何であり、どのように成り立つかという説明に関わる。青銅と像の形の比喩は入口になるが、すべての存在を部品表とCADデータに分解する話ではない。生物についての説明を、製造品の比喩だけで済ませることにも限界がある。[R06](#ref-r06)

ソフトウェアのクラスは、ここでむしろ比喩の限界を示してくれる。クラスの定義を変更しても、外部世界の犬が一斉に変化するわけではない。私たちが作り替えたのは、犬についての情報を扱う規則である。もしそのプログラムがロボット犬を制御していれば、振る舞いが変わる場合はある。そこで変化をもたらすのは、形相の哲学説が証明されたことではなく、制御経路が物理的に接続されていることだ。

この差を押さえると、古代哲学を現代技術の先取りとして褒める必要がなくなる。哲学者がPythonを知らなかったことは欠点ではない。私たちがクラスを知っていることも、普遍者問題に勝った証拠ではない。同じ問いの一部に異なる道具を向けている、と考えるほうが実りが多い。

### 分類には、まだ見ていない一匹が入ってくる

クラスの便利さは、いま手元にある対象だけをまとめることではない。これから作る対象、まだ登録されていない対象にも同じ操作を適用する見通しを与えることだ。犬の名簿を三匹分集めることと、今後やって来る犬を受け入れる仕組みを作ることの差がここにある。

しかし、この見通しは失敗しうる。すべての犬が声を出せると思って`bark`を必須にしたら、声を失った犬をどう扱うのか。吠える能力のない犬を犬ではないとするのか、それとも操作の結果として無音を許すのか。プログラムの都合が分類の本質へ忍び込む瞬間である。

この例で大切なのは、例外が一匹出たらクラスを捨てるべきだということではない。生物学的な犬であること、現在発声できること、音声出力を持つゲームの登場物であることを分けることだ。これらを一つのクラスに束ねる設計は、小さなゲームなら十分かもしれない。獣医療の記録には不十分かもしれない。正しさを判断するためには、何を扱うプログラムかを知らなければならない。

逆向きの失敗もある。分類を一切せず、すべてを自由な辞書へ入れれば柔軟になると思う。しかし、名前の綴り、必須項目、利用できる操作が対象ごとに違えば、読み手は毎回その対象の世界を調査しなければならない。分類を避けたつもりでも、個々の処理が暗黙の分類を繰り返す。規則が消えたのではなく、見えにくい場所へ移ったのだ。

だから設計の争点は、分類するかしないかという二択ではない。どの共通性を明示し、どの差異を残し、どんな新しい対象が来たら分類を見直すかである。クラスは世界を凍結する宣言としても、改訂可能な仮説としても使える。その違いは構文ではなく、設計者の運用に表れる。

### 設計図もまた一つの物である

クラス自体もオブジェクトである、というPythonの特徴は、思考の向きを一段変える。「分類するものは分類されない」という直感は必須ではない。設計図も版を持ち、作成者を持ち、比較される。分類の道具も管理対象になる。

現場でも同じだ。部品だけを管理して設計図の改訂を管理しなければ、昨日の検査と今日の検査が何を対象にしていたのか分からなくなる。対象の世界の上に、対象を定義する道具の世界が重なる。さらにその道具を管理する規則がある。どこかに万能の設計図を置けば、それですべて終わるわけではない。

ここから見えてくるのは、「一個と種類」の問題の背後に、「種類を作る操作自体も一個の出来事である」という問題があることだ。プラトンとアリストテレスをPythonの開発会議に呼ぶなら、まず両者に仕様書の版番号を見せなければならない。もちろん、それで二人の論争が終わる気配はない。

**章末の問い**　犬に似たロボットを犬クラスに入れるべきだろうか。鳴き声を管理するソフトと、動物の健康を管理するソフトで、答えは変わるだろうか。

## 第3章　型とは何か――世界を分類するという暴力

### 足し算が急に文字になる

同じ`+`でも、何に使うかで結果が変わる。

```python
print(2 + 3)
print("2" + "3")
try:
    print(2 + "3")
except TypeError:
    print("型が合わない")
```

実行結果：

```text
5
23
型が合わない
```

数を加えたのか、文字をつないだのか。見た目は小さな差だが、許される操作が異なる。型は単に整理棚のラベルではない。その対象に何をしてよいかを決める規則に関わる。

Pythonではオブジェクトが型を持つ。ある名前が整数を参照した後、文字列を参照するようになることはできる。それは整数が文字列へ変身したという意味ではない。名前の結び付きが変わったのである。動的型付けは「型がない」の同義語ではない。

### 注釈は警備員ではない

次の関数には、整数を受け取り整数を返すという型注釈を付けている。

```python
def twice(x: int) -> int:
    return x * 2

print(twice(4))
print(twice("水"))
```

実行結果：

```text
8
水水
```

標準のPython実行系は、通常この注釈を理由に呼び出しを拒絶しない。型チェッカーは誤った引数として指摘しうるが、それは実行時の別の検査とは区別される。文字列に整数を掛けると反復になるため、この例は実行される。[R08](#ref-r08)

静的型付けでは、実行前の解析によって型に関する制約を検査する。動的型付けでは、実行時の対象の型に基づいて操作が行われる。実際の言語や道具には混合的な設計もある。静的であるほど正しい世界を表し、動的であるほど自由な世界を表す、という順位を付けることはできない。

型注釈があるから安全、という期待は、図面に材質が書いてあるから実物も必ずその材質だ、という期待に似ている。図面は有用だ。しかし、図面、製造、検査は別の仕事である。この比喩でも、型チェッカーが実際に保証する範囲を見落としてはいけない。型の静的検査は単なる願望の記載よりはるかに強い働きを持ちうる。

### 同じ数値型でも足してはいけない

温度20度と長さ20ミリメートルは、どちらも`20.0`で表せる。Pythonに渡せば足し算はできる。しかし、その40は何の単位だろう。

型に通ることと、領域の意味に通ることは異なる。物理量の次元を型に組み込む設計も可能だし、値と単位を一組にする方法もある。いずれにせよ、単に「数である」という分類では粗すぎる場合がある。

逆に細分化しすぎれば、現実で可能な変換や共通操作が書きにくくなる。同じ長さでも測定法別に完全に別の型にした結果、比較のための変換ばかりが増えるかもしれない。分類の価値は細かさの最大化にはない。防ぎたい誤りと許したい操作の釣り合いにある。

ここで章題の「暴力」が意味を持つ。分類は境界を引き、境界の外のものを拒否する。その拒否は、誤送金や単位間違いを防ぐために必要でもある。一方、人間を扱う入力フォームでは、分類に収まらない実在の人を「不正な入力」にしてしまうことがある。機械の拒否が、その人の存在に対する判定のように扱われるとき、設計上の便利さは制度上の力になる。

### 型が合っている事故

長さを表す二つの数を足したい。片方は30、もう片方は2だ。足せば32になる。Pythonは何も不満を言わない。だが、前者がセンチメートル、後者がメートルなら、欲しい結果は単位をそろえた230センチメートルである。計算が正常に終わることと、計算が目的に合っていることの距離が、ここでは数字一つの姿をして現れる。

同じ型の値だから意味も同じだという保証はない。整数の17は、年齢、個数、室温、顧客番号のどれでもありうる。型を増やし、それぞれを異なるものとして扱う設計なら、間違った組合せを拒否しやすくなる。反面、入力や保存の形式との変換は増え、何を許すかを細かく決めなければならない。

製品の重量と許容荷重を、どちらも質量の型で表すのは正しいだろう。しかし二つを足す意味があるかどうかは、単位だけでは決まらない。同じ単位でも、観測値、上限、目標値、差分は異なる役割を持つ。型による防御を強めても、意味の区別をどこまで組み込むかという判断は残る。世界を完全に分類し終えてからプログラムを書こうとすれば、たぶん納期より先に定年が来る。

そこで、どの間違いが起きやすく、起きたとき何が困るかを考える。単位の混同が重大なら単位を明示する。単位は同じでも取り違えやすい番号なら、その番号の種類を分ける。型の細かさは、細かいほど無条件によいわけではない。予想する誤りに対して、どこに壁を置くかという設計になる。

この発想では、型は世界の目録というより、作業の境界線である。何を同じ扱いにすると便利で、何を同じ扱いにすると事故になるか。その経験を、繰り返し検査できる規則へ変える。分類が人間の判断を含むことは弱点であると同時に、目的に合わせて改善できる理由でもある。

### 受け入れることと、保証すること

ある関数が整数を受け取ると書いてある。それだけで、負の整数を受け入れるかどうかは分からない。注文個数なら通常は負を拒みたいが、在庫の増減なら負が役に立つ。型が対象の集合を大まかに限定しても、その中で成立してほしい条件は別にある。

たとえば「0以上の整数」を受け入れ、「同じ個数の席を確保する」処理を考える。前半は入力についての条件だ。後半は処理の結果についての約束である。正しい形式の入力が来たことだけで、席の確保が成功したとは言えない。満席、他の利用者の予約、保存失敗といった状況が残る。型検査が通ったという一つの事実へ、業務の成功まで預けることはできない。

逆に、実行時の検査があるから型の記述は不要とも限らない。呼び出す側がどんな値を渡すべきかを早く知り、誤った組合せを実行前に見つけられるなら、意味がある。静的な検査、実行時の検査、テスト、文書は、互いに完全な代用品ではない。異なる時点で異なる種類の間違いを発見する。

Pythonの型注釈も、この役割分担の中に置けば理解しやすい。注釈それ自体があらゆる代入や呼び出しを自動で拒否するわけではない。静的型検査器などがその情報を利用する。型注釈を書いたこと、検査器に調べさせたこと、その検査器が何を保証するかは、三つの違う事実である。[R08](#ref-r08)

この区別は哲学にも似た警告を発する。ある概念の定義を示したことと、現実の対象がその定義を満たすと示したことは別である。「合理的な人」という分類を作ったところで、目の前の人の判断が合理的だと証明したことにはならない。分類の門を作ることと、門を通ったことを確認することを分ける必要がある。

### 型の外へ出た荷物

入力フォームが、住所を一つの国の形式に合わせて作られているとする。都道府県、市区町村、番地を順に入力する。国内で想定した利用者には便利だが、その区分に収まらない住所が来ると困る。入力者の暮らしがおかしいのではない。データ形式の想定範囲が露わになったのである。

ここで取りうる対応はいくつもある。利用範囲を明示して対象を限定する。自由記入欄を追加する。国や地域に応じて構造を変える。元の文字列を保存し、解釈した構造を別に持つ。どれも費用や使い勝手の違いがある。重要なのは、現在の形式に入らないことを、対象そのものの不正と混同しないことだ。

「分類するという暴力」という章題は、どの分類も道徳的に悪いという意味ではない。異なるものを一つの形式へ押し込むと、何かを切り落とす。その切断が見えなくなることへの警戒である。図書館の分類がなければ本は探しにくい。しかし、一冊を一つの棚へ置く必要から、内容が一分野だけに属すると結論してはいけない。

境界を柔らかくするだけでは解決しない場合もある。何でも受け付ける欄は、検索や集計が難しくなり、誤った内容が後工程へ流れる。厳格な型は対象を排除する危険を持ち、無制限の柔軟さは判断の負担を利用者へ押し戻す危険を持つ。公平な比較には、どちらがどんな仕事を誰に負わせるかを見る必要がある。

読者がフォームを一つ作るなら、「その他」を設けるだけで終わらず、その項目が選ばれた後の扱いまで考えてほしい。誰も読まない自由記入欄は、受け入れたように見せるだけの入口になりうる。型から外れた対象を扱う技術とは、例外を黙って箱へ詰めることではなく、区別が足りなかったという情報を設計へ戻すことである。

### 型が同じでも、できることは変わる

同じ扉でも、開いているときと閉じているときでは可能な操作が違う。開いている扉をさらに開ける処理を無害なものとして扱うか、誤りとして拒否するか。施錠された扉を閉じた扉の一種として扱うだけで十分か。対象の種類と、その対象がいま置かれた状態を分ける必要がある。

素朴な設計では、`opened`と`locked`という二つの真偽値を持たせるかもしれない。すると、開いていて施錠されているという組合せも、データとしては書ける。現物の仕組みによってその状態が不可能なら、表現できる状態の集合が、許したい状態の集合より広いことになる。

そこで「開」「閉」「施錠」の三状態から一つを選ぶ表現にすれば、少なくとも矛盾した真偽値の組合せを減らせる。さらに、どの状態からどの状態へ移るかを操作ごとに限定できる。ただし、三状態で十分かは用途による。半開き、故障、位置不明まで必要なら、また表現を改訂しなければならない。

これは、存在しない状態を作りにくくする設計である。入力のたびに無数の組合せを検査するより、最初から選択肢を整えることで誤りを減らせる場合がある。型やデータ構造が、正しさの一部を支えるというのはこういう意味だ。しかし、扉が本当に開いているかを確かめるセンサーの問題は残る。内部の表現が整合していても、現物との対応は別に検証しなければならない。

この例から、型と状態の境界も設計の選択だと分かる。状態ごとに別の型を使う方式も、一つの型の属性として状態を持つ方式も考えられる。どちらの構文を選ぶにせよ、何を許し、何を禁止したいかを先に言葉にする必要がある。コンピュータが分類を厳密に扱えるのは、人間が分類の意味を決めなくてよくなったからではない。

### 名前で仲間を決めるか、できることで決めるか

ある対象を受け入れる条件を、特定の型の所属に置くこともできる。あるいは、必要な操作ができることに置くこともできる。たとえば「長さを取得できる対象」を処理したいだけなら、リストと文字列の歴史的な親類関係を調べる必要はない。

名目的な型の区別には、誤って似たものを混ぜない利点がある。構造や振る舞いを重視する区別には、別々に作られたものを同じ仕事に利用できる利点がある。ただし、同名のメソッドがあるだけでは意味まで一致しない。`close`という操作が窓を閉じるのか、取引を終了するのかは名前だけでは保証されない。

自然の分類は人間が発見するのか、目的に応じて作るのか。第2章の問いが、実務上の選択として戻ってくる。材料を金属と樹脂に分ける分類は便利だが、導電性を調べるなら導電性樹脂が境界を横断する。現実が矛盾したのではない。分類の目的が違ったのである。

型システムを世界の真理と見なさなくても、型システムを尊重することはできる。道路の白線は自然法則ではないが、だから無視してよいとはならない。人工的な規則にも、その目的と適用範囲の中で強い理由がある。

ここから見えてくるのは、型の厳密さが増しても、何を型にするかという判断は消えないことだ。精密な分類器の手前には、分類する価値のある差異を選ぶ仕事が残る。

**章末の問い**　温度の欄に値がないとき、「温度という型に属する何か」があるのか、それとも温度の値そのものがないのか。境界に収まらないものより厄介なのは、何も入っていない欄かもしれない。

**出典と補足**　型注釈の非強制性は[R08](#ref-r08)、組み込み型の操作は[R09](#ref-r09)。社会的分類への接続は本書の考察であり、型理論から直接導かれる政治的結論ではない。

## 第4章　nullの哲学――「無」は存在するのか

### 冷凍庫が温暖化する日

温度計が一度も測定していないのに、画面には0と表示される。プログラマは空欄を避けたかっただけかもしれない。だが0度は、冷凍庫にとって重大な温度だ。未測定を0へ変えた瞬間、情報がなかった場所に、もっともらしい測定結果が発生した。

Pythonでは、値の不在を表すために`None`をよく使う。しかし`None`は「何も存在しない領域」ではない。`NoneType`の唯一のインスタンスであり、プログラムの中で参照できるオブジェクトだ。[R10](#ref-r10)

```python
temperature = 0
missing = None
print(temperature is None)
print(missing is None)
print(bool(temperature), bool(missing))
```

実行結果：

```text
False
True
False False
```

0と`None`は違う。それでも真偽値として評価すると、両方とも偽になる。`if temperature:`だけで未測定かどうかを判定すると、正常な0度まで除外してしまう。`None`を不在の印にするなら、`is None`で明示的に調べるのが分かりやすい。

### 空の箱と、箱がないこと

空文字列は文字を一つも含まない文字列であり、空集合は要素を持たない集合である。ゼロは数である。`None`は不在などを表すために使う特別な対象である。未定義の名前を評価すれば、単に`None`が返るのではなく、通常`NameError`になる。[R02](#ref-r02)

これらを「全部ない」とまとめると、検索結果がゼロ件なのか、検索をしていないのか、検索に失敗したのかが区別できなくなる。図書館の検索で「本はありません」と言われたとき、蔵書がないのと、端末が壊れているのは違う。どちらも貸出冊数はゼロかもしれないが、次に取るべき行動が異なる。

表1　欠如に似た表現の違い

|表現|この例で表すこと|誤って同一視すると起きること|
|---|---|---|
|`0`|測定された数値がゼロ|未測定と混ざる|
|`""`|長さゼロの文字列|名前未登録と名前取得失敗が混ざる|
|`[]`|要素ゼロのリスト|検索未実行とゼロ件が混ざる|
|`None`|契約で決めた不在の印|複数の欠如理由が混ざる|
|未定義の名前|名前の束縛が見つからない|通常のデータ欠如として扱えない|

どの表現を選ぶかは用途による。ただし、選んだだけで意味が自動的に定まるわけではない。`None`が未測定なのか、対象外なのか、失敗なのかを決めるのは、そのプログラムの契約だ。

### 「無」の印があるという逆説

欠席者を示す名札が机に置かれているとする。そこには確かに名札がある。しかし本人はいない。「不在を表すものが存在する」という状態は、日常では珍しくない。`None`の哲学的な面白さは、この小さなずれを非常に明瞭にするところにある。

哲学での無の議論は、単なる空のデータより広い。穴、欠如、否定的な事実、そもそも何も存在しない世界が可能か、といった問いがある。空の世界を記述した文章があることは、空の世界そのものがあることとは異なる。[R11](#ref-r11)

一つの立場は、欠如も説明に必要なものとして扱う。「給油がなかったので機械が止まった」という説明では、起きなかった出来事が重要だ。別の立場は、欠如を独立した物として数えず、潤滑油の量や摩擦の状態など、存在する事柄の組合せで説明しようとする。どちらにせよ、不在を示す印を導入しただけでは、この争いに決着は付かない。

「無をオブジェクトにしたから、無は存在する」と言うのは、地図に海と書いたので紙が濡れたと言うのに似ている。表示の存在と表示内容の存在を、もう一度分けなければならない。

### ないものを、二段階でなくす

辞書に`temperature`という項目がない場合と、項目はあるが値が`None`の場合を考えよう。前者はその項目をそもそも受け取っていないこと、後者は項目を知っているが値がまだないことを意味させられる。しかし、辞書の`get`を既定値なしで使うと、この違いが消える。

```python
missing = {}
unmeasured = {"temperature": None}
print(missing.get("temperature") is None)
print(unmeasured.get("temperature") is None)

sentinel = object()
print(missing.get("temperature", sentinel) is sentinel)
print(unmeasured.get("temperature", sentinel) is sentinel)
```

実行結果：

```text
True
True
True
False
```

最初の二つの結果からは、キーがなかったのか、値が`None`だったのかを区別できない。次に、ここでだけ使う特別なオブジェクトを既定値にした。これを目印として比較すれば、辞書に項目がない場合を分けられる。`object()`が生み出した対象には特別な超能力はない。他のデータとしてその対象を使わないという、この小さな設計上の約束が働いている。

ここには一つ面白い逆転がある。「情報が存在しない」という違いを保存するために、新しい対象を存在させたのである。無の表現は、無そのものを直接手に取る作業ではない。区別したい状況に応じて、印と規則を追加する作業だ。もちろん、哲学的な無を目印オブジェクトによって説明し尽くしたわけではない。

目印は便利だが、別のプロセスへ送ったり、ファイルへ保存して読み直したりすると、同じオブジェクトを参照しているという条件は一般に保てない。通信するデータなら、欠如の種類を表す明示的な項目を作るなど、別の規則が必要になる。小さな関数の内部でよい表現が、システムの境界でもよいとは限らない。

### 分からないことと、そうでないこと

ある部品が検査に合格したかを、`True`か`False`で記録したい。合格なら真、不合格なら偽。きれいな二分法だ。では、まだ検査していない部品はどちらなのか。不合格へ入れれば合格率が下がり、合格へ入れれば未検査品を出荷しかねない。

「合格だと分からない」と「不合格だと分かっている」は違う。否定が何にかかっているのかを言い直すと、混同が見える。前者は知識の状態についての説明であり、後者は検査結果についての説明だ。知識の欠如を、そのまま対象の否定的な性質へ変換してはいけない。

こうした場面では、未検査、合格、不合格の三状態を明示できる。さらに再検査中、判定不能、試験設備の異常を区別したくなるかもしれない。状態が増えるのは、現実がいきなり複雑になったからとは限らない。最初の二値が隠していた違いを、後から認識したのである。

ただし、区別は多いほど無条件によいわけでもない。作業者が判断できない細分化を求めると、欄を埋めるための当て推量が増える。意味の違う十種類の欠如を定義しても、入力現場で分けられなければデータの精密さは見せかけになる。分類の解像度は、観測と運用の解像度に合わせなければならない。

この問題は、検索結果がゼロだった場合にも現れる。名簿で見つからなかったから、その人は存在しないのか。名簿がすべての対象を漏れなく含むという前提があるなら、その範囲では強い否定の根拠になる。登録漏れがありうるなら、分かるのは検索に使った情報と照合条件のもとで見つからなかったことまでだ。データの世界の外をどこまで考えるかによって、ゼロ件の意味が変わる。

### 欠けたデータは、沈黙しているだけか

測定結果が一部欠けているとき、その値を適当に埋めて平均を計算したくなる。だが、欠け方そのものが情報を持つ場合がある。正常な温度では測定でき、極端な温度のときだけセンサーが停止するなら、記録されたデータだけの平均は現象を正しく表さないかもしれない。

ここで、欠けた値をゼロにするのも、すべて捨てるのも、同じように一つの仮定を持ち込む。ゼロへ置けば実在しない測定値を追加する。捨てれば、記録できた場合だけを集めた集団について計算する。どちらが適切かは、欠如がどのように生じたかによる。計算を実行できることは、その仮定の根拠にはならない。

たとえば十個の試作品のうち、八個の耐久試験が終わり、二個はまだ動いているとする。二個の寿命をゼロと記録するのは明らかに不自然だ。かといって八個だけで平均を出し、それを十個の平均寿命と呼ぶのも違う。まだ終わっていないという事実には、少なくとも現在まで動いたという情報が含まれている。空欄はいつも情報量ゼロではない。

この例から分かるのは、欠如の表現が分析手法の前提と接続していることだ。本書では寿命解析の手法へ踏み込まないが、データを作る段階で欠如の理由と観測期間を消してしまえば、後からどんな高度な計算をしても取り戻せないものがある。`None`を見て単に邪魔だと思うか、まだ言葉にしていない観測条件だと思うかで、設計は変わる。

### 実在しない数値より、正直な空欄

欠如を嫌う気持ちは理解できる。グラフに穴があると不格好だし、報告書の空欄は質問を呼ぶ。だから初期値の0、仮の日付、適当な標準値が入れられる。すると機械は処理しやすくなるが、読み手はそれが測定値なのか、入力の都合なのかを見分けられなくなる。

必要なのは、欠けたまま何もしないことではない。仮の値を使うなら、それが仮であるという状態を一緒に残す。値そのものと、その値をどのように得たかを別の情報として扱う。後から測定値へ置き換えるときも、どの判断が仮定に依存していたかをたどれるようにする。

ここでは「無」を巧妙に表すことより、知らないことを知っているふりへ変えないことが重要になる。プログラムが壊れずに動くための工夫と、人間が誤解せずに読むための工夫は、重なることもあれば衝突することもある。その衝突を見えるようにするのが、欠如を一つの概念として考える利点だ。

### 欠如に理由を持たせる

値一つで足りないなら、状態を添えればよい。

```python
readings = [
    {"status": "ok", "value": 0.0},
    {"status": "not_measured", "value": None},
    {"status": "sensor_error", "value": None},
]
valid = [r["value"] for r in readings if r["status"] == "ok"]
print(valid)
```

実行結果：

```text
[0.0]
```

これは欠如をより細かく分類しただけで、万能ではない。`status`が`ok`なのに`value`が`None`という矛盾した組合せも、この辞書だけなら作れてしまう。型や生成関数、検査によって許される組合せを狭める設計が必要になる。

単一の`None`には、簡潔で使いやすい利点がある。理由ごとの表現には、回復処理や説明がしやすい利点がある。後者を常に採用すればよいわけでもない。たった一つの検索結果に十種類の不在を導入すれば、読み手が理由の分類表の中で行方不明になる。

設計の問いは、「無を完全に表現したか」ではなく、「次の判断に必要な差を残したか」である。この問いなら、哲学的な難しさを認めたまま、具体的な改善を進められる。

**章末の問い**　未測定と故障の両方に同じ`None`を使ったとき、二つの状態は同じなのだろうか。それとも同じ記号で違いを見えなくしただけだろうか。

**出典と補足**　`None`の仕様は[R10](#ref-r10)、真偽値としての評価は[R09](#ref-r09)、無についての議論の範囲は[R11](#ref-r11)。SQLのNULLはPythonの`None`とは別の規則を持ち、第14章で触れる。

## 第5章　`==` と `is`――二種類の「同じ」

### 双子の買い物かご

買い物かごが二つあり、どちらにも同じ商品が一つ入っている。同じかごかと聞かれれば、たいていの人は「中身は同じだが、かごは別」と答える。日常語では、この切り分けは難しくない。ところがコードの中では、同じという一語が急に広がりすぎる。

```python
a = ["パン"]
b = ["パン"]
c = a
print(a == b)
print(a is b)
print(a is c)
```

実行結果：

```text
True
False
True
```

この例では`==`はリストの要素を比較し、`is`は同じオブジェクトかを比較する。`c`は`a`と同じリストを参照するので、`a.append("牛乳")`とすれば`c`からも牛乳が見える。`b`には現れない。

哲学では、一つの同じものなのかという数的同一性と、性質が同じなのかという質的な一致を区別する。ただし、Pythonの`==`を「すべての性質が同じ」と訳してはいけない。比較に採用された性質について一致しているにすぎない場合がある。[R12](#ref-r12)

### 比較は中立な目ではない

ある工場で二本のねじを比較するとする。寸法が同じなら同じ部品なのか。材質、表面処理、摩擦係数、製造ロットまで同じでなければ駄目なのか。設計上の互換性を調べる比較と、不具合品を追跡する比較では、残すべき情報が異なる。

プログラムでも、比較演算は対象を丸ごと透視する装置ではない。ユーザー定義クラスなら、`__eq__`で等しさの振る舞いを定義できる。顧客番号だけを見ることも、金額と通貨の組を見ることもできる。無茶な実装をすれば、数学的な等号に期待する性質さえ失わせられる。[R13](#ref-r13)

標準的な数値にも、注意が必要な例がある。

```python
n = float("nan")
print(n == n)
print(n is n)
```

実行結果：

```text
False
True
```

NaNは浮動小数点の特別な値で、等値比較では自分自身とも等しくならない。一方、この二つの`n`は同じオブジェクトを指す。これで「`is`が真なら必ず`==`も真」という一般化が崩れる。コードの`==`は、論理学の同一性そのものではないのだ。

また、整数や文字列で`is`を使って値を比較してはいけない。同じ不変値のオブジェクトを再利用するかどうかには実装や状況による違いがありうる。小さな数の実験がたまたま期待通りだったとしても、そこから言語全体の規則を発見したことにはならない。[R04](#ref-r04)

### ライプニッツの原理を逆にしない

同一者不可識別の原理は、同じものなら、そのものについて成り立つ性質は一致する、という方向の主張だ。反対に、性質が一致するなら同じものだ、という不可識別者同一の原理を考えることもできる。後者は、どんな性質を認めるかによって内容が変わり、哲学的に争われる。[R12](#ref-r12)

この二つを混同すると、測定結果が同じ二本のねじを、一本だと結論してしまう。しかし測った性質の一致と、あらゆる関連する性質の一致は違う。測定精度の限界もある。さらに二本が置かれている位置や製造履歴は違うかもしれない。

「同じものなのに昨日と今日で性質が違うではないか」という反論も、一度落ち着いて読む必要がある。昨日冷たかったコップが今日温かいことは、同時に同じ意味で冷たくかつ冷たくないという主張ではない。性質が帰属する時点を区別しなければならない。

プログラムの可変オブジェクトでも同じ注意がいる。`a`の昨日の中身と今日の中身が違うことから、ただちに別のオブジェクトだとは言えない。逆に、状態が完全に一致する二つのオブジェクトを、それだけで同一だとは言えない。

### ほとんど同じ、は同じではない

二つの金属部品の長さを測る。測定値が0.1ミリメートル未満しか違わなければ、製造上は同じものとして扱いたいとする。この判断自体は不合理ではない。しかし、その「同じ」を数学的な等しさと同じように使うと、困ったことが起きる。

```python
def close(a, b):
    return abs(a - b) < 0.1

a, b, c = 10.00, 10.09, 10.18
print(close(a, b), close(b, c), close(a, c))
```

実行結果：

```text
True True False
```

AとBはほとんど同じで、BとCもほとんど同じだが、AとCはこの基準では同じでない。これは浮動小数点数の誤差を狙った手品ではない。ここに使った値は境界から離れており、同じ閾値を実数へ適用しても同じ問題が起きる。近さという関係は、一般に推移的ではないのだ。

同じと見なす基準が推移的でないなら、代表品を選んで分類する手順によって結果が変わりうる。まずBを代表にすればAもCも同じ箱へ入る。Aを代表にすればCは外れる。部品が物理的に変化したわけではない。分類手続きが、比較の順番や代表の選び方に依存していたのである。

したがって、許容差による比較を使うことと、それをすべての等価性の代わりにすることを分けたい。許容範囲に入るか、互換部品として使えるか、図面上の同じ品番か、同一の現物か。製造現場なら当たり前に使い分けるこれらの問いが、コードへ移すと`==`という一つの記号へ吸い込まれやすい。

### 一と真が同じ箱に入る

Pythonの数値の比較には、初心者が驚きやすい例がある。`1`、`1.0`、`True`は、それぞれ整数、浮動小数点数、真偽値だが、等価比較では互いに等しい。真偽値の型`bool`は`int`のサブクラスである。この振る舞いは、型が違うなら必ず等しくない、という予想を裏切る。[R09](#ref-r09)

```python
values = {1, 1.0, True}
print(1 == 1.0 == True)
print(len(values))
print(type(1) is type(True))
```

実行結果：

```text
True
1
False
```

集合へ三つ入れたつもりでも、要素数は一つだ。ここでは、等しい数値は等しいハッシュ値を持つという規則とも整合している。だから辞書や集合で、これらを無条件に別のキーとして扱えると思ってはいけない。もしアプリケーションで区別が必要なら、種類を含めたキーを設計するなどの対応が必要になる。

この例は、Pythonが真理と数の哲学を解決したことを意味しない。`True`を1と比較できるようにした言語上の規則がある、という話である。数学や論理学で真理値をどう構成し、数とどのように関係付けるかには別の形式化もある。言語の一つの選択を、世界の唯一の構造へ昇格させないことが大切だ。

逆に、違う型でも同じ数値として扱えるのは便利な場面が多い。整数の1と浮動小数点数の1.0を、すべての計算で別物として拒否すれば、利用者は頻繁に変換しなければならない。統一によって得られる簡潔さと、失われる区別を比べることになる。等価性の設計は、何を一緒に扱うかという実務的な選択でもある。

### 同じ振る舞いなら置き換えてよいか

二つの計算方法が、試した入力のすべてで同じ結果を返す。では、片方をもう片方へ置き換えてよいだろうか。結果だけが問題ならよさそうだが、一方はファイルを書き換え、もう一方は何もしないかもしれない。一方はすぐに結果を返し、もう一方は一時間待たせるかもしれない。

何を観測に含めるかによって、同じという判定は変わる。返り値だけを見る観測者には等しくても、ログ、外部状態、資源消費、終了の有無まで見る観測者には違う。プログラムの等価性を考えるときは、まず比較する言語と環境、許される観測を定める必要がある。何も指定せずに「完全に同じ働き」と言うと、都合の悪い違いを後から消す余地ができる。

ここでライプニッツの原理と再び向き合える。同一の対象には、その対象について成立する性質の違いがない、という原理と、いま用意したテストで違いが見つからなかったことは、距離がある。テストが見落としている性質があるかもしれないし、そもそもテストが扱える性質の範囲を限定しているかもしれない。

一方で、私たちの実務は限定された観測に頼らざるをえない。部品を交換するとき、宇宙のあらゆる性質が一致するかは確認しない。取り付け、性能、寿命など、目的に関係する条件を調べる。これは数的同一性を証明する作業ではない。目的に対する代替可能性を確認する作業である。哲学的に強すぎる結論を求めなければ、限定された検査にも十分な価値がある。

### 同一性の判定を、誰が必要としているか

ホテルの予約を一つ取り、画面をもう一度開く。表示内容が同じなら、利用者には同じ予約に見える。しかしホテル側には、重複予約が二件できていないかが重要だ。同じ氏名、同じ日付、同じ部屋タイプでも、二件なら請求も在庫の扱いも変わる。見た目の一致を個体の一致として使うと、ここで失敗する。

反対に、予約内容を変更して日付も部屋も変わったのに、変更前と同じ予約として扱いたいこともある。その場合、現在の属性の一致からは同一性を決められない。手続きの継続や識別子に頼ることになる。同じであることは、変化がないことと同じではない。

この二方向を並べると、等価性と同一性を分ける理由がはっきりする。同じ内容でも二つあることがあり、内容が変わっても一つのものが続くことがある。`==`と`is`は、この区別を試せる便利な入口だ。ただし、予約が同じである条件は`is`にも書かれていない。それはプログラムが表す世界の側で、改めて決める必要がある。

### あえて違いを見ないという仕事

等価性を定義することは、違いを見落とすこととは限らない。目的に必要でない違いを、意識して無視する仕事でもある。配送先をまとめるときは表記揺れを吸収したいが、法的な名義を扱うときは勝手に吸収したくない。同じ比較規則をすべての画面に押し広げると、便利さが事故の原因になる。

ここで対立する二つの方針がある。対象には用途に依存しない真の同一性があるのだから、それを探すべきだという方針。そして、ソフトウェアではまず仕事に必要な等価関係を明示すべきだという方針だ。両者は必ずしも排他的ではない。現実の人間が同一であるという事実を尊重しつつ、郵便物をまとめるために別の比較規則を使うことはできる。

問題は、業務上の同一視を現実そのものの同一性と取り違えるときに生じる。データが重複しているから人を一人消してよいわけではないし、別のアカウントだから必ず別人とも言えない。

ここから見えてくるのは、「同じ」を一度定義すれば仕事が終わるのではなく、比較するたびに、何のための同じかを確認できることだ。等号は哲学への近道だが、近道にも通行条件がある。

**章末の問い**　中身を一つずつ変えていっても`is`が真のままなら、その対象はいつまで同じものなのか。次は、買い物かごを船に積み替えて考えよう。

**出典と補足**　哲学の二方向の原理は[R12](#ref-r12)、比較演算の仕様は[R13](#ref-r13)。NaNはこのコードの等値比較について述べており、コンテナの比較などすべての文脈へ機械的に一般化しない。

## 第6章　テセウスの船をプログラミングする

### 修理し終えたら別の船なのか

船の板を一枚ずつ交換する。最後の一枚まで新品になったとき、同じ船は残っているのだろうか。さらに、取り外した板を集めて別の船を組み立てたら、どちらが元の船なのか。テセウスの船と呼ばれる問いは、古い物を修理して使う人にとって、遠い知的遊戯ではない。[R14](#ref-r14)

プログラムなら、ひとまずこう決められる。

```python
ship = {"id": "T1", "parts": ["古い船首", "古い船尾"]}
alias = ship
ship["parts"][:] = ["新しい船首", "新しい船尾"]
print(ship is alias)
print(ship["id"], ship["parts"])
```

実行結果：

```text
True
T1 ['新しい船首', '新しい船尾']
```

外側の辞書は同じオブジェクトのまま、部品のリストの内容を置き換えた。私たちは同一性の一つのルールを選んだのである。哲学の問題を解いたのではないが、そのルールが何を保存するのかは観察できる。

製品の修理履歴でも、圧縮機、基板、筐体を交換してなお同じ製造番号を使うことがある。逆に、交換の範囲や契約によって新品扱いにする場合も考えられる。どの運用が実際に採用されるかは組織や制度による。番号の継続は、材料の継続とは別の基準だ。

### コピーをしたはずなのに

修理前の状態を保存しようと、船の辞書をコピーする。これで過去は安全だろうか。

```python
original = {"parts": ["木材A", "木材B"]}
shallow = original.copy()
shallow["parts"][0] = "新品"
print(original["parts"])
print(original is shallow)
print(original["parts"] is shallow["parts"])
```

実行結果：

```text
['新品', '木材B']
False
True
```

外側の辞書は別だが、中のリストを共有していた。浅いコピーは、このように内部の対象への参照を引き継ぐ。深いコピーなら、複合した構造を再帰的にコピーする方向で処理する。ただし何でも現実の独立した複製になるわけではない。ファイルや通信相手、業務上の識別子まで、望み通りに複製されるとは限らない。[R15](#ref-r15)

```python
from copy import deepcopy
original = {"parts": ["木材A", "木材B"]}
independent = deepcopy(original)
independent["parts"][0] = "新品"
print(original["parts"])
```

実行結果：

```text
['木材A', '木材B']
```

プログラム内部の複製は成功した。しかし二つのデータがどちらも同じ現実の船を表しているかもしれない。オブジェクトを増やすことは、現物を増やすこととは違う。反対に、現物が二つあっても、一つの部品仕様を共有することはある。

### 変わらない器の中で変わるもの

不変なデータを使えば、船の問題から逃れられるだろうか。たとえばタプルは要素への直接の参照列を変更できない。しかし中にリストを置けば、そのリストの内容は変えられる。

```python
record = (["旧部品"],)
record[0].append("追加部品")
print(record)
```

実行結果：

```text
(['旧部品', '追加部品'],)
```

タプル自身の構造が不変であることと、その先に到達するすべてが不変であることは違う。不変性にも境界がある。「この記録は変わりません」という約束をするなら、どこまでを記録の内部と考えるかが問題になる。

哲学でも、何が変わってよく、何が変わるとそのものではなくなるかが問われる。材料の連続性を重視すれば、取り外した板の船が有力に見える。機能や運用の連続性を重視すれば、修理されながら航海してきた船が有力に見える。物体の持続を、時間を通じた同じものの存在として考えるか、時間的な部分を持つ全体として考えるかという対立もある。[R16](#ref-r16)

ソフトウェアは、どちらの見方にも似た表現を作れる。可変オブジェクトを更新することも、各時点の不変の状態を並べることもできる。実装のしやすさは、そのまま形而上学的な正しさにはならない。

### 船を二つに増やしてみる

テセウスの船の思考実験は、全部品を交換したところで終えるより、取り外した部品を集めてもう一隻組み立てると面白くなる。修理を続けた船と、古い材料から再構成した船が並ぶ。どちらも元の船とのつながりを主張できるが、今は異なる場所に浮かぶ二隻である。

ここで「どちらも同じ船だ」と言いたくなる。しかし数的同一性として同じだと言うなら、元の船とAが同一、元の船とBも同一という二つの主張から、AとBも同一だと考える必要がある。別々に航海できる二隻を、無条件に一隻だと数えるのは難しい。日常語の「同じ船」には、材料が由来する、歴史を継承する、型が一致するなど、異なる関係が混ざっているのかもしれない。

ソフトウェアのコピーでも、似た混乱が起きる。ある設定を複製し、片方だけ修正する。最初は同じ内容だったが、その後は別の変更を受ける。もし二つのコピーに同じ識別番号を付けたままなら、後で統合するときに困る。番号の同一性が、対象の分岐という出来事を表していないからだ。

だから、複製できるもののIDには、何を同一視したいかが必要になる。製品の型を表す番号は複製品で共有してよい。現物一個を表す番号は共有すると困る。文書の内容を表す識別と、編集作業の継続を表す識別も別だ。「IDを付ければ同一性は解決する」という答えは、実は問いをIDの意味へ移したにすぎない。

このとき実務上のよい解決は、必ずしも唯一の哲学的正解を選ぶことではない。修理履歴を継承する船、材料を継承する船、所有権を継承する船を別々に記録し、必要な場面でどの関係を使うかを定めることもできる。一つの同一性へ無理に押し込むより、関係を増やしたほうが曖昧さが減る場合がある。

### 内容の指紋は、本人確認ではない

ファイルの内容が変わったかを調べるために、ハッシュ値を使うことがある。入力のバイト列から一定の長さの値を計算する仕組みだ。Pythonの`hashlib`でも、SHA-256などのダイジェストを求められる。[R42](#ref-r42)

ここで指紋という比喩は便利だが、同じ内容のファイルを二か所へコピーすれば、同じ方式のハッシュ値も同じになる。二つの保存場所が一つへ融合したわけではない。また、異なる入力が同じ有限長の値へ対応する可能性を、論理的にゼロにはできない。暗号学的に十分強い方式を適切に使うことと、数学的に衝突が不可能であることは別だ。

内容の判定にも範囲がある。改行コードや空白が違えば、バイト列としては違う。人間には同じ文章に見えても、ハッシュ値は変わりうる。逆に、内容が完全に同じ二つの契約書でも、誰がどの手続きで承認したかによって扱いが違う場合がある。内容の一致だけでは、そのファイルが担う社会的な役割は決まらない。

Gitのような履歴管理でも、ある時点の内容だけでなく、親とのつながりや変更の経緯を考える意味がある。同じ最終状態へ、異なる道筋で到達することがあるからだ。現在の樹形だけを見ても、どの枝を切って接いだかは分からない。履歴の記録は、状態のコピーには含まれない情報を追加する。

これは、履歴があればすべての同一性問題が解決するという話でもない。何を一回の変更として記録するか、どの変更を関連付けるかは設計に依存する。記録されなかった作業を、履歴管理が魔法のように発見してくれるわけではない。履歴は由来を考える証拠であって、由来そのものの完全な再現ではない。

### 交換できるのは、どこまでか

船の部品を一個交換すると同じ船でなくなる、という基準は厳しすぎるように思える。では二個ならどうか。半分ならどうか。最後の一個を交換した瞬間に別の船へ変わるのか。連続的な変更に対して鋭い境界を求めると、納得しにくい判定が現れる。

設計では、ここに制度上の境界を置くことがある。ある主要部品を交換したら新しい製造番号を与える、特定の改修範囲なら同じ製品として履歴を続ける、といった規則である。これは物理世界に最初から刻まれた境界をそのまま読み出すというより、追跡と責任分担のために決める境界だ。

もちろん、規則があるからどんな境界でもよいわけではない。安全上重要な変更を軽い修理として扱えば、必要な検査が抜ける。小さな変更ごとに別製品として扱えば、履歴が細切れになり、長期の不具合が見えにくくなる。継続性を保つ利益と、変化を明示する利益を比較しなければならない。

プログラム内のミュータブルな対象は、こうした境界を簡単に覆い隠す。属性を次々に変更しても、オブジェクトそのものは同一だからだ。だが、表される対象の意味まで連続しているとは限らない。住所を書き換えたつもりが、別人の情報へ置き換えてしまった場合、メモリ上の連続性は間違いを防がない。

イミュータブルな記録を使う設計にも課題がある。変更ごとに新しい記録を作れば、過去の状態は保存しやすい。しかし、どの記録がどの記録の続きかを表す関係が必要になる。変化を禁止して同一性問題を消したのではない。変化を、対象の内部から対象間の関係へ移したのである。

### 修理記録の余白を読む

読者が自分の自転車の修理記録を作るとしよう。タイヤ、ブレーキ、サドルを交換しても同じ自転車だと思うかもしれない。ではフレームを交換したらどうか。盗まれた後、部品だけ戻ってきたらどうか。保険、愛着、再販売、整備のどの目的で記録するかによって、必要な説明が変わる。

ここで一つの答えを急ぐ代わりに、「変化しても残るもの」を複数書いてみるとよい。所有の履歴、使用者との関係、構造、材料、登録番号。どれも継続性の候補だが、互いに一致するとは限らない。システムがそのうち一つだけを保存するなら、後で別の問いに答えられなくなる可能性がある。

テセウスの船は、古代の船大工が悩みすぎた話ではない。何を継続させ、何を新しいものとして数えるかという、更新を伴うシステムの設計課題である。コンピュータはその答えを一つに決めて動ける。しかし、決める前に複数の継続性を見ておくことが、よい実装の条件になる。

### 主キーは判決文に似ている

データベースの主キーは、行を識別するための制約を担う。しかし番号T1の行が一つあることから、T1に対応する現物が必ず一つあるとは言えない。入力ミスや複製、廃棄後の未更新がありうる。主キーは外部世界の存在証明書ではない。

それでも主キーには大きな価値がある。担当者が変わっても、同じ対象として扱い続ける判断を、システムに保持できる。これは「真の本体を発見する」働きとは違う、「同じとして扱う規則を継続する」働きだ。

Gitの履歴も興味深い。コミットはプロジェクトの木構造への参照に加え、親コミットや作成者などの情報を持つ。同じファイル内容だから同じコミット、とは限らない。状態の一致と履歴上の位置が区別される。[R17](#ref-r17)

これは製品の品質保証にも通じる。同じ設計図に見える二台でも、一台は高温試験を通過し、もう一台はまだ試験していない。目の前の状態だけでなく、そこへ至った経路が判断に関係する。

ここから見えてくるのは、同一性を「変わらない芯」にだけ求める必要がないことだ。関係と履歴の連続を管理することで、変化する対象を追跡できる。ただし履歴にも記録漏れはある。船に貼られた番号は海水で剥がれうるし、データの番号は人間の判断で誤って統合されうる。

## 第7章　オブジェクトの死――ガベージコレクションと存在の終わり

### 捨てたと思ったものが残る

片付けの難しさは、物を捨てる決断だけにはない。「いつか使う」と書かれた箱を、誰が管理するのかにもある。プログラムのメモリも、作られた対象をいつまでも全部保持してはいられない。

```python
items = ["試作品"]
archive = [items]
del items
print(archive[0])
```

実行結果：

```text
['試作品']
```

名前を一つ消しても、別の経路から参照できる。第1章の矢印の絵を広げれば、オブジェクト同士の網が見えてくる。ガベージコレクションは、その網の中で、もう利用されない対象のための領域を回収する仕組みだ。ただし、何が利用されないと判定されるか、いつ実際に回収されるかには、実装上の事情がある。

Pythonの言語仕様は、到達不能になったオブジェクトが直ちに回収されることを保証しない。CPythonの代表的な仕組みとして参照カウントと循環するごみの検出があるが、これをすべてのPython実装の法則として読んではいけない。[R04](#ref-r04)

### 互いを覚えている二人

参照カウントという考え方は直感的だ。ある対象を参照するものがなくなれば、対象を保つ必要がなくなったと判断できる。ただし互いに参照する対象では、そのままでは困る。

```python
a = []
b = [a]
a.append(b)
print(a[0] is b, b[0] is a)
del a, b
print("二つの名前を削除した")
```

実行結果：

```text
True True
二つの名前を削除した
```

二つのリストは互いを参照していた。名前を消した後も、内部の参照関係だけを数えると互いが互いを支えているように見える。しかし外から利用する経路は、この例では失われる。循環参照を検出する仕組みは、こうした構造を扱う。[R18](#ref-r18)

このコードは循環を作り、名前を消す実験である。最後の表示は「回収が完了した」という測定結果ではない。そのような断言を加えるには、実装に依存する観測や追加の条件が必要になる。

誰かが誰かを覚えている限り存在は続く、という詩的な比喩を作ることはできる。しかしGCは記憶や死についての哲学を実装したものではない。ここでの参照は機械の操作可能性に関わる関係であり、人間の追悼や人格の持続とは違う。似た言葉に心を動かされることと、同じ理論を認めることは別である。

### 到達できるが、二度と使わない

逆の問題もある。巨大なリストをキャッシュに保存したまま、二度と読み出さないプログラムを考えよう。そこへ到達する経路は残っている。回収機構から見れば、将来使われうる。しかし設計者から見れば、不要なデータだ。

「到達できる」と「役に立つ」は同じではない。一般的な回収機構は、業務の目的を理解して、古い試作品の情報を捨ててくれるわけではない。機械が判定できる構造的な条件と、人が望む意味上の条件には隙間がある。

この隙間を狭めるために、キャッシュの上限や有効期限を設ける。すると今度は、古いが重要なデータを消す危険が出る。何を保持し、何を失ってよいかという設計判断は、自動化した後も残る。

### 生きているが、もう使わない

ある関数が結果を計算し、その結果を一覧へ追加する。開発中には、過去の計算を全部見られるので便利だった。ところが本番では、その一覧を誰も読まない。それでもプログラムは毎回結果を追加する。一覧へ届く参照が残っている限り、その要素も到達可能であり続ける。

ガベージコレクションの仕事は、プログラマが後で役に立つと思うかを判断することではない。言語と処理系が採用した仕組みに従って、不要になった記憶領域を回収できるようにすることだ。到達可能だが意味のある利用はされない対象まで、自動的に処分してくれるとは限らない。プログラムの意図を知らずに、その判断をするのは難しい。

このため、自動回収がある言語でも、保持し続けるデータが増えてメモリを圧迫する問題は起きる。日常語でメモリリークと呼ばれる状況の中には、参照が失われているからではなく、逆に参照を保ちすぎているから起きるものがある。回収機構を強化するだけでは直らず、一覧の長さを制限する、古い結果を削除する、保存先を分けるといった設計が必要になる。

これは、倉庫の鍵を捨てた荷物と、鍵はあるが誰も必要としない荷物の差に似ている。前者は到達できない。後者は到達できるが用途がない。機械にとって分かりやすい条件と、人間にとって重要な条件は一致しない。自動化が進むほど、どちらを自動で判定しているのかを確かめる必要がある。

キャッシュにも同じ問題がある。計算を繰り返さないために結果を保存するのは有益だが、保存することで対象の寿命が伸びる。速さを得るために、いつまで何を生かすかを決めているのである。効率化は単なる速度の話ではなく、記憶の保持方針でもある。

### 観察者も、世界に手を加える

対象を調べたいので、別の変数に入れておく。ログのために、対象そのものを一覧へ保存する。このような観察用の処理が、対象への参照を増やすことがある。調べなければ不要になったはずの対象が、調べる仕組みによって保持され続ける。

ここで量子力学の観測問題へ飛ぶ必要はない。これはもっと素朴な、観察のために追加したプログラムもプログラムの一部だという話である。デバッグ用の道具が実行時間を変え、参照関係を変え、記録量を変えることがある。測定を行うコードを世界の外に置いたつもりでも、現実には同じ資源を使っている。

もちろん、それなら観察できないという結論にはならない。対象そのものを保存する代わりに、必要な小さな情報だけを書き出す方法もある。ただしコピーした情報にも寿命があるし、対象の一部分しか残さなければ、後から確認できない性質が出る。何を保存し、何を捨てるかという問題は、観測にもついて回る。

たとえば注文の不具合を調べるために、注文オブジェクトをすべて保持する方法と、注文番号、状態、変更時刻だけを記録する方法を比べよう。前者は細かく調べやすいが重い。後者は軽いが、記録しなかった情報について答えられない。どちらがよいかは、知りたいことと許容できる費用による。

ここでも、記録が存在することと、元の対象が生き続けることを分けたい。写真が残っていても、撮影された物体がそのまま残っているとは限らない。逆に元の対象が変化しても、過去の記録は変わらず残る場合がある。オブジェクトの寿命を考えるとき、複製された表現の寿命まで混ぜると、何が消えたのか分からなくなる。

### 消滅と、約束の終了

ファイル、通信接続、データベースのトランザクションのように、単にメモリへ置かれた値では済まない対象がある。ファイルを開くことは、外部資源との関係を作る。対象が不要になったことと、その関係をいつ終了すべきかは別の問いである。

たとえば、ファイルへ書いたデータを読みたい別の処理が待っているなら、いつ書き込みを終えて閉じるかを明示する意味がある。対象がいつ回収されるかに期待するより、処理の区間を定め、その区間を出るときに後始末する設計のほうが意図を表しやすい。Pythonの`with`は、そのような管理を記述する仕組みである。ただし、何を終了時に行うかは個々のコンテキストマネージャーに依存する。

ここで「死」の比喩には限界が見える。オブジェクトには、生物のような代謝があるとは限らない。役割を終えたが参照されている対象、閉じた資源の状態を表す対象、外部資源は続いているが表現だけ捨てられた場合がある。すべてを生と死の二択にすれば、実務上の大事な違いが消える。

だから対象の設計には、生成と破棄だけでなく、利用可能、処理中、終了済みなどの状態を持たせる場合がある。終わった対象がまだあることは矛盾ではない。閉店した店の記録が存在しても、その店で買い物できるわけではないのと同じだ。存在と利用可能性を分けると、後始末の仕様も書きやすくなる。

### 忘れる能力を設計する

すべての過去を残すシステムは賢そうに見える。しかし有限の資源で動く限り、何をいつ忘れるかを考えなければならない。永久保存を約束することも、一つの費用と運用上の責任を引き受けることである。

直近の百件だけ残すという規則を選べば、百一件目が来ると古い情報が消える。経過時間で削除するなら、時計と削除処理に依存する。集計だけ残して個別データを捨てれば、傾向は見えても個別の経緯は追えない。どの方式も、未来のどんな質問へ答えられるかを変える。

読者が一日の行動記録を作るなら、何を残すだろうか。時刻と場所だけでは、何を考えていたかは分からない。すべての発言を書き起こしても、理解した意味を完全には保存できない。ソフトウェアの記録も同じで、情報量を増やすことと、未来に必要な説明を保存することは一致しない。

ガベージコレクションは、この広い忘却の問題の一部を技術的に扱う。対象の価値を判定する哲学者でも、あらゆる証拠を保管する歴史家でもない。仕事の範囲を限定しているからこそ、実用的な仕組みとして成立する。機械が忘れてくれる部分と、設計者が忘れ方を決める部分を区別することが、安定した世界を作る第一歩になる。

### オブジェクトの寿命と資源の寿命

ファイルを開いた対象が回収されるまで待つ、という書き方は避けたい。ファイルや通信接続には、メモリとは別の資源としての寿命がある。そこで、使う範囲を明示する。

```python
from io import StringIO
with StringIO("記録") as stream:
    print(stream.read())
print(stream.closed)
```

実行結果：

```text
記録
True
```

この例ではメモリ上の文字列ストリームを使った。`with`の範囲を出ると閉じられ、なお名前`stream`からオブジェクト自体は参照できる。つまり「閉じた」と「存在しなくなった」さえ違う。対象が利用可能な状態を終えることと、その対象を表すオブジェクトの寿命は分離できる。[R19](#ref-r19)

業務でも、退役した装置の記録を削除する必要はない。稼働する資格は失っても、監査対象としては残る。反対に、画面から消しただけでは、バックアップや別の記録まで消えたとは言えない。消滅には水準がある。

物理的なビットが残っているか、言語上のオブジェクトとして使えるか、対象を再構成できるか、社会的に同じものとして認めるか。それぞれ別の質問だ。読み出せない媒体に痕跡があることから、実用上のデータが存在すると言い切れないし、現在のプロセスにないことから、世界のどこにも情報がないとは言えない。

ここから見えてくるのは、オブジェクトの死が、一つの瞬間に起きる単一の出来事とは限らないことだ。回収、資源の解放、履歴の廃棄、現物の消滅を、同じ「削除」ボタンの下に隠すと、設計は読みやすくなっても現実は難しくなる。

**章末の問い**　参照できる対象があるとして、その対象を使えば何かが起きるのはなぜだろうか。次の部では、ものから作用へ、存在から原因へ進む。

## 第8章　関数とは因果関係なのか

### 温度計を温めれば部屋も暖まるか

暖かい日には、温度計の表示が高い。データを集めれば、表示と室温の間に強い関係が見えるだろう。それなら表示だけを書き換えれば、部屋は暖まるのか。冬の朝にそんな暖房があれば、電力会社は困り、利用者は喜ぶ。しかし普通は何も起きない。

関係を計算できることと、現実をその関係に沿って変えられることは違う。関数を因果関係と呼ぶ前に、この違いを押さえたい。

```python
def sensor(room_temperature):
    return room_temperature + 1  # 仮定した校正ずれ

room = 20
reading = sensor(room)
reading = 30
print(room, reading)
```

実行結果：

```text
20 30
```

表示値を表す名前を別の数へ結び直しても、`room`は変わらない。このコードが示すのは、私たちが書いた依存関係である。現実の温度計の機構を実験によって証明したわけではない。現実に適用するなら、センサーが何を検出し、どのように熱交換するかを別途確かめる必要がある。

### 数学の対応と、実行される手続き

数学の関数は、定義域の各要素に対応する値を定めるものとして扱える。`f(x) = x + 1`という関係自体は、毎朝電源を入れなくても考えられる。一方、プログラムの関数は呼び出されて動作する。結果を返すほか、ファイルを書いたり、リストを変更したり、終了しなかったりする。

```python
def add_one(number):
    return number + 1

def register(log, message):
    log.append(message)
    return len(log)

history = []
print(add_one(3), add_one(3))
print(register(history, "起動"))
print(register(history, "起動"))
```

実行結果：

```text
4 4
1
2
```

前者は同じ数に同じ結果を返す。後者は渡されたリストを変更するので、同じ名前を引数として繰り返し呼んでも結果が変わる。副作用とは、関数名の印象が悪いという意味ではない。戻り値以外に、観測できる状態の変化があるということだ。

状態を明示的な入力と出力に含めれば、副作用のある処理も数学的に記述できる。たとえば「入力と以前の状態」から「出力と新しい状態」への対応として考える。数学の関数とプログラムの関数を区別することは、両者に橋がないという意味ではない。何を入力に含めたのかを明らかにする必要がある、という意味である。

反事実的な因果の考え方は、「それがなかったら、結果はどうなっていたか」に注目する。これは有力な入口だが、単純な一文だけですべての原因を説明できるわけではない。たとえば二つの独立した加熱装置が、どちらも単独で目標温度に達するほど強ければ、片方を除いても結果が変わらない場合がある。それでも片方が何も作用しなかったとは限らない。[R20](#ref-r20)

因果を規則的な共起として捉えようとする方向と、介入や反事実によって捉えようとする方向では、説明に必要なものが変わる。本書の小さな関数は、それらの違いを試す模型にはなる。しかし、関数に`cause`という名前を付けても、因果関係の認定は完了しない。

### 決定されていることと、予測できること

決定論的な手続きでも、結果を知るために長い計算が必要な場合がある。初期状態を十分に知らなければ予測できないこともある。入力、外部環境、実行の順序をどこまで固定するかによって、「同じプログラムなら同じ結果」の意味も変わる。

ここから自由意志へ直行したくなる。人間の判断が何らかの法則に従うなら、選択は幻想なのか。だが、決定論と自由意志の両立を認める立場も、認めない立場もある。自分の理由や望みに応じて行動することを重視する見方と、同じ過去と法則のもとでも本当に別の選択ができることを求める見方では、争点が異なる。[R21](#ref-r21)

乱数を一つ入れれば自由意志が生まれる、という解決も早すぎる。サイコロで行動が変わることと、行為者が理由を理解して選ぶことは同じではない。逆に、理由に整合的に従うことを、単に機械的だからという理由だけで自由から排除するのも、すでに一つの立場を選んでいる。

プログラムの決定性は、自由意志についての問いを整理する助けにはなる。しかし人間を数行の関数と同一視する根拠にはならない。説明の成功を、対象の取り替えと混同してはいけない。

### 条件をそろえるとは、何を切り離すことか

新しい断熱材を使った試作品が、以前の製品より冷めにくかったとする。そこで、断熱材の効果を確認できたと言いたい。しかし試作品では容器の形も変わり、室温も違い、水の量も増えていたなら、観測した差をどの変更へ帰属させればよいのか。

実験で条件をそろえるのは、比較を退屈にするためではない。変えたい要因と、他の変化が混ざるのを減らすためだ。数式へ入れた入力の一つだけを書き換えるのは簡単だが、現物の一要因だけを変えるのは難しい。厚い断熱材へ交換すれば外形も変わり、固定方法も変わるかもしれない。介入は、ソフトウェアの代入のようにきれいな一行とは限らない。

介入による因果の考え方では、対象の変数を変え、結果への影響を他の経路と区別できるようにすることが重要になる。このとき、人が操作できるものだけが原因だと限定する必要はない。人間が実際に変更できない事柄についても、適切な介入を仮定した問いは考えられる。ただし、どんな介入が意味を持つかは無条件に決まらない。[R40](#ref-r40)

この発想を小さな模型に移そう。室温が上がると二つのセンサーの表示が上がるとする。一方の表示だけを30へ固定しても、もう一方は変わらない。しかし室温を30へ変えれば、両方が変わる。観測上は似た値でも、どの生成過程を置き換えたかで結果が違う。単にデータを絞り込んで「表示が30だった行」を選ぶことと、表示を強制的に30へ設定することも同じではない。

だから因果モデルには、方程式の数値関係だけでなく、それぞれの式をどんな仕組みとして解釈し、どの式を変更しても他が保たれると考えるかが含まれる。代数的に同値な式へ変形できることだけでは、その介入の意味は保存されない。計算式を解けたことと、現実の操作を理解したことの差がここにある。

### 予測に成功しても、修理に失敗する

ある機械で、異常音が出ると故障が近いと分かった。予測器としては役に立つ。では、音を消せば故障も防げるだろうか。防音材で外へ聞こえにくくしても、内部の摩耗は進み続けるかもしれない。音が故障の原因ではなく、同じ損傷から生じる兆候なら、音を消す操作は原因への対策にならない。

この例は、予測モデルの価値を否定するものではない。早期警報だけでも十分な利益がある。問題になるのは、予測に役立った変数を、操作すれば結果を変えられる変数だと読み替えることだ。故障予測と故障対策は関連するが、同じ課題ではない。

プログラムでは、両者が同じ`predict`という関数の出力から語られやすい。入力値を少し変えて出力が減ったので、その入力に対応する現実の量を変えれば改善すると考える。しかし、その値を現実に変える方法が他の量も動かすなら、関数内だけの変更と一致しない。模型のスライダーは、現実のつまみの所在を保証しない。

ここで読者に小さな設計課題を出そう。機械の故障を減らすために、温度、異常音、稼働時間の記録がある。どのデータを増やし、どんな比較試験をすれば、予測の相関から修理の手がかりへ進めるだろうか。唯一の正解を当てる課題ではない。どんな説明なら代わりの原因を区別できるかを考える課題である。

よいモデルは、問いに答えるだけでなく、まだ答えるために足りない観察を教えてくれる。プログラミングを形而上学の実験装置として使う利点は、この不足を具体的な形へできることにもある。

### 理由に従うことは、不自由なのか

自由意志を考えるとき、法則に従うことと、強制されることをすぐ同じにしないほうがよい。雨が降っているから傘を持つ場合と、脅されて傘を持たされる場合では、どちらにも原因がある。それでも行為の扱いを変えたい理由がある。

両立論の中には、行為が原因を持たないことより、行為者が理由に応答できることや、自分の意思に基づいて動くことを重視する方向がある。晴れていれば傘を置き、雨なら持つ。新しい情報を理解すれば判断を変える。こうした能力を自由に関係するものとして考えるのである。ただし両立論は一枚岩ではなく、別の選択の可能性をどう扱うかにも違いがある。[R39](#ref-r39)

ここで「それなら条件分岐にも自由意志があるのか」と反論したくなる。だが、簡単な分岐にも入力への応答があることから、人間の理由理解に必要な条件をすべて満たすとは言えない。理由を評価し、別の場面へ適用し、自分の行動を説明し、長期の計画と調整する能力など、どこまで含めるかが問題になる。

逆に、単純な分岐では足りないからといって、原因に従う仕組みはどれほど複雑でも自由に関係しないと結論するのも早い。そこには、自由は因果的な説明の外になければならないという追加の前提がある。議論の争点を明示すると、プログラムを見てすぐ自由を認めたり否定したりする近道が、どちらも危ういと分かる。

非両立論側からは、それでも行為者自身がその性格や理由の重みを究極的に作ったわけではない、という疑問が出る。過去と法則によって判断が決まるなら、本当に自分が源なのか。両立論側は、そのような究極的な自己創造を自由の条件にする必要があるのかと問い返せる。この対立は、ランダムな数を一つ加えるだけでは片付かない。

### 編集された選択を、自分のものと呼べるか

もう一段難しくしてみよう。人が理由を理解し、自分で望んだと感じながら行動しているとしても、その望みを他者が密かに作り替えたならどうだろうか。外形だけ見れば自発的でも、形成の経緯が気になる。自由を現在の内部構造だけで評価してよいかという問題である。

両立論をめぐる操作・洗脳の反論は、このような来歴への疑問を強調する。理由へ応答する仕組みがあることと、その仕組みを自分の行為の基盤として引き受けられることは同じか。普通の学習や社会的影響と、自由を損なう操作の境界をどこへ置くかも難しい。[R39](#ref-r39)

プログラムの設定値を外部から変える場合を、人間の選択へそのまま当てはめることはできない。しかし、その模型から問いを作ることはできる。現在の出力だけを見れば同じ二つの仕組みでも、一方は利用者が設定を確認でき、取り消せる。他方は設定が隠され、変更できない。制御の所在を考えるなら、この違いは無視しにくい。

ここで本書が持ち帰りたいのは、自由意志の最終判決ではない。決定性、予測可能性、理由への応答、外からの強制、形成の履歴、責任の帰属は、分けて問えるということだ。機械が決定的に動くという一つの性質から、これらのすべてを一度に決めることはできない。

考えが精密になるほど、結論が遠くなるように見えるかもしれない。しかし、論点が見えることは前進である。プログラミングの模型が最も役に立つのは、人間への判決を代行するときではなく、どの性質を比べているのかを明らかにするときなのだ。

### 設計者が書いた矢印の外側

ヒーター制御を作るとき、温度を入力、出力電力を結果として関数を書く。現実ではその出力電力が温度へ戻り、次の入力を変える。プログラムの関数一回を見ているだけでは、閉じたループの一部しか見えない。

ここから見えてくるのは、原因を語るためには関数の式だけでなく、何が観測され、どこに介入し、どの時間幅で変化を見るかを指定しなければならないことだ。入力と出力の箱を描くのは簡単だが、どちら側に現実を置いたかで物語は変わる。

**章末の問い**　同じ関数をもう一度呼ぶとき、その「もう一度」はどこに保存されているのか。数学の関係を動かすために、時間は何を付け加えるのだろうか。

## 第9章　時間のない世界、時間のある世界

### 残高だけでは昨日が分からない

口座の残高が5000円だと分かったとする。最初から5000円あったのか。10000円から5000円を使ったのか。借りた金を入れたのか。現在の数字だけでは、過去は一意に決まらない。

在庫でも同じだ。現在5台あることと、なぜ5台になったかは別の情報である。そこで、変化を出来事として記録する。

```python
events = [("入庫", 10), ("出庫", 3), ("出庫", 2)]

def replay(records):
    stock = 0
    for kind, amount in records:
        stock += amount if kind == "入庫" else -amount
    return stock

print(replay(events[:2]))
print(replay(events))
```

実行結果：

```text
7
5
```

最初の二つの出来事までを適用すると7、全部なら5だ。ここでは入力を既知の二種類に限定している。未知の種類を出庫扱いするこの簡略化を、本番の在庫管理へ持ち込んではいけない。

イベントソーシングは、状態変更を出来事の列として保持し、それを適用して状態を得る設計だ。単に「ログを少し残す」のとは違い、状態の変化を記録された出来事から再構成できることが重要になる。[R22](#ref-r22)

### 過去を保存したという言い方

このプログラムは過去へ戻ったのだろうか。もちろん、倉庫で一度出荷した製品が、画面の再生に合わせて配送車から逆流するわけではない。復元したのは、記録された出来事に基づく状態の表現だ。

しかも再現には条件がある。出来事が漏れていないこと。適用する規則が分かること。外部の価格や時刻に依存した計算なら、その値も再現できること。同じログに現在の為替レートを使えば、過去の金額を別の値へ書き換えてしまうかもしれない。

ログは過去そのものではなく、現在存在する過去についての記録である。この区別は歴史学にも品質保証にも重要だ。試験結果のファイルがあることと、当時その条件で試験が行われたことには、証拠としての橋が必要になる。

### 数式の中の時刻と、計算にかかる時間

「数学の式には時間がない」とは、数式に`t`を書けないという意味ではない。温度を`T(t)`と書けば時間変化を表せる。言いたいのは、数学的な関係それ自体が、コンピュータの秒針に合わせて順番に成立するわけではないということだ。

一方、数値計算の実行には物理的な時間がかかる。シミュレーションの一秒を計算するのに、現実には一時間かかる場合もある。モデル内の時間、計算機の実行時間、結果を読む人の時間は別々に進む。

この分離は、ソフトウェアの自由さの源である。過去を再生し、未来を予測し、途中の状態で停止できる。しかし、シミュレーション内の一日を飛ばしても、計算機が経験した物理的な時間を飛ばしたわけではない。早送りのボタンを作れることは、時間旅行の装置を作ったことではない。

### 現在だけがあるのか

時間の哲学には、現在だけが存在するという現在主義と、過去・現在・未来の対象を含めて存在を考える永久主義がある。過去と現在を認め、未来をまだ存在しないとする成長ブロック的な見方もある。さらに時間の流れをどう理解するか、変化する対象がどう持続するかが争われる。[R16](#ref-r16)

現在の状態だけを持つプログラムは現在主義に、全時点の状態を並べたデータは永久主義に似て見える。だが、それは表現上の類似である。現在主義者でも古い記録を保存できるし、永久主義者でもメモリを節約するために現在の状態だけを保持できる。

画面に過去の状態が表示されていることと、過去の出来事が現在の出来事と同じ仕方で存在することは違う。ここを混同すると、タイムラインを持つアプリを作っただけで、時間の形而上学に勝利したことになってしまう。

それでもプログラムは思考実験として役立つ。状態だけの設計では説明できない問いがあり、履歴を加えると答えられる。それによって、私たちが「いま」を理解するとき、どれほど過去の情報に頼っているかが見える。

### 知った時刻と、起きた時刻

月曜日に部品を受け取り、水曜日に入庫記録を入力したとする。金曜日になって、受領日は火曜日の間違いだったと分かった。ここで「在庫はいつ増えたのか」という問いには、少なくとも二種類の答えがある。現場で増えたと考える時点と、システムがそのことを知った時点だ。

日付の項目を一つだけ作れば、どちらかを選ぶ必要がある。火曜日へ訂正して上書きすると、水曜日には月曜日の入庫だと理解していたという過去の知識状態が消える。水曜日のまま残せば、現物が倉庫へ来た時期についての説明が不正確になる。違う時間を一つの欄へ入れたことが、訂正の難しさとして現れる。

そこで、出来事が有効だった時期と、記録された時期を別に持たせる方法がある。さらに訂正前の記録を保存すれば、過去のある日に何が分かっていたかを再構成しやすい。ただし記録項目を増やせば自動的に過去が復元できるわけではない。どの変更がどの記録を訂正したのかという関係も必要になる。

この区別は、時間を宇宙の時計の一列として扱うだけでは見えにくい。私たちは出来事の中にいると同時に、出来事について遅れて知る。システムも同じで、外部から届く情報は遅れたり、訂正されたりする。世界の時間と、世界を記述する活動の時間が重なっているのである。

読者が昨日の出来事を日記へ書くときも、今日の知識が混ざる。後から分かった事情を、当時すでに知っていたように書けば、記録の性質が変わる。データベースに時刻を入れることは、単なる数字の付加ではない。何の時間を表しているのかを選ぶことだ。

### 再生すれば、同じ現在へ戻れるか

イベントを順番に保存しておけば、過去から現在まで再生できる。だが、再生に使う規則が変わったらどうなるだろう。以前は一件の注文につき送料を一度加算し、現在は商品ごとに加算する。過去のイベントを現在の規則で読み直せば、当時と違う合計が出るかもしれない。

これはイベントの保存が無駄だという意味ではない。イベントだけでなく、その意味を解釈する規則も考える必要があるということだ。イベントに当時決まった金額を含めるのか、金額を計算する条件だけ保存するのか。規則の版を持たせるのか。何を後から再計算したいのかによって、適切な記録が変わる。

外部情報への依存も問題になる。再生時に現在の為替や現在の在庫を読み込めば、同じイベント列から同じ結果が出るとは限らない。当時使った外部値を記録しておくか、再現の対象から外すかを決める必要がある。過去を再生するボタンは、過去の世界全体へ接続する入口ではない。

さらに、再生の途中で実際のメール送信や決済をもう一度行ってはいけない場合がある。状態を復元するための計算と、外部世界へ新しく作用する処理を分けることが重要になる。同じ手続きをもう一度実行することと、過去を理解することは違うのだ。イベントソーシングの説明でも、再生と外部システムへの作用の区別は重要な論点になる。[R22](#ref-r22)

こうして見ると、記録とは時間を容器へ閉じ込める技術ではない。後から必要な問いに答えられるよう、出来事の一部を選んで残す技術である。保存量の多さより、どんな再構成を可能にするかが設計の中心になる。

### 元へ戻すことは、時間を戻すことか

画面の「取り消す」ボタンを押すと、文字が消える。まるで時間が逆向きに進んだように見える。しかし、その操作自体は現在に起きている。前の状態を保存して読み戻したり、直前の操作を打ち消す変更を追加したりしているのであって、物理的な過去を消したわけではない。

この違いは、外部の作用があると明白になる。誤って送った荷物を取り戻しても、発送のために使った時間や運搬の過程はなかったことにならない。誤請求を返金しても、請求と返金の二つの出来事がある。最終残高が元と同じことと、履歴が同じことは別である。

そこで設計では、元の状態へ巻き戻す処理と、逆向きの効果を持つ新しい処理を区別したい。編集途中のメモリなら巻き戻しやすくても、他者がすでに読んだ情報や、外部へ出した作用は同じようには扱えない。「取り消し可能」の意味は、その操作がどこまで届いたかに依存する。

この点は、数学的に逆関数があるかという問題とも一致しない。計算上の状態を一意に戻せるとしても、現実の実行で発生した熱や待ち時間まで元へ戻るわけではない。逆に、細かな過去を復元できなくても、業務上必要な補償を行える場合はある。可逆性にも、計算、記録、実務、物理という異なる層がある。

### 現在だけがあるという考えの強さ

現在主義に魅力があるのは、私たちが実際に行為できるのが現在だからだ。昨日の食事を今から変更することはできず、明日の空腹を今すぐ体験することもできない。その切実な非対称性から、存在するものは現在にあるものだけだと考えたくなる。

一方、過去の出来事について真偽のあることを語り、未来を含む時空の関係を一つの構造として記述することにも理由がある。永久主義は、過去や未来の出来事も現在と同じ意味で存在すると捉える方向の立場である。そこでは、私たちが現在からしか経験できないことと、何が存在するかを区別する。[R16](#ref-r16)

プログラムの履歴をすべて保存したことから永久主義が正しいとは言えない。現在の記憶装置に、過去を表す記録があるだけかもしれない。逆に最新状態だけを残す設計を選んでも、現在主義の証明にはならない。データの削除方針と、時間についての形而上学的主張は違う。

それでも両者を比較する価値はある。記録の中の「今」は、表示位置を動かせば変わる。では、経験される現在の特別さは、単なる位置の違いとして説明できるのか。それとも追加の何かが必要なのか。コンピュータはこの問いの模型を作れるが、表示中のフレームがあることだけで、時間の流れを説明したことにはならない。

「現在」を一つの時刻値へ変えたとき、何が残り、何が消えたかを確かめる。これがプログラミングから時間の哲学へ進む、慎重だが豊かな道になる。

### 二つの「いつ」

製品が故障した日と、故障がシステムへ登録された日は違う場合がある。訂正された記録についても、「事実が有効だった時刻」と「私たちがそれを知った時刻」を分けて考えたい。

たとえば先月の出荷数を尋ねるとき、現在分かっている訂正を反映した値が欲しいのか、先月末に担当者が見ていた値が欲しいのか。両方とも正当な質問だ。これを一つの更新日時だけで処理すると、数字の食い違いが誰かの嘘に見えてしまう。

時間の設計は、単に日時を一列追加することではない。どの変化が現実の変化で、どの変化が知識の更新なのかを分ける仕事である。これは本書がプログラミングから引き出す独自の観点であり、特定の時間論を証明する議論ではない。

ここから見えてくるのは、履歴を残すと過去が完全になるのではなく、「過去についての現在の知識」というもう一つの時間が現れることだ。

**章末の問い**　二つの倉庫から同時に更新が届いたとき、どちらを先に適用すべきだろうか。そもそも「先」は、すべての出来事の間に必ずあるのだろうか。

**出典と補足**　イベントソーシングの基本は[R22](#ref-r22)、時間の存在論の対立は[R16](#ref-r16)。二つの時刻を分ける在庫・故障の例は本書の設計上の考察である。

## 第10章　並行処理が壊す「出来事の順番」

### 二人とも正しく一を足した

共有のカウンターが0で、二人が一回ずつ1を加える。答えは2のはずだ。ところが、二人がともに最初の0を読み、それぞれ1を書き戻すと、最後は1になる。

実際のスレッドを動かして偶然この現象が起きるのを待つ代わりに、読みと書きの交錯を明示しよう。

```python
counter = 0
read_a = counter
read_b = counter
counter = read_a + 1
counter = read_b + 1
print(counter)
```

実行結果：

```text
1
```

これは競合の構造を示す逐次的な模型である。特定のPython処理系で特定の一行が必ず分割実行される、と主張しているのではない。読み、計算、書き戻しを一つの不可分な操作として保護しなければ、こうした順序が許されるシステムでは更新が失われうる。

ロックなどで必要な区間を保護する方法も、共有更新そのものを減らす方法もある。どの処理系でどの保証があるかを確認せず、「GILがあるから共有データは安全」と考えるのは危うい。言語、実装、ライブラリ、外部資源それぞれの保証は同じではない。

### 世界に一つの時計を置きたくなる

全員が同じ時計を見れば順番は分かる、と考えたくなる。しかし分散した計算機の時計はずれる。メッセージも遅れる。時刻を付けた順と、別の計算機が受け取る順が一致するとは限らない。

Lamportは1978年の論文で、物理時計に先立って出来事の順序を考える方法を示した。同じプロセスでの順序、メッセージの送信から受信への順序、それらをつないだ推移的な順序によって、happened-beforeという関係を定める。[R23](#ref-r23)

一方からもう一方へ、この関係の道がない出来事同士は並行と呼ばれる。ここでの並行は、世界共通の時計でまったく同じ瞬間に起きたという意味ではない。モデルが捉える情報の流れによって、前後が結ばれていないという意味である。

図3では、Aの送信がBの受信に先行する。Cの独立した出来事は、この通信だけではAやBの出来事と順序付けられない。絵の紙面上で上にあるから、先だとは限らない。

### 論理時計は時間を測らない

単純な論理時計を、整数のカウンターで表せる。自分の出来事で増やし、メッセージ受信時には、自分の値と受け取った値の大きいほうより先へ進める。

```python
clock_a = 0
clock_b = 0
clock_a += 1
sent = clock_a
clock_b = max(clock_b, sent) + 1
print(sent, clock_b)
print(sent < clock_b)
```

実行結果：

```text
1 2
True
```

適切な更新規則を使えば、aがbにhappened-beforeで先行するとき、時計の値も小さくなる。しかし逆は一般には成り立たない。時計の数値が小さいからといって、aがbの原因だったとは言えない。関係のない二つの出来事にも、たまたま1と2が割り当てられうる。

この非対称性は重要だ。温度計の値を並べると時間の履歴が得られた気になるのと同じく、番号を並べると因果の履歴が得られた気になりやすい。数字の大小は、数字に何を保存する規則を与えたか以上のことを語らない。

### 正しい時計を買えば解決するか

二台のコンピュータで処理の順番が分からないなら、よい時計を付ければよいと思うかもしれない。時刻の同期は重要であり、多くの実務で役立つ。しかし、記録された時刻が正確であることと、二つの処理の間にどの情報が伝わったかは別である。

Aが注文を受け付け、Bが在庫を引き当てるとする。BがAからの注文情報を受け取って処理したなら、受信という関係から先行が分かる。一方、AとCが互いに通信せず、それぞれ別の注文を受け付けた場合、時刻順に並べられても、一方が他方を知っていたとは言えない。記録の一列化と、情報の依存関係は違う。

物理時刻の誤差が小さくなっても、この区別は消えない。逆に時計の精度が足りなくても、メッセージを送ってから受け取るという関係は利用できる。Lamportの論理時計は、このような先行関係に整合する数を与える道具である。数が小さいから必ず因果的に先行した、と逆向きに読むと誤る。[R23](#ref-r23)

ここで因果という語にも注意がいる。分散計算で扱う情報の先行関係を、現実のすべての原因についての定義として使うわけではない。モデルに含めていない電源障害が二台へ同時に影響するかもしれない。モデル内の通信から分かる順序と、物理世界の原因全体を区別しておきたい。

### 最後の一席を、二人が買う

残り一席の座席表を二人が同時に見る。両方の画面に「空席あり」と出る。二人が購入ボタンを押す。各処理を単独で読むと、空席を確認してから予約するという自然な手順になっている。それでも二重予約が起こりうる。

問題は、確認と確保の間に他の処理が入れることだ。「見た時点では空いていた」と「自分のために確保した」は別の事実である。確認した状態が、その後の変更まで保たれる仕組みがなければ、最初の情報へ依存した判断は古くなりうる。

対策として、確認と確保を一つの分割されない操作として扱う、変更時に状態が変わっていないか再確認する、競合した一方を失敗させてやり直す、といった方向がある。それぞれ、待ち時間、失敗時の処理、処理量などの違いを持つ。哲学的な「真の同時性」の答えを待たずに、破ってはいけない条件を守る規則を作ることはできる。

ただし、どの順番に並べるかを決めたことと、唯一の自然な順番を発見したことは違う。受け付けた順、確定した順、優先順位順のどれを採用するかは制度の選択でもある。ソフトウェアが順番を決めると、その判断が機械の客観性をまとって見える。しかし実際には、何を公平と考えるかを設計へ織り込んでいる。

この例では、二人の利用者の行為を物理的な細部まで一列に並べる必要はない。同じ座席を二人へ確定しない、という必要な性質を保証したいのである。世界の完全な時間順序を求めるより、保証する関係を限定したほうが、実用的な解決へ近づく。

### 返事がないのは、失敗したからか

相手へ予約の依頼を送り、返事が来ない。処理が失敗したのか、成功したが返事だけ遅れているのか、相手がまだ処理しているのか。通信の遅れに上限を仮定しないなら、待ち時間だけからこれらを確実には区別できない。

タイムアウトは、その不確実性を消す装置ではない。これ以上待たずに、現在の側で次の対応へ進むという規則である。タイムアウトしたから相手では何も起きていない、と考えて再実行すると、二重の作用が生じる場合がある。

そこで、依頼ごとに識別子を付け、同じ依頼の再送なのか新しい依頼なのかを受信側で区別する設計が役に立つ。だが、その識別子をどこまで保存するか、処理結果の記録と実際の作用をどう結び付けるかという次の問題が出る。一つの番号だけで分散システムの難問が消えるわけではない。

ここに、単一のプログラムの実行順序だけを見ていたときには目立たなかった知識の問題がある。各参加者は、全体の状態をそのまま見ているわけではない。自分が送ったこと、受け取ったこと、まだ受け取っていないことから判断する。何が起きたかと、誰がそれを知っているかが、設計の別々の対象になる。

読者同士でこの状況を試すなら、紙の依頼書を渡し、返事を故意に遅らせてみればよい。返事がない側は不安になり、二枚目を書きたくなる。機械も、ここで勝手に全知になることはない。相手の沈黙をどう扱うかという規則が必要なのである。

### 同期には、失う自由もある

処理をすべて順番に並べ、一つが終わるまで次を始めなければ、考えやすくなる。しかし、互いに無関係な仕事まで待たされるなら効率が落ちる。一方、自由に同時実行すれば、共有する状態をめぐる競合が増える。同期は秩序を得るために、許される並び方を減らす操作でもある。

ここで大切なのは、同期を多くすれば常によいと考えないことだ。ある処理が鍵を持ったまま、別の鍵を待つ。相手も逆の鍵を待っていれば、双方が進めなくなる構造を作れる。誰も規則違反をしていないのに、組合せとして停止する。局所的に礼儀正しい登場人物だけで、全体が働くとは限らない。

逆に、共有しなくてよい情報を分け、各々が自分の状態だけを更新するようにすれば、複雑な同期を減らせる場合がある。順序を厳しく管理することだけが解決ではない。順序が問題になる接点そのものを少なくする設計もある。

並行処理は、私たちが当然だと思っていた「まず世界の現在が一つあり、全員がそれを見る」という図を崩す。必要になるのは、部分的な知識から矛盾を避け、必要な合意を作る方法だ。これは時計の精度だけの問題でも、哲学だけの問題でもない。何を共有し、何を別々に進めてよいかを定める、具体的な世界設計の問題である。

### 順番を知ることと、順番を決めること

一部の出来事にしか前後関係がない順序を部分順序と呼ぶ。すべての異なる二つの出来事について順番を付ける全順序を、追加の規則で作ることもできる。同じ論理時刻なら計算機の識別子で順番を決める、といった方法だ。

これは、隠れていた唯一の宇宙の順番を発見したのではない。既知の先行関係を壊さずに、運用上の順番を補ったのである。

整理券を配る店を考えよう。二人がほとんど同時に入店したとき、券の発行順で対応するのは合理的だ。しかし券番号が「どちらが先に店へ行こうと思ったか」まで示すわけではない。制度が作る順序には、制度が解決したい問題に応じた意味がある。

ここには対立する誘惑がある。すべてを物理時刻で一列に並べたい誘惑と、時刻など不要だと言い切る誘惑だ。どちらも行き過ぎる。実時間の締切や有効期間を扱うなら、物理的な時刻とその誤差が重要になる。一方、必要なのが情報の依存関係なら、全員の完全に同期した時計を前提にする必要はない。

Lamportの議論と相対論には順序をめぐる響き合いがあるが、同じ理論ではない。分散システムのhappened-beforeは、モデル化したプロセスと実際の通信に基づく。そこから宇宙の時空構造そのものを導けるわけではない。

ここから見えてくるのは、順序が足りないとき、私たちは無秩序に落ちるのではなく、何が既知で何が規約かを分けて秩序を作れることだ。機械の世界には、発見された順番と、合意して追加された順番が同居している。

**章末の問い**　実際に選ばれた順番以外にも、許される順番がある。その選ばれなかった実行は、どこにあるのだろうか。

**出典と補足**　部分順序、論理時計、その逆が成り立たないことはLamport原論文[R23](#ref-r23)で照合した。最初のコードは読み書き交錯の模型であり、スレッドAPIの実装例ではない。

## 第Ⅳ部　ありえた世界を計算する

選ばれなかった分岐、想定外の入力、万能にはなれない検査器。可能性の範囲を測る。

## 第11章　if文は可能世界を生み出す

### 行かなかった店の夕食

雨なら家で食べ、晴れなら外食する。私たちは毎日、実現しない可能性について考える。プログラムも同じように見える。

```python
rain = True
if rain:
    dinner = "家で食べる"
else:
    dinner = "外食する"
print(dinner)
```

実行結果：

```text
家で食べる
```

外食する分岐は書かれているが、この実行では選ばれない。では外食する世界は、コンピュータのどこかに生まれたのだろうか。ソースコードの文字としては記述がある。しかし外食の処理が実行されたわけではない。まして、もう一つの物理的宇宙が作られたわけでもない。

章題は比喩である。正確には、if文は条件に応じた実行の選択肢を記述する。そこから「ありえた実行」を考えられるようになる。この小さな言い直しが、可能世界への入口を安全にする。

### 書ける分岐と、たどれる分岐

プログラムに分岐があっても、そこへ到達できるとは限らない。`n > 0`かつ`n < 0`という条件を、通常の数について同時に満たすことはできない。二つの条件を文字として並べることと、それを満たす状況があることは違う。

もっと具体的に、扉の状態を考えよう。閉じている状態からは開けられる。鍵がかかっていれば、そのままでは開けられない。到達関係を明示して、そこで何が可能かを調べる。

```python
reachable = {
    "閉": ["閉", "開"],
    "開": ["開", "閉"],
    "施錠": ["施錠"],
}
is_open = {"閉": False, "開": True, "施錠": False}

for state in ["閉", "施錠"]:
    possible = any(is_open[s] for s in reachable[state])
    necessary = all(is_open[s] for s in reachable[state])
    print(state, possible, necessary)
```

実行結果：

```text
閉 True False
施錠 False False
```

`any`は少なくとも一つが真か、`all`はすべてが真かを調べる。ここでは「今から許された一段階の状態」に限って可能と必然を評価している。鍵を開ける操作をモデルに追加すれば、施錠状態についての答えは変わる。物理的に絶対開かない扉だと証明したわけではない。

### 可能と必然の範囲を決める

様相論理では、何が真かに加えて、可能か、必然かを扱う。可能世界意味論では、世界の集合と、ある世界からどの世界を考慮するかという到達関係を使い、到達できる少なくとも一つの世界で成り立つなら可能、すべてで成り立つなら必然、と解釈できる。[R24](#ref-r24)

本書の扉モデルは、この評価規則を小さく試すためのものだ。状態を世界と呼んでも、それだけで形而上学的に完全な可能世界を表したことにはならない。扉以外のことは何も記述していないからである。

物理法則に従って可能なのか、契約上許されているのか、今の知識では否定できないのか。「可能」には複数の読みがある。鍵の担当者が休暇中だから開けられない、というのは論理的矛盾ではない。意味の違いを到達関係へ押し込めた後も、その関係を選ぶ根拠が必要になる。

到達先が一つもない場合に`all`が真になることにも注意したい。これは全称的な判定の空虚な真に対応する。日常語の「必ず成功する」という安心感と同一視すれば誤る。コードが真を返したとき、何を全件調べたのかを確認しなければならない。

### ルイスの世界は保存フォルダではない

デイヴィッド・ルイスの様相実在論は、非現実の可能世界も、私たちの世界と同じく具体的な世界として認める大胆な立場だ。さらに、別の世界の「私」は、文字通り同一の個体が複数の世界にまたがるのではなく、対応者として扱われる。[R25](#ref-r25)

これは、ゲームのセーブデータをいくつも用意することと同じではない。セーブデータは私たちの現実世界にある記録であり、世界内の対象に関する部分的な表現にすぎない。ルイスの世界は、同じコンピュータの中に収まった別々のファイルではない。

対立する考え方では、可能世界を抽象的な表現や事態のまとまりとして理解し、ルイスのような具体的な世界の多さを引き受けない。それでも可能世界の道具を使って推論することはできる。意味論の便利さへの賛成と、世界の実在についての賛成は別だ。

この違いは、プログラマには馴染みやすい。データ構造を使うために、その構造が表すものを全部、机の上へ実物として並べる必要はない。一方、便利な形式だからといって、それが何を意味するかを永遠に問わなくてよいわけでもない。



<!-- EXTENSION START ch11 -->
### 可能性には、種類がある

「明日はこの電車に乗れる」という言い方を考えよう。物理的に線路がつながっているという意味かもしれない。ダイヤ上その列車が運行するという意味かもしれない。切符を持っていて規則上乗車できるという意味かもしれない。自分の予定に間に合うという意味かもしれない。同じ「できる」でも、参照している条件が違う。

プログラムの分岐にも、こうした違いが潜む。入力欄へ書ける値、形式検査を通る値、業務規則で許される値、現実に用意できる値は一致しない。体温へ千度と入力できることは、通常の人間がその体温で存在できることを意味しない。構文上表現できることを、現実の可能性へ直結させてはいけない。

さらに、知らないので排除できない場合もある。閉じた箱に赤い玉か青い玉が入っている。観察前にはどちらもありうると考えるが、すでに入っている玉の色が観察のたびに自由に変わるとは限らない。知識に相対的な可能性と、対象についての可能性を区別する必要がある。

本章の扉モデルは、指定した状態と到達関係に相対的な可能性を扱っている。だから、ある状態が到達できないと計算されたとき、何を禁止した模型なのかを見なければならない。鍵を開ける操作を入れていないだけなのか、故障で不可能なのか、規則で禁止したのか。同じ計算結果でも、外部世界への読み方が変わる。

様相論理は、可能性や必然性を扱うための形式的な道具を与えるが、到達関係を一種類に固定した世界観そのものではない。どの関係を採用し、どの条件を課すかによって、どんな推論が成り立つかが変わる。[R24](#ref-r24)

### 選ばなかった道には、何が残るか

迷路のゲームで右へ進んだとしよう。左へ進んだ場合のデータもメモリに入っているかもしれない。あるいは左へ進んだときに初めて作られるかもしれない。どちらでも、左へ行けたというゲーム上の可能性を表すことはできる。すべての可能な状態が、実際のオブジェクトとして先に存在する必要はない。

逆に、未実行のコードがファイルに書かれていることと、そこへ実際に到達できることも違う。整数nについて`n > 0 and n < 0`を条件にした分岐なら、その条件は満たせない。構文上の枝が見えるだけでは、入力の制約を含めた到達可能性は分からない。

可能性の数え方も変わる。入力の値を全部別世界と数えるのか、表示結果が同じなら一つと数えるのか、途中の履歴まで区別するのか。迷路で同じ部屋へ戻っても、鍵を持っているかどうかが違えば、その後できることは変わる。状態の記述から鍵を省けば、本当は違う可能性を同じものとして扱ってしまう。

ここで探索アルゴリズムは、存在論の小さな実習になる。何を一つの状態と認めるか、どんな変化を許すか、いつ二つの探索経路を同じとしてまとめるか。その決定によって、見つかる解が変わる。世界を探索する前に、探索する世界を記述しているのだ。

ただし、迷路の中で到達できる部屋を列挙しても、ルイスの可能世界の実在論を立証したわけではない。ルイスが論じる具体的な可能世界と、コンピュータ内の状態の集合は、存在論上の主張が異なる。模型は関係の一部を可視化できるが、それだけで存在するものの種類まで同じにはならない。[R25](#ref-r25)

### もし違う選択をしていたら

昨日、駅まで走っていれば電車に乗れただろうか。この問いに答えるには、単に「走る」という値を入れるだけでは足りない。いつ走り始めるのか、どれくらい速いのか、途中で何が変わるのかを考える必要がある。走ったために転んだ可能性まで含めるなら、結果はさらに複雑になる。

反事実をシミュレーションするとき、私たちは一部の条件を変え、他を保つという選択をする。だが、どの条件を保つのが適切かは、問いの目的に依存する。列車の発車時刻を固定して自分の行動だけを比べるのか、混雑や信号の変化も含めるのか。何でも変えてよいなら、望む結論へ導く別世界を簡単に作れてしまう。

このため、「もし」の計算結果には、変更した条件と固定した条件を添えたい。製品の設計比較でも、材質だけを変えたつもりで、重量、剛性、製造条件まで変化する場合がある。代替案の良さは、何を同条件として比較したかを抜きに語れない。

読者は、今日の選択を一つ選び、変える条件を一つだけ書いてみてほしい。次に、その変更が他の条件へ及ぼす影響を考える。最初は独立して見えた条件が、実は結び付いていることに気付くはずだ。プログラムが変数を別々に持てることと、現実の要因が独立であることは違う。

### ありうることと、起こりやすいこと

六面のサイコロで1が出ることと、十回続けて1が出ることは、どちらも可能だとしても起こりやすさは違う。可能世界を列挙しただけでは、各々にどの確率を与えるかは決まらない。同じ結果へ至る経路の数が多いからといって、その経路が等確率で選ばれる保証もない。

プログラムで枝を二つ書けば、二つが半々で起こるわけではない。`if`の条件がほとんど常に真なら、一方へ偏る。ランダムな入力を使う場合でも、どんな分布を選んだかが必要になる。可能性の図へ確率の数字を書き加えるには、別の根拠がいるのだ。

この違いはリスクの議論で重要になる。壊れる経路を見つけたことは、起こりうる失敗を示す。しかし、それだけでは発生頻度を示さない。反対に、頻度が低いと思うことは、経路が存在しない証明にはならない。可能性、頻度、影響の大きさを分けると、議論のすれ違いが減る。

そして、計算に現れなかった可能性は二種類ある。模型の規則に従って本当に到達できない場合と、そもそも状態や操作を記述しなかった場合である。前者は模型の中の結論だ。後者は模型の外への問いだ。この差を忘れたまま「すべての可能性を調べた」と言うと、世界はすぐに想定外を送り返してくる。

### 「可能」と「必然」の順序を入れ替える

様相の言葉は、順序を変えると意味も変わる。ある場所からA室かB室へ進めるとする。Aへ入れば、その後に進める先はAだけ。Bへ入れば、その後に進める先はBだけ。Aには照明があり、Bにはない。この模型で、次の二つの問いを比べてみる。

一つ目は、どこかへ進めば、その次の行き先がすべて明るい場所になるか。Aを選べばよいので、答えは真である。二つ目は、どこへ進んでも、その次に明るい場所を選べるか。Bへ進む場合には明るい行き先がないので、答えは偽になる。

```python
routes = {"start": ["A", "B"], "A": ["A"], "B": ["B"]}
light = {"start": False, "A": True, "B": False}

def possible(world, predicate):
    return any(predicate(next_world) for next_world in routes[world])

def necessary(world, predicate):
    return all(predicate(next_world) for next_world in routes[world])

print(possible("start", lambda w: necessary(w, lambda v: light[v])))
print(necessary("start", lambda w: possible(w, lambda v: light[v])))
```

実行結果：

```text
True
False
```

コードの`lambda w: ...`は、wを受け取り、コロンの右側の式を評価する小さな関数である。ここでは名前を別に付けず、その場で渡した判定規則として使っている。

最初は「可能、その内側で必然」、次は「必然、その内側で可能」という順で評価した。ここでは、行き先は一段階ずつであり、どんな未来にも永久に明るいと主張しているわけではない。模型の関係を保ったまま、存在する行き先が一つあればよいのか、すべての行き先について成り立つ必要があるのかを入れ替えたのである。

これを日常語へ戻すと、「うまく選べば安全な手順がある」と「どんな選択の後でも安全な手順が残る」の違いに似ている。前者が真でも後者が真とは限らない。製品の操作や復旧手順を考えるときにも、この区別は重要だ。成功できる経路があることは、利用者がどの経路へ入っても回復できることを保証しない。

記号を使う意味は、難しく見せることではない。日常語の「できる」「必ず」の入れ子を、どの範囲で何を要求しているかへ分解することだ。コードを短く書けるところまで問いを整理すると、似ていた二つの主張の間に、具体的な反例を置けるようになる。

### 反実仮想には保存条件がいる

「もし別のボタンを押していたら」と考えるとき、何を同じに保つのだろう。直前の状態だけか。ネットワークから届く入力も同じか。乱数の種も同じか。他の人の選択まで固定するのか。

条件を一つ変える実験では、変えなかったものを明示しなければ比較が成立しない。熱設計で材料だけを変えたつもりでも、接触面圧や形状まで変わっていれば、結果の違いを材料だけへ帰属できない。同様に、プログラムの分岐比較にも、変化させる条件と保存する条件がある。

ここから見えてくるのは、可能性を増やすこと以上に、どの可能性を比較対象として認めるかが重要だという点にある。if文は世界を量産する装置ではない。世界についての仮定を分岐条件へ追い込み、その仮定の帰結を見る装置になる。

**章末の問い**　すべての分岐を書いたつもりでも、入力が想像の外から来たらどうなるのか。可能世界のリストにないものは、現実から来てはいけないのだろうか。

## 第12章　例外処理――想定外の世界をどう扱うか

### 世界が文字列で届く

温度を受け取る関数を作った。届くのはいつも数だと思っていたら、ある朝「点検中」という文字列が来た。機械からの入力だから機械的に整っている、という期待は、機械を作っているのが人間だと思い出すまでの短い夢である。

```python
def parse_temperature(text):
    try:
        return float(text)
    except ValueError:
        return None

print(parse_temperature("23.5"))
print(parse_temperature("点検中"))
```

実行結果：

```text
23.5
None
```

数へ変換できない文字列について、`ValueError`を捕まえ、不在の印を返す。ただしこの関数では、なぜ変換できなかったかを失っている。第4章の問題が別の形で戻ってきた。正常と異常の枝を作るだけでは、情報をどう残すかという設計は終わらない。

### 例外は言語の外ではない

「例外が起きると世界が壊れる」と言いたくなるが、Pythonの例外には定義された規則がある。例外が発生し、対応する処理へ制御が移り、処理されなければ外側へ伝わる。これは言語の外へ飛び出すことではない。むしろ言語が用意した秩序の一部だ。[R19](#ref-r19)

だから、例外を哲学的な「想定外」と完全に同一視してはいけない。ファイルがないという例外は、十分に予想できる事態だ。正常な利用者の操作で起きることさえある。一方、想定外の誤った計算が、例外を出さずに最後まで進むこともある。

章題の比喩を限定すると、こうなる。例外は、ある処理が前提としていた通常の経路を続けられないと知らせる方法である。その前提が現実に破られたとき、設計者はモデルの境界を見直す機会を得る。

### 失敗して止まるか、続けるか

二つの設計方針がある。異常を見つけたら早く止め、誤った状態を広げない。もう一つは、部分的な失敗から回復し、できる仕事を続ける。どちらが正しいかは、失敗の意味による。

一件の画像が読めなくても写真一覧は表示したい。だが送金処理の途中で金額の整合性が壊れたなら、黙って先へ進むべきではない。「絶対に落ちない」は、必ずしも利用者の利益を意味しない。誤ったまま動き続ける装置は、止まる装置より困ることがある。

例外を広く捕まえて`pass`する書き方は、警報器の電池を抜いて静かになったと喜ぶような結果を生みうる。静かさと正常さは別の性質だ。回復するなら、何を回復できたのか、何を失ったのか、誰へ知らせるのかを決めたい。

### 不変条件という細い手すり

在庫は負にならない、という規則を持つ小さな出庫関数を作ろう。

```python
def withdraw(stock, amount):
    if amount < 0:
        raise ValueError("数量は非負")
    if amount > stock:
        raise ValueError("在庫不足")
    return stock - amount

print(withdraw(5, 2))
try:
    withdraw(5, 8)
except ValueError as error:
    print(error)
```

実行結果：

```text
3
在庫不足
```

この関数は初期在庫が非負であり、比較・減算のできる適切な数量が渡されることを前提とする。その範囲では、受け付けた出庫によって負の在庫を作らない。現実の全入力を防御した関数ではない。たとえば値の型やNaN、他の同時更新などは別の条件になる。

不変条件は、処理を通じて守りたい性質である。それを明示すると、異常が何に対する異常なのかが分かる。ただし、そもそも在庫を負にしてはいけないかも、用途による。予約超過を負数で表すシステムなら、別の規則が必要だ。物理的な台数と受注上の不足を一つの数に押し込むと、規則をめぐる議論が混乱する。

### もう一度押してください、の難しさ

画面に「処理に失敗しました。もう一度お試しください」と出る。親切そうな案内だが、何が失敗したのか分からなければ危険なこともある。依頼が届かなかったのか、処理の途中で止まったのか、処理は終わったが返事だけ届かなかったのか。同じ画面表示の背後に、異なる状態が隠れている。

一度だけ行いたい加算を考えよう。毎回そのまま足せば、再試行で二度足される。そこで同じ依頼番号は一度だけ受け付ける、小さな模型を作る。

```python
seen = set()
balance = 0

def apply(request_id, amount):
    global balance
    if request_id in seen:
        return "処理済み"
    balance += amount
    seen.add(request_id)
    return "反映"

print(apply("req-1", 100))
print(apply("req-1", 100))
print(balance)
```

実行結果：

```text
反映
処理済み
100
```

これは、単一プロセスで順番に実行し、途中で停止しないという条件の模型である。実際の永続的な処理では、残高を変えてから依頼番号を記録するまでの間に停止したらどうなるか、という問題が残る。二つの変更を一体として保存するなど、別の仕組みが必要になる。わずか数行で、実用的な決済システムが完成したわけではない。

この例の狙いは、再試行には「同じ処理」という同一性の規則が必要だと示すことだ。同じ金額なら同じ依頼なのか。同じ利用者なら同じなのか。どちらも一般には違う。同一性の章で考えた区別が、障害からの回復という具体的な仕事へ戻ってくる。

### どこまで終わったかを表す

長い作業を、開始か成功かの二状態だけで管理すると、途中の失敗を説明しにくい。ファイルを読み、変換し、別の場所へ保存し、通知する処理なら、保存まで終わって通知だけ失敗することもある。そのとき全体を失敗と呼ぶだけでは、何をやり直すべきか分からない。

そこで途中の状態を明示する。ただし、状態名を細かく増やすだけでは足りない。どの状態からどの状態へ移れるか、各状態で何がすでに外部へ作用したか、再実行してよい操作は何かを決める必要がある。「保存済み」という言葉も、バッファに書いたこと、保存要求が受け付けられたこと、後から読み出せることのどれを意味するかで違う。

失敗時に全部を巻き戻す設計が使える場面もある。しかし外部へ送った通知や、すでに人が実行した作業は、同じ方法では戻せない。取り消しの通知や代わりの作業を行うなど、新しい出来事によって対応する場合がある。例外処理は、過去を消去する能力ではない。

このように見ると、正常系と異常系は完全に別の世界ではない。失敗も含めた状態の変化が、システムの実際の世界を作っている。成功だけを書いた仕様は、世界の普段着だけを描いた設計図に近い。雨が降ると何を着るかも、動く仕組みには必要になる。

### 例外を隠すと、誰が困るか

エラー表示を減らしたいので、すべての例外を捕まえ、空の結果を返す。すると画面は穏やかになる。しかし、検索結果が本当にゼロだったのか、検索できなかったのかが分からなくなる。「何も見つからない」と「見つける作業が失敗した」が同じデータへ潰される。

第4章で考えた欠如の問題が、ここでは制御の流れとして現れる。空のリストは有効な検索結果かもしれない。だから失敗を同じ空リストで表すなら、呼び出す側が区別できる別の情報が必要になる。そうでなければ、失敗が正常な事実として後工程へ流れる。

もちろん、利用者へ内部の例外名をすべて見せればよいわけでもない。利用者が必要なのは、作業が完了したか、やり直してよいか、入力を直すべきか、待つべきかといった情報だ。内部向けの詳細と、外部向けの意味を分けて伝える設計が必要になる。

ここでエラーを「処理した」と言う意味を問い直せる。例外が外へ出なくなったことか。状態が安全に保たれたことか。利用者が次に行うべきことを理解できることか。これらは同時に達成したいが、一つを満たしても他を満たすとは限らない。例外の行を短くするだけでは、仕事が終わったことにならない。

### 想定外をなくすより、発見できるようにする

あらゆる故障を事前に列挙するのは難しい。それなら、既知の失敗だけを丁寧に処理しても無意味なのか。そうではない。すでに分かっている失敗を扱えることは、それだけで価値がある。さらに、知らなかった失敗へ気付くための情報を残すこともできる。

たとえば、守られているはずの件数関係を定期的に確認する。処理の開始と終了を関連付けて記録する。想定外の状態になったら、曖昧な結果を外へ出す前に停止する。こうした仕組みは、未知の失敗の具体的な姿を予言していない。それでも、何かが前提から外れたことを検出できる場合がある。

ただし、検査項目自体が不十分なら見逃す。正常な範囲に見える誤った結果もある。だから「異常が検出されなかった」と「正しいと確認された」を区別する必要がある。検査器も、見ている性質についてしか語れない。

世界の外側から例外がやって来る、という章題の比喩をここで修正しておこう。例外機構そのものは、言語の規則の内側にある。外側にあるのは、設計者の現在の想定から漏れた事情かもしれない。その事情を観測し、状態として表し、規則を改訂できたとき、昨日の想定外は明日の通常の入力になる。境界は絶対の壁ではなく、学習によって移動するものなのだ。

### 未定義動作と、知らない動作

仕様が振る舞いを定めていない場合と、仕様は定めているが自分が知らない場合も区別したい。さらに「実装によって異なる」と定められている場合もある。これらを全部「想定外」にすると、調べるべき場所が分からなくなる。

Pythonでゼロ除算が例外になることは、未定義動作ではない。何が起きるかについての規則がある。C系言語で使われる未定義動作という技術用語を、そのまま「バグが起きた」という意味へ広げるべきではない。

ここに哲学的な問いがある。世界を規則で記述したとき、記述しなかったものは存在しないのか。それとも、記述のほうが不十分なのか。人工的なゲームなら、許される操作を閉じた形で決められることがある。しかし現実につながるソフトウェアは、センサーの故障、入力形式の変更、人間の誤解などにさらされる。設計者が世界の外側で全入力を見渡しているわけではない。

ここから見えてくるのは、例外処理を追加するだけで想定外がなくなるのではなく、どの範囲の失敗を名前付きで認めたかが明確になることだ。例外の一覧は、敗北の目録ではない。自分の世界が何に依存しているかを示す地図にもなる。

**章末の問い**　前提も例外も丁寧に書けば、すべての誤りを機械的に発見できるのだろうか。そろそろ、機械が絶対にできないことを一つだけ正確に調べよう。

## 第13章　すべてのバグを取り除くことはできるのか

### 一万回動いたという証拠

一万回試して正しかったプログラムは、一万一回目にも正しいだろうか。毎回同じ入力なら、新しい情報はほとんど増えていないかもしれない。異なる入力でも、まだ試していない境界で失敗することがある。

一方、入力が本当に有限個しかなく、すべてを正しい判定基準で検査できるなら、その範囲の全数検査は強い証拠になる。単純な上限処理を試そう。

```python
def clamp_level(n):
    return min(10, max(0, n))

values = [clamp_level(n) for n in range(-20, 21)]
print(all(0 <= v <= 10 for v in values))
print(clamp_level(-3), clamp_level(5), clamp_level(14))
```

実行結果：

```text
True
0 5 10
```

これは入力を整数の-20から20に限った検査だ。すべての数、すべての型、すべての環境を調べたわけではない。一般の整数についてなら、式の構造から別の証明を与えることができる。テストと証明は競合する看板ではなく、異なる範囲の根拠を与える方法だ。

### 正しさの前に、何を約束したか

「結果が0以上10以下」という条件だけでは、常に0を返す関数も合格する。欲しいのが、範囲内の入力はそのまま返し、範囲外だけを端へ寄せる動作なら、その条件も必要になる。

形式的検証は、明示した性質に対して実装やモデルが適合することを調べる。仕様が利用者の目的を正しく表すかという別の仕事は残る。間違った仕様を完璧に守る機械は、曖昧な仕様を適当に守る機械とは違うが、自動的に良い機械ではない。

ここで万能の検査器が欲しくなる。任意のプログラムと入力を渡せば、そのプログラムがいつか終了するかを、必ず有限時間で正しく答える検査器である。これが一般に作れないというのが、停止問題の決定不能性だ。

### 自分への予言を裏切る機械

万能検査器Hがあると仮定する。HはプログラムPと入力xを受け取り、Pがxについて停止するなら「停止」、しないなら「非停止」と答え、H自身は必ず停止する。

次に、プログラムDを作る。DはプログラムPを受け取り、Hに「PをP自身へ適用すると停止するか」と尋ねる。「停止」と言われたらDは永遠に回り続け、「非停止」と言われたらDはすぐ終了する。

ではDへD自身を渡す。Hが停止と答えれば、定義によってDは停止しない。Hが非停止と答えれば、Dは停止する。どちらでもHの完全な正しさに反する。したがって、仮定した万能検査器は存在しない。

これは無限ループを実行して確かめる実験ではなく、仮定の矛盾を示す論証である。本書では、それらしく動く偽のHをコードにして読者へ渡さない。存在しない部分を省略記号で埋めれば、プログラムらしい外見だけは簡単に作れてしまう。

Turingの1936年の論文は、計算機のモデルと対角線的な議論により、一般的な判定手続きの限界を明らかにした。ただし原論文は、現在の教科書でよく使う停止問題の提示とまったく同じ言い方ではない。circle-freeな機械の判定などを扱っている。上の説明は現代的な停止問題の形での論証である。[R26](#ref-r26)

### 「すべて」と「一つ」の距離

万能の停止判定器がないことから、どのプログラムの停止も証明できないとは言えない。10回だけ反復する処理について、その条件のもとで終了を示せる場合はある。特定の言語やプログラムの範囲を制限すれば、判定可能な問題もある。

同じように、停止問題から「バグのないプログラムは存在しない」とは導けない。バグの定義には仕様が必要であり、万能な検査手続きの不在は、正しい個別のプログラムの不在とは違う。

有限の現物のコンピュータだけを考えれば、状態数は有限ではないかという反論もある。閉じた有限状態の決定的なモデルなら、状態の反復を調べるなどして停止を判定できる。ただし、そのための計算量は実用を遠く超えうるし、一般の停止問題は無制限の計算資源を許す抽象的なモデルについて述べている。対象を変えて得た答えを、元の定理への反証とは呼べない。

### 小さな証明を、自分で持ってみる

万能の検査器がないという話だけでは、何も確かめられない気分になるかもしれない。そこで、十分に小さなプログラムについて、テストとは別の根拠を作ってみよう。0から始めて、1からnまでを順に足す関数である。入力は0以上の整数に限定する。

```python
def triangle(n):
    if type(n) is not int or n < 0:
        raise ValueError("0以上の整数を指定する")
    i = 0
    total = 0
    while i < n:
        i += 1
        total += i
    return total

print(triangle(0), triangle(5), triangle(10))
```

実行結果：

```text
0 15 55
```

この例では真偽値まで個数として受け入れないよう、`type(n) is int`で型を限定している。`isinstance(n, int)`なら`True`も受け入れる。どちらが一般に正しいかという問題ではなく、この関数の入力の約束を明示するための選択である。

知りたい性質は、結果がn(n＋1)／2に等しくなることだ。小さい値をいくつも試すだけでなく、反復の途中でも保たれる関係を探す。ここでは、反復条件を調べる各時点で、`total`がi(i＋1)／2に等しいという関係が使える。このように反復を通じて保たれる条件を、ループ不変条件と呼ぶ。

最初はi＝0、total＝0だから、関係は成立する。次に、ある時点で成立していると仮定する。元のiをjと書けば、処理後のiはj＋1になり、totalにはj＋1が加わる。元のtotalはj(j＋1)／2だったから、新しいtotalはj(j＋1)／2＋j＋1、整理すると(j＋1)(j＋2)／2になる。これは新しいiについてのi(i＋1)／2に一致する。

最初に成立し、一回の反復で壊れないなら、何回反復しても、この条件を調べる位置では保たれる。ここで重要なのは、コードのすべての瞬間で式が成立する必要はないことだ。iだけ増やし、totalをまだ更新していない中間地点では、同じ形の条件は成立しない。保証がどの地点についてのものかを指定する必要がある。

反復が終わったときはiがnに達している。したがって、不変条件からtotal＝n(n＋1)／2が得られる。どのような値であっても同じ代数的な議論が使えるので、個別に試していない大きなnについても根拠がある。これは本書独自の教材例であり、証明支援系でPythonの実装全体を形式化して検証したものではない。

### 正しい答えが出る、だけでは足りない

まだ一つ穴がある。上の議論は、反復が終わったときの答えについて述べている。では、そもそも終わるのか。不変条件を保ちながら永久に回り続ける処理も作れる。正しい関係を壊さないことと、目的地へ到達することは別だ。

この例ではn−iに注目できる。反復へ入るとき、それは正の整数であり、一回ごとに1ずつ減る。iがnを越えて増える処理はなく、0になると反復をやめる。非負の整数を無限に減らし続けることはできないから、有限回で終了する。このような終了へ向けて減少する量を見つけると、停止の根拠を与えられる。

ここでは、「終了するなら結果が正しい」という性質と、「終了する」という性質を分けて考えた。Hoare論理の入門でも、事前条件、プログラム、事後条件を結び付ける考え方と、部分正当性における終了の扱いが重要になる。[R43](#ref-r43)

ただし、実際のコンピュータが電源を失わないことや、巨大な整数のための記憶領域を必ず確保できることまで、この証明は保証していない。理想化した実行の規則のもとで、正常な計算がどのように進むかを説明したのである。保証が依存する前提を示すことは、証明を台無しにすることではない。どこで有効かを明らかにすることだ。

この小さな経験があると、停止問題の主張が違って見える。すべてのプログラムについて自動で成功する一般手続きがなくても、個別のプログラムには、構造に即した証明がある。万能性を失うことと、確実性をすべて失うことは違う。

### 仕様の穴を、正しさが通り抜ける

さて、上の関数について「結果が0以上である」という仕様だけを書いたらどうなるか。常に0を返す関数も、入力の条件のもとで合格する。「結果はn以上」と書いても、n＝0の扱いを考えたうえで、適当な大きな値を返す実装が通るかもしれない。欲しい性質を取りこぼした仕様は、間違った実装に広い逃げ道を与える。

ここで仕様を完全にしようとして、結果は正しい合計でなければならないと書いても、その「正しい」が未定義なら出発点へ戻る。数式、入力条件、例外の条件、外部への作用などへ分け、何を確認するかを具体的にする必要がある。

一方、仕様を細かくしすぎると、目的には関係しない実装方法まで固定してしまうことがある。合計が正しければ、順に足す方法でも、公式を使う方法でもよいはずなのに、変数名や反復の順番まで要求してしまう。その場合、改良の余地が消える。仕様は、欲しい振る舞いを限定し、不要な方法の違いを残す仕事でもある。

この問題は、哲学における定義と反例の関係に似ている。ある定義が意図した対象をすべて含むか、含めたくない対象を排除できるかを調べる。ただし、プログラムの仕様なら、目的に合わせて定義を変更する権限を私たちが持つ場合が多い。現実の存在についての概念は、使い勝手だけで自由に改訂できるとは限らない。この差を保ったまま比べたい。

### 反例のない試験を疑う

テストにも、違う種類の強さがある。実装と同じ計算式をテスト側へコピーして結果を比べれば、一致しやすい。しかし同じ誤解を二か所へ書けば、二か所が仲良く間違う。検査器を別に置いたという外観だけでは、根拠が独立したことにならない。

合計の例なら、既知の小さい結果との比較に加え、nを一つ増やすと結果がn＋1だけ増えるという関係も調べられる。順に足す実装に対して公式を使った計算と比べることにも意味がある。ただし、これらの検査をいくつ積んでも、それだけで数学的な全称命題の証明になるとは限らない。

反例が出たときは、失敗した入力を小さくしてみるとよい。大きな複雑な条件で起きた誤りが、0や1のような境界で再現することがある。何を当然だと思っていたかが、最小の反例で見えやすくなる。これは哲学の思考実験にも似た作業で、周辺の装飾を取り除き、争点が残る最小の状況を作る。

もちろん、現実の事故は複数条件の組合せでしか起こらないこともある。小さくすれば必ず分かるという保証はない。それでも、何が必要な条件で、何がたまたま同時にあった条件なのかを分ける試みは有益だ。反例は、失敗の印だけでなく、仕様やモデルの境界を示す情報になる。

### 証明した人も、道具の内側にいる

証明支援系を使えば、推論の細かな見落としを機械に検査させられる。しかし、その証明が扱うプログラムのモデルと、実際に配布する実行物の関係は別に確認する必要がある。仕様を書き間違えた可能性、実装へ結び付ける工程、使った基盤の前提などが残る。

だから形式的検証の価値を、「絶対に何も間違わない装置」になれるかどうかだけで評価するのは不公平だ。ある種類の誤りを、明示した前提のもとで排除できることは大きな達成である。現実の設計でも、一つの試験ですべてを保証しないからといって、その試験が無意味にはならない。

本書の立場は、証明を神託にせず、テストを気休めにもせず、それぞれがどの問いへ答えているかを明確にすることだ。世界の完全な記述が得られるかという大きな問いを残したままでも、目の前の十行について、昨日より強い理由を持つことはできる。

### ゲーデルは品質保証部長ではない

ゲーデルの不完全性定理も、しばしば「完全な体系は作れない」という標語に縮められる。正確な適用条件を外すと、便利すぎる言葉になる。

第一不完全性定理は、一定の初等算術を表現でき、効果的に公理化された無矛盾な形式体系に、その体系内では証明も反証もできない文があることを述べる。第二定理は、標準的な証明可能性の形式化などの条件のもとで、十分な強さを持つ無矛盾な体系が自分自身の無矛盾性を証明できないことを述べる。[R27](#ref-r27)

停止問題が一般的なアルゴリズムによる判定の限界を扱うのに対し、不完全性定理は特定の形式体系における証明可能性の限界を扱う。関係は深いが同じ命題ではない。そこから人間が機械を必ず超える、神が存在する、科学は無意味だ、といった結論がそのまま出るわけでもない。

むしろ実務への教訓は慎ましい。何を前提に何を保証したかを明らかにし、保証できる範囲を増やす。万能な救済装置を待たずに、入力を制限し、型を使い、重要な性質を証明し、境界を試験する。それぞれが異なる穴を塞ぐ。

ここから見えてくるのは、限界の定理が努力の無駄を証明するのではなく、努力を向ける範囲を精密にすることだ。宇宙全体を一度に検査できないからといって、明日の出荷検査をやめる理由にはならない。

### 同じ人を三回登録する

ある人が社員であり、会社の商品を買う顧客でもあり、研修の講師でもある。社員表、顧客表、講師表に一行ずつ登録したら、人間は三人になったのだろうか。給与計算では社員として数え、販売分析では顧客として数えればよい。ところが住所変更のたびに三か所直す必要があるなら、同じ人を三つに分けた代償が見えてくる。

データベースを作る前に、何を一つの存在として扱うかを決めている。テーブル名を英語にする作業の前に、すでに存在論的な仕事が始まっているのだ。

```python
people = {7: {"name": "青木"}}
roles = [(7, "社員"), (7, "顧客"), (7, "講師")]
print(len(people))
print([role for person_id, role in roles if person_id == 7])
```

実行結果：

```text
1
['社員', '顧客', '講師']
```

人と役割を分けた。ただしこれが唯一正しいモデルとは限らない。匿名の購入者も顧客として扱いたいなら、個人との対応が分からない顧客記録を許す必要がある。法人顧客もいるなら、人という表だけでは足りない。最初の分類を精密にすれば、世界が自然に収まるという保証はない。

### 主キーと外部キーの届く範囲

SQLでは、主キーや外部キーなどの制約を使って記録の整合性を守れる。次は説明用のスキーマだ。

```sql
CREATE TABLE person (
    person_id INTEGER PRIMARY KEY,
    name TEXT NOT NULL
);
CREATE TABLE role_assignment (
    person_id INTEGER NOT NULL REFERENCES person(person_id),
    role TEXT NOT NULL,
    PRIMARY KEY (person_id, role)
);
```

この例で主キーは行の識別を支え、外部キーは役割の付与先に対応する人の行があることを要求する。PostgreSQLの主キーは一意性と非NULLを伴う。[R28](#ref-r28)

しかし外部キーは、その人が現実に存在するかを調査しない。誤った名前の人の行を作れば、その行への参照は整合的でありうる。データベース内の整合性と、外部世界に対する正確さは別である。

このSQLはPython標準のSQLiteでも、外部キー検査を明示的に有効にして動作を試せる。確認用の入力は次の通りだ。

```python
import sqlite3
with sqlite3.connect(":memory:") as db:
    db.execute("PRAGMA foreign_keys = ON")
    db.execute("CREATE TABLE person (person_id INTEGER PRIMARY KEY, name TEXT NOT NULL)")
    db.execute("CREATE TABLE role_assignment (person_id INTEGER NOT NULL REFERENCES person(person_id), role TEXT NOT NULL, PRIMARY KEY(person_id, role))")
    db.execute("INSERT INTO person VALUES (7, '青木')")
    db.execute("INSERT INTO role_assignment VALUES (7, '社員')")
    try:
        db.execute("INSERT INTO role_assignment VALUES (99, '顧客')")
    except sqlite3.IntegrityError:
        print("参照先がないため拒否")
    print(db.execute("SELECT count(*) FROM role_assignment").fetchone()[0])
```

実行結果：

```text
参照先がないため拒否
1
```

実行したのはSQLiteであり、PostgreSQLサーバーの実行試験ではない。似た構文が通ることと、両システムのあらゆる仕様が同じことを混同しないようにしたい。

### NULLは「不在という値」とも少し違う

SQLのNULLを含む通常の比較は、真か偽かだけでなく不明という結果を持つ。たとえば`NULL = NULL`で、Pythonの`None is None`と同じ答えを期待してはいけない。欠如を表す規則が異なるのだ。

SQLiteでその差を一つ試してみる。

```python
import sqlite3
with sqlite3.connect(":memory:") as db:
    row = db.execute("SELECT NULL = NULL, NULL IS NULL").fetchone()
    print(row)
```

実行結果：

```text
(None, 1)
```

ここで表示されたPythonの`None`は、SQLのNULLがPython側へ変換された結果である。右側の1はこのSQLiteの問い合わせにおける真を表す。二つの言語の境界をまたいでいるので、「同じnull」という言い方では情報が足りない。

### 人が一人、行が三つ

ある人が会社に勤め、同時にその会社の商品を購入し、さらに退職後に取引先の担当者になるとする。社員、顧客、取引先担当者の各テーブルへ別々に登録すれば、三つの行ができる。では人も三人になったのか。もちろん、行の数と現実の人の数はそのまま一致しない。

一人の人物へ複数の役割を結び付ければよいと思うだろう。しかし、その「一人」をどう照合するかが次の問題になる。氏名は変更され、同姓同名もある。メールアドレスは共有されたり変わったりする。複数の部署が独立に集めた情報を、どの証拠で同じ人物へ結び付けるのか。主キーを新しく発行するだけでは、この照合は終わらない。

誤って二人を統合すると、違う人の履歴が混ざる。逆に一人を別々の人として扱い続けると、連絡や集計が重複する。どちらの誤りが困るかによって、統合の条件や確認手順は変わる。自動的に一致を決めず、候補として提示して確認を受ける設計も考えられる。

ここでデータベースは、人間が一人であることの証明器ではなく、同一性についての判断と根拠を管理する場所になる。統合したという操作、統合を取り消せるかどうか、どの情報がどこから来たかを残す意味がある。誤った判断を後から直せないなら、識別の誤りがシステム全体へ広がる。

個体を中心にしたモデルにも、役割や関係を中心にしたモデルにも利点がある。個体中心なら同じ人の情報をまとめやすい。役割中心なら、期間や組織によって変わる扱いを表しやすい。対立する世界観として一方を捨てるより、何を安定した対象とし、何を変化する関係として扱うかを組み合わせることが実務では多い。

### 関係が主役になる日

社員と部署を結ぶとき、社員の行に部署番号を一つ入れれば簡単だ。しかし兼務が始まると困る。部署番号の欄を二つ、三つと増やすのか。別の関係表を作るのか。さらに兼務の割合や開始日を記録したくなれば、「所属」という関係そのものが情報を持つことになる。

これは、最初から存在していた本質を発見したというより、問いが増えたことで、以前は付属情報だったものを独立した対象として扱うようになった例である。関係を行として表現することは、現実に新しい物体が出現したという意味ではない。それでも、管理と推論のために一つのものとして数える意味が生まれる。

部品と製品の関係も同じだ。ある部品がどの製品に使われるかだけでなく、使用個数、取り付け位置、適用期間を知りたくなる。すると部品そのものの属性と、ある製品における使われ方の属性を分ける必要がある。同じねじでも、使う場所ごとに数量が違うことを、ねじ一個の本質へ押し込むことはできない。

この区別ができないと、製品Aの使用個数を変更したら製品Bまで変わる、といった事故を招く。共有すべき情報と、関係ごとに変わる情報を置く場所を間違えたのである。これは抽象的な哲学論争のようでいて、変更の影響範囲を正しくするための実務そのものだ。

### 一つの世界を、同時に更新する

データの構造が正しくても、更新の仕方で矛盾は起きる。残り一個の商品を二つの処理が同時に予約し、両方が成功したと判断するかもしれない。表の設計だけでは、複数の変更が重なるときの振る舞いまで決まらない。

データベースのトランザクション分離は、同時に動く処理が互いの変更をどう見て、どのような結果を許すかに関わる。たとえば直列化可能性は、成功した処理の効果が、何らかの順番で一つずつ実行した場合と整合するという考え方だ。PostgreSQLでは分離レベルによって保証が違い、直列化可能な実行を保つために処理が失敗し、再試行が必要になる場合もある。[R41](#ref-r41)

ここでは「各行が正しい」だけでなく、「行どうしの変化が一つの整合した履歴を作るか」が問題になる。数字がそれぞれ許容範囲内でも、合計が合わない状態は作れる。個体の属性だけを見る存在論から、関係と変化を見る視点へ移る必要がある。

ただし、強い分離を選べば何でも解決するわけではない。取引処理が保存したデータと、外部の倉庫で実際に動いた荷物との関係は別に確かめる必要がある。データベースの中が整合していることと、外部世界を正しく表していることは違う。小さな宇宙の秩序は、その宇宙の外への正確さを自動的には保証しない。

### 名前を変えると、過去も変わるのか

顧客の会社名が変わったとき、過去の注文書に表示する名前はどちらがよいだろうか。現在の名前へ統一すれば検索しやすい。しかし当時発行した書類の内容を再現したいなら、当時の名前も必要になる。現在の顧客情報を参照するだけでは、昔の表示が変わってしまう。

ここで、同じ情報を一か所だけに置くことと、当時の状態を保存することが緊張する。情報の重複を減らす設計は更新の不整合を減らしやすいが、過去の状態が必要なら、履歴や当時の写しを別に残す必要がある。「重複は悪」とだけ覚えると、時間の違う事実まで不必要な重複として消してしまう。

反対に、すべての場所へ会社名をコピーすればよいわけでもない。訂正すべき誤記と、保存すべき当時の表記を区別しなければ、何を更新するか分からなくなる。変更が新しい事実なのか、古い記録の誤りを直すことなのかを表す規則が必要だ。

ここでは、データベースは現在の世界の模型であるだけでなく、世界をどう理解してきたかの記録でもある。ある列の値を上書きするとき、現実の変化を記録しているのか、過去の誤解を消しているのかを考える。その問いを持つだけで、更新処理の意味はずっと明確になる。

### 表を作る前の会話

よいデータモデルを作るために、最初から高度な記法が必要とは限らない。「この番号は何を一個として数えるのか」「この情報はいつ変わるのか」「同時に二つありうるか」「消した後も必要か」と尋ねるだけで、多くの前提が表へ出てくる。

重要なのは、現場の言葉をそのまま列名へ移すだけで終わらないことだ。同じ「顧客」でも、請求先、利用者、契約相手を指すことがある。違う部署が違う意味で同じ言葉を使っているなら、データベースが矛盾を生んだのではない。矛盾を隠せなくした可能性がある。

もちろん、言葉の不一致をすべて哲学討論に変えていては仕事が進まない。どこまで共通化し、どこは別の概念として接続するかを決めればよい。ただし、その決定を自然そのものの分類だと思わず、目的と運用に応じた約束として記録する。小さな宇宙を作るとき、最初に必要なのは創世の呪文ではなく、丁寧な質問なのである。

### 世界の分類が変わるとき

会社が製品を売るだけでなく貸し出し始めたらどうなるか。購入者と所有者と利用者が分かれる。所有者を一つの顧客番号で表してきた設計が、急に狭くなるかもしれない。

これは必ずしも昔の設計者の無能さではない。当時の目的には十分だった分類が、新しい制度に合わなくなったのである。ただし、変化の可能性を考えず、分類を自然法則のように扱うと、改修のたびに例外の柱が増える。

一つのモデルを全社共通にする方針には、連携しやすい利点がある。業務ごとに異なるモデルを認める方針には、文脈の違いを尊重する利点がある。前者は巨大で硬い分類になりやすく、後者は対応付けが難しくなる。哲学的に整っていることと、運用可能であることの両方を考えなければならない。

ここから見えてくるのは、世界の歪みが計算式より先に、主語の選び方から始まることだ。何を一行にするか。それは保存形式の都合であると同時に、どんな問いへ答えやすい世界を作るかという選択なのだ。

**章末の問い**　すべての情報を持てないなら、何を捨てるべきだろうか。「大事なものだけ残す」という助言は、大事とは何かを決めるまで役に立たない。

## 第15章　抽象化――何を捨てれば本質が残るのか

### 同じ40キログラムでも転び方は違う

二台の装置があり、どちらも総重量40キログラムだ。輸送運賃を計算するなら、それで十分な場合がある。しかし転倒しやすさを調べたいなら、重い部品が上にあるか下にあるかが重要になる。

```python
layout_a = [(30, 0.2), (10, 0.8)]
layout_b = [(10, 0.2), (30, 0.8)]

def mass_and_height(parts):
    mass = sum(m for m, height in parts)
    center = sum(m * height for m, height in parts) / mass
    return mass, round(center, 2)

print(mass_and_height(layout_a))
print(mass_and_height(layout_b))
```

実行結果：

```text
(40, 0.35)
(40, 0.65)
```

質量をキログラム、高さをメートルとする単純な模型である。各部品を指定した高さの点質量として扱った。総重量という抽象化は二台を同じと見なすが、重心高さという抽象化は区別する。

どちらかが本物の装置で、もう一方が偽物ということではない。問いに応じて残した情報が違う。抽象化とは、複雑なものを曖昧な言葉で言い換える技ではなく、どの差異を保存し、どの差異を潰すかという操作なのだ。

### 失われた情報は後から湧かない

総重量だけを保存したデータから、元の部品配置を一般に復元することはできない。同じ総重量を持つ配置がいくつもあるからだ。後から転倒解析が必要になっても、合計欄を小数点以下六桁まで表示して重心を取り戻すことはできない。

精度と情報の種類を混同しないようにしたい。足りないのが配置情報なら、重量の数値精度を増やしても問題は解決しない。抽象化によって失った差異は、計算の巧みさだけでは復活しない。

一方、あらゆる情報を保存すればよいわけでもない。測定・保存・管理には費用がかかり、余分な変数は誤入力や更新漏れの入口になる。全原子の位置を保存した製品データベースは、少なくとも多くの製品管理には扱いにくすぎる。情報は多いほど役に立つとは限らない。

### 本質と、目的にとって重要なこと

アリストテレスの本質を、単に「仕事に必要な属性」と訳すのは早すぎる。本質は、そのものが何であるかに関わる。一方、設計者が保存する属性は、請求、修理、試験など目的に依存する。哲学的な本質と、モデル上の重要性は区別したい。[R06](#ref-r06)

本質を対象の側に求める立場からは、どんな特徴でも同じ重みで選べるわけではないと考えられる。目的に応じたモデル化を重視する立場からは、唯一の抽象化をすべての仕事に押し付けるべきではないと考えられる。

両者の緊張は、材料選定に表れる。鋼板の材質記号は重要だが、プレス成形の問題では板厚、表面状態、方向性なども効く。呼び名が同じだから同じ挙動、という判断は、分類を説明の代わりに使っている。本質を求めることが、細部を無視してよい理由になってはいけない。

### カプセル化は知らなくてよい範囲を作る

プログラムでは、内部の実装を隠し、必要な操作だけを外へ示すことができる。利用者が内部の記憶配置を知らなくても、`read`で値を読むという約束が守られれば仕事を進められる。

```python
from abc import ABC, abstractmethod

class Sensor(ABC):
    @abstractmethod
    def read(self):
        raise NotImplementedError

class FixedSensor(Sensor):
    def read(self):
        return 23.5

print(FixedSensor().read())
try:
    Sensor()
except TypeError:
    print("抽象クラスはこのまま実体化できない")
```

実行結果：

```text
23.5
抽象クラスはこのまま実体化できない
```

この抽象基底クラスは、読む操作を具体化するよう求めている。しかし、返す値が摂氏なのか、誤差がどれくらいなのか、故障時にどう振る舞うかまでは、この短い定義では保証していない。抽象メソッドを実装したという事実と、適切なセンサーであることは違う。[R29](#ref-r29)

抽象クラスという名前も、プラトン的な抽象対象を意味しない。Pythonの中で規則を持つクラスであり、作られ、参照される対象だ。哲学の語と技術の語が重なるときこそ、定義を読み直す必要がある。

### 同じ重さの荷物が、同じように転ぶとは限らない

二つの箱があり、どちらも10キログラムだとする。台車の積載重量だけを調べるなら、同じ入力として扱える。しかし片方は底に重い物が集まり、もう片方は上部に重い物が集まっている。傾けたときの安定性まで知りたいなら、重量だけでは足りない。

ここでモデルが間違っていると一言で片付ける必要はない。重量の上限を確かめる目的には適切だったものが、転倒を予測する目的には不十分なのである。モデルのよさは、情報を多く含むかどうかだけでなく、答えたい問いに必要な違いを残しているかで決まる。

では重心を追加すれば完全になるか。今度は箱の中で液体が動くかもしれない。台車が曲がるときの挙動には、形状や慣性、固定状態も関係する。すべてを追加すればよいように見えるが、測定できない項目が増え、計算と検証の負担も増える。精密な見た目のモデルが、単純なモデルより予測しやすいとは限らない。

抽象化とは、対象を小さくするだけの作業ではない。どの問いに対して、どんな違いを無視してよいかという判断である。同じ対象でも、輸送費の計算、転倒防止、熱設計では必要な表現が異なる。一つの究極のデータ構造ですべてを済ませようとすると、使う側が不要な情報の森を歩くことになる。

### 内部を隠すことと、都合の悪いことを隠すこと

カプセル化は、内部の仕組みを利用者から隠し、決めた操作を通じて使えるようにする考え方だ。利用者が毎回内部のデータ構造を理解しなくても仕事ができるなら、複雑さを減らせる。しかし、何を隠してよいかには条件がある。

たとえば、温度を返す操作の内部が電圧を読んでいるのか、通信で数値を受け取っているのかを、通常の利用者が知らなくてもよい場合はある。だが測定に時間がかかる、故障時に前回値を返す、一定範囲を越えると測れない、といった性質は、利用方法に関係する。隠してしまえば、利用者は誤った前提で組み合わせる。

よい抽象化が隠すのは、使い方に影響しない内部の違いである。使う側の判断に必要な制限まで消せば、抽象化は説明不足へ変わる。インターフェースが短いことと、約束が十分であることは別なのだ。

この差を考えるには、代わりの実装を入れたときの想像が役に立つ。利用者が約束された操作だけを使っているのに、意味の違う結果になったら、何か重要な条件を約束から落としていた可能性がある。逆に、内部の配列を辞書へ変えても同じ約束を守れるなら、その違いはうまく隠せていたと言える。

### できることが同じでも、意味が違う

二つの対象が`read`というメソッドを持っているとする。名前が同じだから交換可能だろうか。一方は呼ぶたびに次のデータを返し、もう一方は毎回同じ現在値を返すかもしれない。返り値がどちらも数値でも、操作の時間的な意味が違う。

抽象クラスやインターフェースでメソッドの形を定めることは役に立つ。しかし、メソッドが存在することと、その意味上の約束を守ることは別に確認しなければならない。Pythonの抽象基底クラスも、すべての意味上の性質を自動で証明する仕組みではない。[R29](#ref-r29)

これを身近な道具で考えよう。同じ差し込み口に挿せる機器でも、必要な電圧や通信の意味が違えば交換できない。形が合うことは、交換可能性の一部にすぎない。ソフトウェアの操作名や引数の数も、同じように接続の表面を定めるものであり、内部で守るべき意味が残る。

だから共通の抽象を作るときは、名前をそろえるだけでなく、利用者が期待してよい性質を文章や条件で示す。繰り返し呼べば状態が変わるのか、入力を変更するのか、失敗したときに何が残るのか。こうした約束があって初めて、内部を知らずに組み合わせることが可能になる。

### 本質は、目的の言い換えなのか

ここまでの説明だと、本質的な性質とは用途に必要な性質にすぎないように見えるかもしれない。だが、哲学的な本質の問題を、設計者の都合だけで置き換えるのは早すぎる。ある物がそれであるために必要な性質と、ある仕事で重要な性質は同じとは限らない。

たとえば、図書館の管理にとって本の背表紙の番号は重要だ。しかし番号を貼り替えたから本そのものが別の本へ変わったとは通常考えない。逆に、内容を大きく書き換えた本を同じ版として扱ってよいかは、番号の一致だけでは答えられない。業務上の重要性を、そのまま対象の本質へ変換すると、こうした違いを見失う。

本質を対象の側へ認める立場には、人間の目的が変わっても対象が何であるかは変わらないという強みがある。一方、目的に応じた抽象に注目する立場は、なぜ同じ対象へ複数の有効なモデルを作れるかを説明しやすい。対立を公平に扱うなら、対象の成立条件と、記述の有用性を別々に問う必要がある。

本書が勧めるのは、プログラムの抽象を即座に形而上学的な本質と呼ばないことだ。「この計算では必要」「この制度では識別に使う」「この対象がそれであるために必要」と言い分ける。それだけで、強すぎる主張を避けながら、抽象化の実際の価値を認められる。

### 捨てた情報の台帳

モデルを引き継ぐ相手へ、何を含めたかだけでなく、何を含めなかったかも伝えるとよい。剛体として扱った、温度を一様とした、通信の遅れを無視した、同じ名前を同じ人物として扱った。こうした省略は、モデルの恥ではなく、その有効範囲を説明する情報である。

特に、以前は無視できた違いが、新しい用途では重要になるときに役立つ。静的な重量計算に使ったモデルを振動の検討へ流用するなら、時間変化や変形を省いたことを思い出す必要がある。データ構造が使い回せることと、前提まで使い回せることは違う。

読者がモデルを一つ作ったら、短い「捨てたものの一覧」を添えてほしい。単なる免責の文章ではなく、どの問いには答えないかを具体的に書く。モデルが何を語れないかを知っている人は、モデルを信じない人ではない。適切な問いに対して、より正確に使える人である。

### 要約を合成したとき、何が保存されるか

十個の箱の平均重量が5キログラム、別の二個の箱の平均重量が11キログラムだったとする。二つの平均を単純に平均すると8キログラムになる。しかし十二個全体の平均は6キログラムだ。集団の大きさを捨てたため、後の集計で必要な情報が失われたのである。

ここで平均という抽象が悪いわけではない。平均だけで答えられる問いには便利だ。ただし、複数の集団を統合するつもりなら、合計と個数、あるいは平均と個数を残す必要がある。抽象化が将来の操作に耐えるかは、どんな情報を保存したかによる。

同じことは、プログラムの部品を組み合わせるときにも起きる。それぞれの部品では十分な要約でも、結合後の問いへ答えるには不足するかもしれない。個別の部品が正しく動くことと、必要な情報が全体を通して保たれることは別である。

この例は、抽象化を「細部を忘れること」とだけ覚える危険を示す。大事なのは、捨てた後にどんな操作を行うかだ。単に小さくしたデータが、必要な組合せに対して閉じているとは限らない。後で統合する、比較する、元へ戻すといった予定が、何を残すべきかを決める。

哲学的な本質と設計上の必要情報を区別したうえで、それでも両者の接点はある。ある問いに対して重要な違いを保存し、重要でない違いを無視するという営みは、理解の多くの場面で行われる。抽象化は忘却の技術であると同時に、未来の推論の可能性を守る技術でもある。

### 抽象化は約束の置き場所である

ねじの頭を回せば締まる。利用者が結晶構造まで知らなくてよいのは便利だ。しかし締め付けトルクを軸力の代理として使うとき、摩擦の変化が隠れた前提になる。隠すこと自体が悪いのではない。隠した部分が外側の約束に影響するとき、どこでそれを検出するかが必要なのだ。

ソフトウェアのインターフェースも同じである。内部が変わっても外から見た契約が保たれるなら、利用者は変更を知らずに使える。性能や順序や誤差が契約に含まれるなら、戻り値の形だけ同じでも置換できないことがある。

ここでカントを思い出すことはできる。彼は、私たちが対象を経験する仕方の条件を問い、現象と物自体を区別した。ただし、その解釈には大きな議論があり、「APIが現象で、内部実装が物自体だ」と置き換えることはできない。APIの内部は通常、別の手段で調べられる対象だからだ。[R36](#ref-r36)

比較として有益なのは、私たちが何かを見るとき、見るための枠組みも働いているという問いを持てることだ。しかし、その問いを借りることと、カントの議論をソフトウェア設計へ翻訳し尽くすことは違う。

ここから見えてくるのは、優れた抽象化が「より高い言葉」ではなく、「どの問いについて同じ答えを保つか」の約束として考えられることだ。重量だけを残すなら、重量についての仕事を引き受ける。重心を捨てたモデルに転倒の説明まで要求しない。それが正しく捨てるということなのである。

**章末の問い**　物理シミュレーションでは、何を捨てているのだろうか。数式と高精細な色の付いた図があれば、捨てたものは見えなくなるのだろうか。

**出典と補足**　本質については[R06](#ref-r06)、抽象基底クラスは[R29](#ref-r29)、カントの現象／物自体と解釈の幅は[R36](#ref-r36)。重心の計算と設計上の議論は本書の例である。

## 第16章　物理シミュレーションは現実なのか

### 冷めるはずの物が計算の中で暴れ出す

熱い物体を涼しい部屋に置く。単純な近似では、室温との差が大きいほど速く冷めると考えられる。室温との差をθ、正の定数をkとすると、モデルは次の式になる。

> dθ/dt = −kθ

この章では、物体内の温度を一様とし、周囲の温度とkが一定だと仮定する。この微分方程式の解はθ(t) = θ(0) exp(−kt)で、正の初期値なら符号を変えずにゼロへ近づく。

時間を小さな幅Δtで区切り、現在の変化率を使って次の値を予測する陽的オイラー法では、θの次の値は(1−kΔt)倍になる。ここに、物理モデルとは別の条件が入り込む。

```python
def cooling(factor, steps=4):
    theta = 1.0
    result = [theta]
    for _ in range(steps):
        theta = (1 - factor) * theta
        result.append(round(theta, 4))
    return result

print(cooling(0.5))
print(cooling(2.5))
```

実行結果：

```text
[1.0, 0.5, 0.25, 0.125, 0.0625]
[1.0, -1.5, 2.25, -3.375, 5.0625]
```

`factor`はkΔtである。二つ目では温度差が正負を交互に変えながら増えていく。これは、この微分方程式が表す冷却の性質ではない。時間刻みと計算法が生んだ不安定性だ。

このスカラーの式について、誤差や状態の倍率の絶対値が1未満となる条件は、0 < kΔt < 2である。ただし1 < kΔt < 2では符号を交互に変えながら減衰するので、安定であることと、元の解の単調な振る舞いを保つことも違う。単調に非負のまま下がるには、正の初期値で0 < kΔt ≤ 1が必要になる。

### 方程式、離散化、丸めを分ける

ここには少なくとも三段階のずれがある。現実を単一温度の冷却モデルへ置き換えるモデル化。連続時間の式を離散的な更新へ置き換える近似。数を有限の桁で表す浮動小数点計算である。

### 検証と妥当性確認

計算がモデルの式を正しく扱っているかを調べる仕事と、そのモデルが現実の目的に適しているかを調べる仕事は違う。シミュレーションの議論では、verificationとvalidationの区別として整理されることがある。[R30](#ref-r30)

前者では、既知の解との比較、刻み幅を変えた収束、保存量の確認などが役立つ。後者では、実測との比較、境界条件の確認、予測したい領域での適合性が重要になる。両方を行わなければ、計算の精密さと現実の正確さを混同する。

熱設計で、接触熱抵抗をゼロと仮定したとする。計算を何倍細かくしても、その仮定によるずれは自然に消えない。実物では隙間や表面状態が熱流に影響するかもしれない。あるいは水を完全混合としたために、上部だけが熱い状態を表現できないかもしれない。モデルに変数として存在しない差異は、結果の図にも原則として現れない。

### 色が付くと信じたくなる

測定では数点しか温度が分からないのに、シミュレーションはすべての場所へ滑らかな色を付ける。画面は現実より詳しく見える。しかしその詳しさの一部は、モデルの仮定によって埋められた情報である。

これはシミュレーションの欠点だけではない。観測しにくい内部の状態を、理論と計算によって推定できるのは大きな力だ。問題は、どの部分が測定によって支えられ、どの部分がモデルの延長なのかを分けて読むことである。

モデルの対象が現実の構造を捉えていると考える実在論的な見方には、なぜ予測が成功するかを説明する魅力がある。モデルを特定の目的に役立つ道具として重視する見方には、不要な実在の断言を避けられる利点がある。両者の間にも多くの立場があり、予測の成功だけで唯一の存在論が決まるわけではない。

熱を計算したプログラム自身も発熱する。だが、その発熱が、計算対象の鍋の温度上昇を再現しているわけではない。シミュレーションの物理的な実行と、シミュレーションが表す物理過程は別だ。この区別は、次章の人工知能の議論で再び重要になる。

### ぴったり合う式が、二つある

測定値にぴったり合う式を見つけたら、現象を理解できたと言ってよいだろうか。三つの点だけを使って、簡単な実験をしてみよう。ここでは単位を持たない数の対応を扱う。

```python
def model_a(x):
    return x

def model_b(x):
    return x + x * (x - 1) * (x - 2)

for x in [0, 1, 2, 3]:
    print(x, model_a(x), model_b(x))
```

実行結果：

```text
0 0 0
1 1 1
2 2 2
3 3 9
```

0、1、2では二つの模型が一致する。しかし3では違う。後半に加えた項が、最初の三点では0になるよう作ったからだ。この例は、観測した点で一致することだけから、観測していない点でも一致するとは言えないと示す。現実の物理モデルはこれより多くの条件に縛られるが、データとの一致だけで一意に決まるとは限らないという教訓は残る。

実際の設計では、測定誤差もある。複数のパラメータを変えることで、同じ測定曲線へ近付ける場合がある。熱が逃げる経路を二つ考えたとき、合計の熱損失だけを観測していれば、各経路の寄与を分けにくいかもしれない。見た目の一致を改善する調整と、仕組みを識別する観測は別の仕事だ。

そこで、どの追加実験なら模型どうしの予測が分かれるかを考える。条件を変える、別の位置を測る、立ち上がりと定常状態の両方を見る。シミュレーションは、測定結果を美しくなぞるためだけでなく、次に何を測れば説明を区別できるかを考える道具にもなる。

### 刻みを細かくしても直らない誤り

オイラー法の時間刻みを十分小さくすれば、適切な条件のもとで、その微分方程式の解へ近付くことを期待できる。しかし、使った方程式が現実に合っていなければ、計算精度を上げても正しい現象へ近付くとは限らない。

たとえば温度を一様とした模型で、実際には上部と下部に大きな温度差があるとする。時間刻みだけを細かくしても、模型に存在しない空間の差は現れない。室温を一定と置いたなら、計算を百万回行っても、実験室の温度変動は勝手には入ってこない。解く精密さと、何を解くかの妥当性を分ける必要がある。

ここで、実装した計算が意図した方程式を正しく近似しているかという確認と、その方程式が用途に必要な現象を表しているかという確認が分かれる。前者では既知の解や刻み幅の比較が役立ち、後者では現物との比較や前提の検討が必要になる。両方とも重要だが、片方の成功をもう片方の代わりにはできない。[R30](#ref-r30)

同じことは、画面の解像度にも当てはまる。色の滑らかな等高線図が得られても、境界条件を間違えていれば美しい誤答になる。図の細かさは、知識の細かさと同じではない。むしろ、表現が精密になるほど、入力した前提が忘れられやすくなることに注意したい。

### 境界条件という、外の世界の要約

有限の模型を作るには、その外側をどう扱うかを決める必要がある。物体の表面で熱が逃げるのか、断熱されているのか、一定の温度へ接続されているのか。同じ材料、同じ形、同じ初期温度でも、この条件が違えば結果は変わる。

境界条件は、計算の端へ便宜的に付ける飾りではない。模型の外にある世界が、内側へどう作用するかを要約したものである。だから、部品単体の試験で合った模型を、そのまま製品へ組み込んでも合うとは限らない。周囲の流れ、取り付け方、接触する物体が変われば、外との関係が変わる。

プログラムの関数も似ている。入力の形式だけでなく、呼び出す環境が何を保証するかによって正しさが変わる。数値シミュレーションでは、その環境の約束が物理量として現れる。模型の中だけを細かく見て、境界で何を約束したかを忘れると、原因を内部へ探し続けてしまう。

読者がコップの湯の冷却を調べるなら、液体の量だけでなく、ふた、置く面、風、周囲温度も記録してみてほしい。何もかも厳密に管理する必要はない。何を固定したつもりなのかを自覚するだけで、同じ式が合ったり合わなかったりする理由を考えやすくなる。

### 保存されるはずのものを監視する

物理モデルには、エネルギーや質量など、条件のもとで保存される量がある。計算結果を確認するとき、そのような関係がどの程度保たれているかを見ると、単にグラフの形を眺めるより強い手がかりになる場合がある。

ただし、どの範囲を系として考えたかが重要だ。熱が外へ逃げるコップだけを見れば、内部のエネルギーは減る。コップと周囲の間の出入りを含めて考える必要がある。計算上の量が減ったから保存則違反だ、と直ちに判断してはいけない。模型の境界と、収支の対象をそろえることが必要になる。

数値計算で生じるずれも、何の誤差かを分けたい。有限の刻みによる近似、丸め、反復計算の打ち切り、入力値の不確かさ、現象の省略は別のものだ。同じ「誤差」という言葉へまとめると、刻みを細かくすればすべて改善するように見えてしまう。

また、出力の桁数を増やしても、入力に含まれる不確かさが減るわけではない。材料の性質が数パーセントしか分からないのに、小数点以下六桁の温度を示せば、見た目だけが確実になる。細かな数字を表示する能力と、その数字を主張する根拠は別なのである。

### 模型が自然より見やすい理由

シミュレーションでは、現物にセンサーを付けられない場所の値も表示できる。任意の時点を止め、断面を見て、条件を一つだけ変えて比較できる。これは大きな強みだ。現実より見やすいからこそ、仕組みを理解する手助けになる。

しかし、見えた値は模型から計算された値である。見える範囲が広いことと、独立した証拠が増えたことは同じではない。一つの誤った前提から百万点の値を出しても、百万回の独立した確認を得たわけではない。情報量の豊かさに、証拠の強さを重ねすぎないことが大切だ。

それでも、適切に検証された模型は、観測だけでは得にくい説明を与えうる。現物と模型を競争させ、どちらか一方を信じるのではなく、模型が示した差を現物で確かめ、現物のずれから模型を直す。計算と観測の往復があるとき、コンピュータの中の小さな世界は、外の世界を理解する道具になる。

## 第17章　人工知能は意味を理解しているのか

### 返事が来ると、誰かがいる気がする

「こんにちは」と送ると「こんにちは」と返る。たったそれだけでも、無反応な箱とは印象が変わる。人間は応答に敏感だ。しかし応答できることと、意味を理解していることの関係は、それほど簡単ではない。

```python
replies = {
    "こんにちは": "こんにちは",
    "温度は？": "23度です",
}
for message in ["こんにちは", "温度は？", "なぜ23度なの？"]:
    print(replies.get(message, "登録されていない質問です"))
```

実行結果：

```text
こんにちは
23度です
登録されていない質問です
```

これは応答表であり、現代の学習された言語モデルの仕組みではない。複雑な人工知能を、巨大な辞書と断言するための例でもない。もっと限定した役割を持つ。「適切に見える一回の返事」だけでは、どのような能力があるかを十分には特定できないと示す例である。

### 中国語の部屋の問い

サールの中国語の部屋では、中国語を理解しない人が、規則に従って記号を受け取り、別の記号を返す。外からは中国語を理解しているように見えても、内部の人は意味を知らない。そこからサールは、適切なプログラムを実行することだけでは理解に十分でないと論じた。[R32](#ref-r32)

重要なのは、「どんな人工物も考えられない」という単純な主張にしないことだ。争点は、形式的なプログラムの実行がそれだけで心的な内容を成立させるかにある。機械がどんな物理的な因果的能力を備えるかという問いは別に残る。

有力な反論はシステム全体に注目する。規則を実行する一部分が中国語を理解しなくても、記憶、規則、処理を含む全体が理解する可能性はないか。人間の脳の一個の細胞が日本語を理解しないことから、人間も理解しないとは言えない、という方向の反論だ。

サールは、規則や記憶を全部一人が内部化しても意味は分からないだろうと応じる。そこで反論側は、その人の自覚の有無と、構成されたシステムの能力を同じにしてよいかをさらに問う。この論争は、部屋の絵を一枚描けば終わる決着済みの定理ではない。

### チューリングが問いを置き換えた理由

チューリングの1950年の論文は、「機械は考えられるか」という語の定義に足を取られる代わりに、模倣ゲームによる問いへ置き換える。原論文の導入には男女と質問者のゲームがあり、そこへ機械を導入する形が示される。現在よく知られる人と機械の会話判定だけを、原文のすべてだと思わないほうがよい。[R33](#ref-r33)

会話でどこまで区別できるかは、観察可能な能力についての問いだ。それは意識や意味理解を直接測定する温度計ではない。一方、内部に触れられないという理由だけで、外部の行動をすべて無価値とするのも困る。他者の理解を判断するとき、私たちは説明、応用、訂正などの振る舞いに頼っている。

外から十分に区別できないなら理解を認めるべきだという方向と、振る舞いだけでは欠けているものがあるという方向の対立は、測定可能な事柄と存在する事柄の関係をめぐる対立でもある。

### 「23度」の根を探す

応答表の「23度です」は、部屋の温度とつながっていない。センサーがあっても、その値を読まなければ変わらない。そこで、測定値を読む仕組みを付ければどうか。温度が上がったら答えを変え、単位を変換し、センサー故障時には分からないと答えるようにすれば、世界との結び付きは増える。

それで意味理解が成立したと断言できるかは、なお別の問いだ。しかし、何が増えたかは具体的に言える。環境に応じた更新、誤りの検出、別の課題への応用が可能になった。このような能力を細分化すれば、「理解する／しない」の二択だけで議論するよりも、比較と実験を進められる。

人間でも、温度計の数字を読めることと、熱容量や熱抵抗を理解していることは違う。式を暗唱できても、単位が変わると答えを間違えることがある。理解は一枚の免許証というより、関連する能力のまとまりとして検討できる。

ただし、能力へ分解することに反対する立場は、そうした一覧が主観的経験を取り逃がすと指摘するだろう。赤について正しく話すことと、赤く見える経験を持つことは同じか。機能的な説明だけで十分かという争点は残る。

### 正しい言葉を、間違った理由で言う

温度を尋ねると、システムが「23度です」と答える。たまたま部屋は23度だった。答えは正しい。しかし、そのシステムが常に23度と答えるだけなら、温度を知っていると評価する根拠は弱い。結果の正しさと、正しく答える能力を区別する必要がある。

能力を調べるなら、条件を変える。室温を変えたとき答えも変わるか。単位を変えても整合するか。センサーが壊れたとき、前回値を今の値として断言しないか。質問の言い方を変えても同じ対象を指していると扱えるか。一回の成功を、関連する状況のまとまりの中へ置くのである。

これは、意味理解の十分条件をすぐ定義する作業ではない。それでも「偶然正解しただけ」という代わりの説明を弱めることはできる。何もかも分かるか、何も分からないかという二択から離れると、評価可能な問いが増える。

人間についても似た事情がある。暗記した答えを正しく言えても、図を変えた問題には答えられないことがある。反対に、説明の言葉が不器用でも、道具を適切に使い、誤りを直せる人がいる。理解をどんな証拠から認めるかは、人工知能だけの特別な問題ではない。

### 接地すれば、意味は自動で生まれるか

言葉をセンサーや行動へ結び付ければ、世界との関係は増える。だが、接続があるだけで意味が完成すると言うのも早い。温度センサーが二つあり、片方は室内、片方は屋外を測っているとする。システムがどちらを読んだかを区別せず「室温」と答えれば、数字が正しく読めても、言葉の対象を取り違えている。

接続には、位置、対象、時間、単位、校正、故障の可能性がある。何に由来する信号なのかを、利用する文脈へ結び付ける必要がある。物理的に線がつながることと、報告の意味が正しいことは同じではない。

反対に、あらゆる言葉が直接の感覚経験を持たなければ意味を持てないとすると、人間の知識も説明しにくくなる。私たちは行ったことのない場所や、直接見たことのない現象について、他人の証言や理論を通じて学ぶ。世界との接続は、一つの主体の一回の観測だけに限られない。

そこで、直接の信号、他者から得た情報、内部での推論を分けて考えたい。どれも意味に関係しうるが、誤り方が違う。センサーは別の場所を測るかもしれない。記録は古いかもしれない。推論は前提を取り違えるかもしれない。理解を議論する際にも、こうした具体的な失敗の区別は役に立つ。

### 規則に従う全体は、どこで終わるか

中国語の部屋に対するシステム反論を考えると、「全体」の範囲が気になってくる。部屋の中の人と規則書だけか。記憶装置も含むか。外から情報を与える人々や、言葉が使われる社会まで含むのか。範囲を広げれば説明できる関係は増えるが、何が理解しているのかという主語も変わる。

人間も、辞書、メモ、他者との会話を使って考える。計算を紙へ書いたから理解していないとは通常言わない。しかし、道具を使う人の理解と、道具自体の理解を同じにしてよいわけではない。補助された能力の担い手をどこに置くかは、慎重に考える必要がある。

プログラムの性能を評価するときも、同じ問題が具体的に現れる。外部の検索、専用の計算器、人間による確認を含めた全体の結果と、中心のモデル単体の能力を区別する。全体が役立つことは重要だが、その成功を構成要素のどれへ帰属させるかは別の問いである。

この区別は、能力を低く見積もるためではない。どこを変更するとどの能力が失われるかを理解するためだ。システムの境界を明示すれば、より公平な比較ができ、失敗時の改善先も見えやすくなる。意味の問題でも、主体の境界を曖昧にしたまま議論を進めると、途中で主語が入れ替わってしまう。

### 反証できない判定は、何を教えるか

どんな返事をしても「ただの計算だから理解していない」と言うなら、どの観測が評価を変えるのだろうか。逆に、流暢な返事が一度あれば「理解している」と決め、誤答はすべて些細な例外とするなら、その判断も検査しにくい。

ここで、哲学的立場が実験だけで決着しなければ無意味だと言いたいのではない。意味理解を何と考えるかに、観察の解釈を超えた論点があることは認められる。ただ、実験によって分かることを語るときは、評価を改める条件をできるだけ明示したほうがよい。

たとえば「この範囲の説明を新しい状況へ適用できる」という主張なら、状況を変えた課題を用意できる。「どんな文脈でも完全に意味を理解している」という主張は、対象が広すぎて確認が難しい。主張の大きさを、証拠の範囲に合わせることが大切だ。

この節の考え方は、人工知能への期待と批判の両方に向けられる。期待する側も批判する側も、一つの成功例や失敗例を選ぶだけでは、能力の全体像を示せない。どの条件で何ができるかを細かく調べることが、強い賛否より先に必要になる。

### 誤りを語ることにも、意味がある

ある対象を正しく表すことだけでなく、誤って表すことが可能だという点にも注目したい。温度についての文が間違っていると言えるのは、その文が何について何を主張しているかを、何らかの基準で捉えているからである。ただの模様なら、事実との不一致とは呼びにくい。

ただし、機械の出力へ人間が正誤を与えられることだけで、機械自身に人間と同じ意味が成立しているとは限らない。外からの解釈と、内部の状態が持つ内容をどう関係付けるかが争点として残る。ここでも、評価できることから存在を一足飛びに結論しない姿勢が必要になる。

それでも実務では、誤りを検出し、根拠へ戻り、答えを訂正できる仕組みを作れる。自信のある言い方をすることと、誤りを直す能力は違う。知識の出所、観測時点、推論の条件を残せば、利用者も判断しやすくなる。意味理解の最終解答がなくても、よりよい知的な道具を作る作業は進められる。

中国語の部屋を巡る対立は、こうした実務を停止させるための壁ではない。何を達成したら何を認めるのかという、評価の基礎を問い直す機会である。コンピュータに向かって「分かった？」と尋ねるとき、私たちは同時に、自分が「分かる」という言葉で何を求めているかを問われている。

### 模擬と実現を一つの比喩で決めない

前章では、熱のシミュレーションが鍋を温めないと確認した。しかし、それを根拠に計算は理解を実現できないと結論するには、理解が熱と同じ種類の性質だという追加の議論が必要になる。

一方、足し算を模擬するプログラムは、適切な意味で実際に足し算を行う。模擬チェスもチェスの規則に従って対局できる。何を模擬と呼び、何を実現と呼ぶかは、対象の性質と成立条件による。どの比喩が正しいかこそ、議論されている部分なのである。

「言葉を出したから理解した」とするのも、「計算だから理解しない」とするのも、結論を前提へ忍ばせやすい。何を証拠とし、どの反例なら立場を改めるかを先に考えたい。

本章は特定の最新モデルの性能順位を扱わない。技術が変わっても、評価の対象を分ける作業は残る。文の正確さ、未知の状況への対応、世界との接続、自己訂正、主観的経験。これらを一つの点数にしてしまう前に、どれを知りたいのかを確認する。

ここから見えてくるのは、意味をめぐる難問を残したままでも、確かめられる能力を増やせるということだ。決着を急がないことは、研究を止めることではない。

## 第18章　プログラムは発見されるのか、発明されるのか

### 同じ答えへ向かう二つの道

1からnまでの整数を掛け合わせる階乗を、二通りに書いてみよう。0の階乗は1とする。

```python
def factorial_loop(n):
    result = 1
    for k in range(1, n + 1):
        result *= k
    return result

def factorial_recursive(n):
    if n == 0:
        return 1
    return n * factorial_recursive(n - 1)

print(factorial_loop(5), factorial_recursive(5))
```

実行結果：

```text
120 120
```

ここでは入力を小さな非負整数に限定している。負数は受け付ける仕様にしていないし、大きな値での再帰の深さや計算資源の問題もある。その条件のもとで、二つのコードは同じ数学的な関数を計算する。

では二つは同じプログラムなのか。ソースコードは違い、呼び出し方や必要な資源も違う。同じ結果を返すという水準では等価でも、手続きや実行の水準では差がある。第5章の「同じ」が、今度は計算そのものへ戻ってきた。

### 数学は私たちを待っていたのか

数学的プラトニズムでは、数や集合などの抽象的対象は、人間の言語や思考から独立に存在すると考える。そうなら、数学的な真理を知ることは発見に近い。人類がいなくても、自然数についての関係は変わらないと考えられる。[R03](#ref-r03)

他方、形式主義的な方向では、規則に従う記号の操作を重視し、それが直ちに抽象的な世界の対象への存在論的な約束を要求するとは考えない。ただし形式主義には複数の形があり、「数学は意味のない遊びだ」と一言で片付けられない。[R34](#ref-r34)

プラトニズムには、数学の客観性を説明しやすい魅力がある。誰が計算しても同じ関係へ到達するのは、対象が私たちと独立だからだと考えられる。一方、空間や時間の中で因果的に働かない抽象的対象を、私たちはどう知るのかという難しさがある。

形式的な規則を重視する見方には、実際の証明や計算の作業へ近づける利点がある。しかし、なぜある形式が自然現象の記述に強く役立つのか、なぜ単なる任意の遊び以上の重要さを持つのかという問いが残る。どちらの立場にも、簡単な勝利宣言を許さない課題がある。

### 発明した規則から、発見される帰結

チェスの規則は人間が作った。しかし、その規則のもとである局面が詰みかどうかは、プレイヤーの気分では変えられない。人工的な出発点から、好きに変更できない帰結が生まれる。

プログラムにもこの二重性がある。データ構造や仕様を選ぶのは設計者だが、その選択の帰結を全部見通せるとは限らない。ある操作を許すと、意図しなかった状態へ到達できる。新しく実装した規則の中で、設計者自身が未知の性質を発見するのである。

だから、発見か発明かという二択を、作業全体へ一括して適用しなくてもよい。問題の定式化は発明に近く、定式化したものの性質を調べる作業は発見に近い、と分けて考えられる。これは数学の存在論の最終解決ではないが、実際の制作経験をよく捉える。

熱を逃がす部品の形状を考えるときも、設計者は形を選ぶ。しかし選んだ形がどこで共振するかを、自由に宣言することはできない。発明した構造が、発見を要求する。

### コード、アルゴリズム、実行

紙に書かれたコード、計算の手続き、一回の実行は区別したい。コードは特定の言語で書かれた記述である。アルゴリズムは、どの程度の細かさで同じ手続きと見るかに関わる。実行は、ある入力と環境で実際に進む出来事だ。[R35](#ref-r35)

同じアルゴリズムを別の言語で書ける。一つのコードを何度も実行できる。逆に、異なる手続きが同じ数学的関数を計算できる。これらの区別を消すと、ソースを保存したから実行も保存できた、という錯覚が起きる。

再現のためには、入力、依存する道具、環境、外部資源などが必要になる場合がある。料理のレシピが同じでも、材料や火力や鍋が違えば仕上がりが変わる。もちろん、適切な抽象化によって環境差を隠せる場面もある。その隠し方が成立する範囲を明らかにするのが実装の仕事である。

### 紙に書かれる前の手順

誰かが新しいアルゴリズムを考えた日、そのアルゴリズムは初めて存在したのだろうか。それ以前にも、同じ手順を記述すれば同じ結果が得られたはずだという意味では、可能な構造としてすでにあったように思える。一方、具体的な記述、理解、用途は、その人の活動によって初めて現れた。

ここで、存在の問いを一つにまとめると対立が激しくなる。紙の上の記号列がいつ作られたかと、その記号列が表す計算上の関係が人間から独立してあるかは別の問いだ。発明したという日常的な言い方と、数学的構造を発見したという哲学的な言い方が、必ず矛盾するわけではない。

数学的プラトニズムは、数学的対象の存在や性質を人間の活動から独立したものとして捉える方向を持つ。一方、形式主義的な見方にも複数の立場があり、単に数学は何でも好きに決められる遊びだという説明では足りない。形式的規則の操作と、その規則によって成立する推論の関係を真剣に扱う。[R03](#ref-r03)[R34](#ref-r34)

プログラムを書く経験には両方の感触がある。変数名や表現方法は選べる。しかし一度規則を決めると、思いどおりにならない帰結が出る。自分で作ったコードのバグに驚くことは、創造者であることと、帰結を発見する者であることが両立する身近な例だ。

### 同じ計算を、違う姿で運ぶ

階乗を反復で計算する方法と再帰で計算する方法は、入力の範囲を適切に定めれば同じ数学的な値を与えられる。しかしソースコードは違い、実行の仕方も違う。現実の処理系では、資源の使い方や扱える入力の範囲に差が出ることがある。

では、二つは同じアルゴリズムなのか、違うアルゴリズムなのか。答えは、どの抽象度で数えるかに関わる。同じ関数を計算することを重視すれば一つにまとめられる。計算の手順や使用するデータ構造を重視すれば区別したくなる。コードの一致、手順の一致、入出力関係の一致は、異なる水準である。

この区別は、別のプログラミング言語へ移植するときにも役立つ。構文を置き換えるだけでなく、整数の範囲、評価の規則、例外の扱い、外部との接続などを確認する必要がある。同じように見える式が、異なる言語で同じ約束を持つとは限らない。

一方、内部の表現が違っても、必要な振る舞いを保てれば移植は成功しうる。そのとき保っている「同じもの」は、特定のビット列ではない。定めた観測の範囲での関係や操作である。ソフトウェアが複数の装置へ移りながら継続できる理由の一部は、この抽象度の移動にある。

### 無限の手順と、有限の机

数学的には、任意の大きさの自然数を入力として考えられる。実際の机の上のコンピュータには、記憶領域と時間の制限がある。この差を忘れると、計算可能であるという理論上の主張を、すぐ実行できるという実務上の約束へ読み替えてしまう。

停止する手順でも、結果が出るまで極端に長い時間が必要なら、現実の問題解決には使いにくい。反対に、厳密な答えをすぐ得られなくても、必要な精度の近似や特定の入力範囲への解法が役立つ場合がある。可能性の分類だけでは、設計の価値は決まらない。

ここで発明の仕事が見えてくる。計算すべき関係を知ることに加え、どの資源を使い、どの精度を選び、どの入力に集中するかを決める。現実の制約のもとで使える形を作ることは、抽象的に正しい式を示すこととは別の達成である。

ただし、それを理由に理論は現実と無関係だと言うのも違う。理論は、一般に何が可能で何が不可能か、どんな構造が利用できるかを教える。実装は、その地図の上で具体的な経路を選ぶ。地図を描くことも、道を作ることも必要なのである。

### 発見の証拠と、発明の評価

ある手順を発見したと主張するとき、何を示せばよいだろう。まず、その手順が何を計算するかを説明し、必要な性質を確かめることになる。発明として評価するときは、使いやすさ、速さ、変更のしやすさなど、目的に関係する観点が加わる。

この二つは競合するとは限らない。美しい数学的関係を使って実用的な処理を作ることもあれば、実用上の工夫から一般的な構造が見えてくることもある。発見か発明かを一度だけ判定して片方へ押し込むより、作業のどの部分がどちらの問いを呼ぶかを見たほうが豊かだ。

読者が同じ問題へ二つのプログラムを書いたら、どこが自由に選べ、どこが問題の条件に縛られていたかを書き出してみてほしい。入力形式を変える自由はあったか。答えの意味は変えられたか。誤差を許す自由はあったか。何を固定しているかによって、創造性の所在も変わる。

ここでプログラミングの創造は、無から何でも生み出す力ではなく、制約の中で表現と手順を選ぶ力として見えてくる。制約があるから創造でないのではない。制約の帰結を理解して初めて、よい選択ができるのである。

### 実行されたことが付け加えるもの

紙に正しいコードがあることと、装置がそれを実行したことは違う。実行には、電力、記憶媒体、入力、読み取る仕組み、結果を使う環境が必要になる。抽象的な計算の構造があるとしても、それだけで今日の注文票は印刷されない。

逆に、装置に電流が流れたという物理的記述だけでは、何を計算したかの説明として不十分な場合がある。同じ物理的な変化へどんな符号や規則を対応させるかが必要だからだ。ただし、その対応を好き勝手に言い張れば、どんな物体もどんな計算もしていることになるという問題がある。計算の実装をどう捉えるかは、コンピュータ科学の哲学の重要な論点である。[R35](#ref-r35)

本書ではその論争を一つの定義で閉じない。少なくとも、記号としてのコード、抽象的に捉えた計算、物理的な実行を区別すれば、発見と発明をめぐる言葉の衝突を減らせる。実装の達成は、これらを無造作に同一視することではなく、相互の関係を働く形にすることにある。

### 変えられない帰結を、作ったと言えるか

盤面の大きさと駒の動きを、自分で決めたゲームを考えよう。規則の発明者は私たちだ。しかし、その規則のもとで必勝法があるかどうかを、発明しただけで知っているとは限らない。実際に遊び、探索し、証明しなければ分からないことがある。

ここで、帰結も人間が好きに決めたのだと言うと、規則に反する結果まで認めてよいのかという問題が出る。一方、帰結を発見するのだからゲームの規則も初めから実在していたと結論する必要はない。規則を選ぶ行為と、選んだ規則に拘束されることを分ければ、発明と発見の共存を説明できる。

プログラミングでも、データ構造と操作を決めた後、その組合せが思いがけない状態へ達することがある。設計者は規則の作者だが、あらゆる実行の観察者ではない。自分の作った世界を研究し直す必要がある。これは創造の失敗ではなく、有限の知識で複雑な規則を扱うことの普通の姿だ。

この経験は、自然界も誰かが作ったゲームだという証拠にはならない。私たちが規則を発明できるという事実から、自然法則にも発明者がいるとは導けない。ただ、作ることと知ることが別の仕事だという区別は、どちらの話をするときにも役立つ。

だから、プログラマを小さな宇宙の創造者と呼ぶなら、その宇宙の最初の探検家とも呼びたい。道を敷いた本人が、地図を描き直し、思わぬ行き止まりへ出会う。発明の喜びと発見の驚きは、同じ作業机の上に置くことができる。

### 無限を一行に押し込む

自然数を順に生成する規則は短く書ける。だが、無限個の自然数を全部、有限のメモリへ同時に展開したわけではない。必要になった次の値を作る手続きを表現したのである。

有限の記述が無限の対象について語れることと、無限の実行が完了することは別だ。ここには本書の副題への重要な留保がある。実装できるという言葉を、有限の表現を作れること、必要な値を計算できること、全体を物理的に展開できることのどれに使っているのかを決めなければならない。

ここから見えてくるのは、私たちが作った世界にも、私たちがまだ知らない事実があることだ。設計者であることは、全知であることではない。規則を書いた人が、その規則の最大の研究者になる理由がここにある。

## 第19章　仕様書という神、バグという反逆

### 指示通りに動く困った装置

「温度が25度以上なら冷却を動かす」。分かりやすい仕様だ。だが測定値が24.9度と25.1度を行き来すると、装置は起動と停止を繰り返すかもしれない。プログラムは一度も指示に背いていない。それでも利用者は満足しない。

```python
temperatures = [24.9, 25.1, 24.9, 25.1]
simple = [t >= 25.0 for t in temperatures]

running = False
stable = []
for t in temperatures:
    if t >= 26.0:
        running = True
    elif t <= 24.0:
        running = False
    stable.append(running)

print(simple)
print(stable)
```

実行結果：

```text
[False, True, False, True]
[False, False, False, False]
```

後半は、起動を26度以上、停止を24度以下とする簡略化したヒステリシスを入れた。この入力列では起動条件に達しないので停止のままだ。同じ温度でも過去の状態によって動作が異なりうる。現実の空調制御にはさらに多くの条件が必要だが、ここでは「現在の温度だけで決まる」という世界観を変更したことが重要である。

### 仕様通りと、目的通り

仕様は約束を明示する。そのため、実装の欠陥を指摘する基準になる。しかし仕様自体が目的を取り逃がしている場合は、仕様通りであることだけでは足りない。正しさには、形式的な適合性と、利用の文脈での適切さという別の側面がある。[R35](#ref-r35)

「仕様が正しければ実装は正しいのか」という問いには、まだ一段飛躍がある。正しい仕様があっても、実装がそれに従うとは限らない。さらに実装が従っても、ハードウェアや外部環境についての前提が破られれば、望む結果は得られない。

ここまで分けると、責任の押し付け合いに見えるかもしれない。しかし本来は逆だ。どこを修正すれば問題が減るのかを明らかにするための区別である。要求、仕様、コード、装置、使い方を全部「バグ」という一語にすると、対応先を間違える。

### 観察が仕様を訂正する

あるセンサーは通常±0.1度程度の揺れしかないと仮定した。それを前提に制御を作り、試験するともっと大きく揺れる。センサーが故障しているかもしれないし、取り付け位置で温度分布を拾っているかもしれない。仕様が十分な観察を待たずに固定された可能性もある。

ここでは自然が仕様違反をしたわけではない。仕様の仮定が自然に合っていなかったのである。人工的なルールを決められる部分と、観察によって学ばなければならない部分を分ける必要がある。

設計レビューで役立つのは、「要求される動作」「そのために仮定した条件」「仮定を確認する方法」を別に書くことだ。たとえば要求は安定した室温、仮定はセンサーの応答と装置の能力、確認方法は条件を振った試験になる。要求を強く唱えても、仮定が確認されたことにはならない。

### 完全な仕様書は絶対に書けないのか

ここでも言い過ぎを避けたい。範囲が限定された単純な関数や有限モデルなら、振る舞いを完全に定められる場合がある。完全な仕様など一切不可能だ、という結論を停止問題から引き出す必要はない。

問題は、現実につながる大規模なシステムで、どこまでを仕様の対象に含めたかである。性能、障害時の動作、人間の誤解、運用変更まで含めると、書くべきことは増える。書かなかったことが自然に安全な値へ決まるわけではない。

固定した仕様を厳格に守る方針には、責任と検査条件を明確にする利点がある。経験に応じて仕様を改訂する方針には、新しい知識を取り込む利点がある。前者だけでは現実の変化へ対応しにくく、後者だけでは過去の判断の根拠が流れてしまう。改訂を認めつつ、何をなぜ変えたかを残すことが重要になる。

### バグが文化になるとき

利用者が、意図していなかった操作を便利に使い始めることがある。ファイル名の癖、並び順、画面の抜け道。修正すれば「正しくなった」のに、利用者の仕事が壊れる。すでに観察された振る舞いが、事実上の期待として組み込まれているからだ。

これはどんなバグも保存せよという話ではない。危険な欠陥は修正する必要がある。ただし、変更の対象はコードだけではなく、利用者の学習や他のシステムの依存でもある。何が仕様かは、文書だけでなく運用との関係によって問題になる。

テセウスの船の修理に似て、システムを直し続けると、何を同じ製品として保つかが問われる。画面の見た目か、入力形式か、結果か、既存業務が続くことか。互換性という言葉の中にも、複数の同一性が入っている。

### 正しい動作が、悪い結果を作る

部屋が設定温度より暑ければ冷やし、低ければ止める。単純な仕様だ。ところがセンサーの値が境界の近くで揺れると、機械が短い間隔で運転と停止を繰り返す。プログラムは条件に正しく従っているのに、機器や利用者にとって望ましくない結果を作る。

ここでは、実装の誤りと、仕様の不足を区別する必要がある。条件を逆に書いていたなら実装の問題だ。条件どおりでも頻繁な切り替えが起きるなら、時間的な振る舞いを仕様へ入れる必要があるかもしれない。二つの温度境界を設ける、最小の運転時間を設ける、測定値の扱いを変えるなど、複数の設計が考えられる。

ただし、どの対策も別の性質を変える。切り替えを減らせば温度の変動が増える場合がある。測定を平均すれば反応が遅れる。最小時間を設ければ、すぐ停止したい状況との関係を決める必要がある。バグを一つ消すという単純な図ではなく、複数の要求の折り合いを付ける作業になる。

ここで仕様は、理想的な動作を天から授ける文章ではない。何を優先し、どの変動を許すかという判断の記録になる。その判断を隠して、仕様に書かれているから正しいと言ってしまえば、決めた人の責任が見えなくなる。機械が厳密に従うほど、何へ従わせたかが重要になるのだ。

### 要求は、測れる形へ変わるときに縮む

利用者は「使いやすくしてほしい」と言う。実装する側は、そのままでは試験できないので、操作数、応答時間、入力項目などへ分ける。具体化は必要だが、この変換で何かが失われる。操作回数を減らしても、意味が分かりにくい一回の操作になれば、使いやすくなるとは限らない。

同じことは「安全」「正確」「公平」「分かりやすい」にも起きる。測定可能な指標を選ぶと、検査と比較はしやすくなる。しかし選んだ指標が元の目的を完全に表すとは限らない。指標を良くすることと、目的を達成することを分けて考える必要がある。

たとえば問い合わせへの応答時間だけを短くすれば、すぐに定型文を返すシステムが優秀に見える。利用者が問題を解決できたかを見れば、違う評価になるかもしれない。測りやすいものを代理として使うことは避けがたいが、代理だということを忘れないことが大切だ。

この問題に対して、仕様を曖昧なままにしておくのは解決ではない。具体的な条件を作り、その条件が目的とどのようにつながるかを確認する。試験で確認する性質と、利用の場面で確かめる性質を分ける。仕様が目的の翻訳であるなら、翻訳の良し悪しも検討の対象になる。

### 利用者が知らない規則も、利用者を動かす

入力欄に収まらない名前を省略してもらう。住所の形式が合わない人には別の窓口へ行ってもらう。システム上は存在しない状態なので、現場で別の処理をしてから登録してもらう。こうした対応が積み重なると、ソフトウェアの模型に合わせて現実の仕事が変わっていく。

模型が現実へ作用すること自体は悪くない。新しい予約方法が待ち時間を減らし、共通の部品番号が作業を整理することもある。ただし、記述する道具が行動を規定する道具へ変わるとき、影響を受ける人の側からも評価する必要がある。

プログラムに存在する項目だけが、会議で見える問題になる場合がある。記録欄のない手直し作業は集計されず、集計されない仕事は改善対象から外れる。データがないから作業がないのではなく、記録の設計が作業を見えなくしているのかもしれない。

ここで形而上学的な問いが、組織の実務と接続する。何を一個として数えるか、何に名前を与えるか、何を例外として消すか。その決定は、ただコンピュータ内部の分類を変えるだけではない。人が何を現実の問題として扱うかにも影響する。小さな宇宙の外側に、利用者が暮らしているのである。

### 仕様変更と、過去への責任

仕様が変わるとき、過去の実装はバグになるのだろうか。昨日の仕様に合っていたものが、今日の要求に合わないことはある。しかし、後から得た知識を使って、当時何を保証していたかまで曖昧にすると、履歴の評価が難しくなる。

そこで、仕様の版、適用する時点、変更理由を残す意味がある。何が当時の約束で、どの発見によって改訂したのかが分かれば、単なる言い換えと実際の改善を区別しやすい。仕様書を最新の一枚だけにすると、なぜ奇妙な条件が入ったのかという経緯が消えることがある。

ただし、履歴を保存することは、古い判断を永遠に正当化することではない。前提が崩れたなら変更が必要になる。過去を理解することと、過去へ従い続けることは違う。規則を変えた理由を記録するのは、その違いを扱えるようにするためだ。

プログラムの予想外の動作が便利で、新しい仕様として採用される場合も考えられる。しかし便利だと感じた一例だけで、すべての利用者への影響が分かったわけではない。どんな条件で再現し、どの依存関係ができるかを確かめる必要がある。偶然の振る舞いを約束へ変えることには、新しい責任が伴う。

### 誰にも書けない、一枚の完全な仕様書

大きなシステムでは、一人がすべての前提を理解しているとは限らない。利用者、開発者、運用者、製造担当者が、それぞれ違う知識を持つ。仕様をまとめる仕事は、その知識を一枚の文章へ単純に足し合わせることではない。互いに矛盾する要求や、語られていない前提を見つけることでもある。

たとえば「いつでも変更できる」と「一度決めた値は絶対に変わらない」を、違う人が同じ項目へ求めているかもしれない。どちらも、その人の仕事の文脈では自然な要求である。ここで必要なのは、どちらかを無知と決めつけることより、現在の値と確定時点の値を分けるなど、衝突していた概念を整理することだ。

このような仕様の不完全さを、直ちにゲーデルの不完全性定理へ結び付ける必要はない。単に知識が不足している、目的が変わる、言葉が曖昧である、といった実務的な理由が多い。難しい定理の名を付けなくても、十分に難しい問題なのだ。

反対に、実務上の不完全さがあるから形式的な記述は無意味だとも言えない。明確に書ける部分を明確にすれば、まだ決まっていない部分が見える。仕様を完璧な神託としてではなく、検査と改訂に開かれた約束として扱えば、精密さと柔軟さを両立させる余地が生まれる。

### バグ報告を、世界観の点検へ変える

不具合の報告を受けたとき、まず再現条件を集める。次に、どの約束が破られたかを確認する。実装が仕様に違反したのか、仕様が実際の利用を取りこぼしたのか、外部との接続で前提が崩れたのか。原因の層を分けると、修正も変わる。

単に条件分岐を一つ足せば、その入力だけは通るかもしれない。しかし、同じ前提を使う別の場所には同種の問題が残る。未測定をゼロとして扱っていたなら、平均計算だけでなく警報や表示にも影響する。バグを世界観の点検へつなげるとは、この共通の前提を探すことだ。

もちろん、すべての不具合が壮大な哲学問題ではない。綴り間違いや単純な計算の取り違えもある。重要なのは、何でも存在論へ飾り立てることではなく、必要なときに一段上の前提を問い直せることだ。よい修正は、目の前の失敗を止めるだけでなく、同じ誤解から生まれる次の失敗を減らす。

### 神の立場から降りる

プログラマは小さな世界の規則を決める。しかし、その世界を動かす計算機、入力を与える人、取り扱う現物まで、すべて作ったわけではない。世界の創造者という比喩は、責任を感じるためには役立つが、万能感を正当化するためには危険だ。

むしろ、設計者は部分的な知識で約束を作り、実行結果や利用者の反応によって約束を改める立場にいる。形而上学との接点は、絶対的な答えを持つことではなく、自分がどんな前提で世界を区切っているかを問い直すところにある。

ここから見えてくるのは、バグが仕様への反逆とは限らず、仕様の背後にあった仮説の反証になりうることだ。エラー報告は、世界が設計者へ送り返した批評かもしれない。ただし、単純な打ち間違いまで荘厳な哲学的事件にする必要はない。セミコロン一つに宇宙の責任を負わせるのも気の毒である。

**章末の問い**　ここまで実装の力と限界を見てきた。では副題に戻ろう。存在するとは、結局、実装することなのだろうか。

## 第20章　存在するとは、実装することなのか

### 倉庫へ戻る

冒頭の倉庫に戻ろう。現物は一台あるのに、販売可能在庫はゼロだった。ここまで来た私たちは、どちらかを間違いだと決めつけずに、問いを分けられる。

```python
warehouse = {"A17": {"reserved": True}}
physical_count = len(warehouse)
available_count = sum(not item["reserved"] for item in warehouse.values())
print(physical_count, available_count)
```

実行結果：

```text
1 0
```

このコードの`physical_count`も、本当は現物を直接数えてはいない。現物に対応すると想定した辞書の行を数えている。名前を物理的台数と付けても、センサーや棚卸しの作業は省略できない。

その一方で、予約済みという区分は、単なる空想ではない。適切な契約や業務の中では、誰に販売できるかを変える。物体そのものの形を変えずに、社会的な扱いを変える状態が実装されている。

### 四つの存在の問い

本書の議論を、最後の実験道具として整理しよう。第一に、記述があるか。第二に、その記述に従う計算上の対象や処理が成立するか。第三に、それを実行する物理的な仕組みがあるか。第四に、その記述が表している外部の対象があるか。

ドラゴンのデータを書けば、第一の意味で記述はある。ゲームの中で動かせれば、第二の意味で計算上の振る舞いがある。コンピュータで実行すれば、第三の意味で物理的な過程もある。だが、第四の意味で空を飛ぶ動物が存在するとは限らない。

逆に、まだ誰も記録していない岩は、プログラムへ登録されていないからといって消えないだろう。少なくとも、外部世界の存在を実装から独立に認める通常の見方ではそうなる。

表2　「存在する」の対象を分ける

|問い|確認するもの|それだけでは言えないこと|
|---|---|---|
|記述があるか|文章、コード、データ|内容が無矛盾か、現実にあるか|
|計算上成立するか|規則と実行可能な処理|外部の対象も同じ性質を持つか|
|物理的に実行されるか|装置と実際の過程|表された対象そのものが実現したか|
|外部の対象があるか|観察、測定、証拠|唯一の表現や分類が決まるか|

この表は存在の普遍的な分類体系ではない。本書の混同を防ぐための道具である。社会的な制度、数学的対象、意識などをどこへどう位置付けるかには、さらに議論が必要だ。

### 実装できるものは実在するのか

何かを実装したなら、その実装があるという限定された主張はできる。しかし表現された対象の実在まで一緒に認めることはできない。洪水の計算は机を濡らさない。架空の銀行の残高表示は、現実の支払能力を保証しない。

ただし実装が現実に作用しないわけではない。予約システムの誤りは配送を変え、制御ソフトの出力は機械を動かす。デジタルなものと現実を完全に切り離すのも誤りである。問題は、どの関係を通じてどんな効果を持つかだ。

操作的な立場は、対象について何ができ、何を観測できるかを重視する。実在論的な立場は、私たちが現在扱えるかとは独立に対象が存在しうると考える。前者は確認の方法を明確にしやすく、後者は観察や実装の能力を超えた世界を認められる。だが操作の可能性だけで存在を定義すれば、現在の道具の限界を世界の限界と取り違えかねない。逆に実在を認めるだけでは、それについての具体的な知識は得られない。

### 実装できないものは存在しないのか

実装できないという言葉にも段階がある。予算がない。計算資源が足りない。現在の技術では分からない。数学的に一般的手続きが存在しない。これらは異なる。

台風のすべての状態を細部まで計算できなくても、台風が存在しないとは言えない。抽象的な数学の領域では、計算可能なものと存在すると認めるものの関係自体が、採用する立場によって論点になる。第13章の限界の定理を、一足飛びに世界全体の存在判定へ使うことはできない。

また、有限の記述を持つことと、物理的に実現できることも違う。極端な資源を要求する設計図は、紙の上で明確でも建造できないかもしれない。「書けた」「計算できた」「作れた」「役に立った」は、別々の達成である。

### 哲学の実験装置としてのコンピュータ

それでもコンピュータは、形而上学を考えるための良い実験装置になれる。たとえば、同一性をIDで保つ世界と、内容の一致だけで保つ世界を作り、どの操作で差が出るかを比べられる。欠如を一種類で表す場合と理由ごとに分ける場合の帰結も見える。

ただし、その実験が直接調べているのは、明示した前提の帰結である。現実がその前提に従うことは、別に確かめなければならない。哲学の立場をコードにしたつもりでも、コードに落とすときに重要な論点を省いた可能性がある。

この限界を認めることは、実験を弱くするだけではない。何についての反例なのかを正確にできる。自分の主張が崩れたのか、実装が間違っていたのか、単純化しすぎたのかを切り分けられるからだ。
